# Decisiones Arquitectónicas (ADRs)

## ADR-013: Stack desktop con Tauri 2 (Rust + Vite + Web Components)

- **Fecha**: 2026-07-08
- **Estado**: Aceptada
- **Contexto**: Se necesita una app móvil/desktop multiplataforma con frontend web y backend nativo para una aplicación de tracking de rutas en moto.
- **Decisión**: Tauri 2 con Rust backend y Vite + TypeScript + Web Components frontend. Adaptado para target mobile (Android/iOS) además de desktop.
- **Alternativas consideradas**: Electron (descartado: bundle pesado, consume mucha RAM), React Native (descartado: requiere Dart/JS bridge complejo), Flutter (descartado: requiere Dart, no comparte lógica con web).
- **Consecuencias**: Bundle ligero (~5-10MB) gracias al WebView nativo del SO y Rust compilado. IPC tipado con invoke<T>(). CSP estricto obligatorio. Compatibilidad con Android/iOS usando el mismo código base.

## ADR-014: Seguridad en Tauri - CSP + permisos mínimos + path validation

- **Fecha**: 2026-07-08
- **Estado**: Aceptada
- **Contexto**: Tauri expone APIs del sistema operativo. Sin una configuración cuidadosa, se pueden introducir vulnerabilidades.
- **Decisión**: Aplicar defensa en profundidad: CSP sin unsafe-eval/unsafe-inline en producción, capabilities con permisos mínimos, validación de paths en Rust contra path traversal, wrappers tipados para invoke(), sin `window.__TAURI__` directo.
- **Alternativas consideradas**: Confiar en defaults de Tauri (descartado: permisos demasiado abiertos en algunas versiones).
- **Consecuencias**: Cada nuevo permiso (filesystem, shell, etc.) debe añadirse explícitamente en `capabilities/default.json`. Los comandos Rust deben validar inputs.

## ADR-015: Rust testing y linting con Clippy + cargo test

- **Fecha**: 2026-07-08
- **Estado**: Aceptada
- **Contexto**: El backend Rust necesita su propia suite de testing y linting, separada del frontend.
- **Decisión**: Usar `cargo test` para tests unitarios y de integración, `cargo clippy` con `-D warnings` para linting estricto, `rustfmt` para formateo, `cargo audit` para vulnerabilidades.
- **Alternativas consideradas**: Solo tests en frontend (descartado: no cubre la lógica de Rust).
- **Consecuencias**: El pre-commit hook ejecuta toda la suite: ESLint + Clippy + rustfmt + Vitest + cargo test + cargo audit.

## ADR-016: Filosofía visual "Telemetry & Freedom" - Modo oscuro técnico obligatorio

- **Fecha**: 2026-07-08
- **Estado**: Aceptada
- **Contexto**: La app se usa montada en el manillar de una motocicleta, con luz solar directa y vibraciones. Se necesita máxima legibilidad y mínimo deslumbramiento.
- **Decisión**: Modo oscuro técnico obligatorio sin variante clara. Paleta de colores basada en fondo #0b0c10, acentos neón (verde #00ff66, rojo #ff3131, azul #00d2ff). Hitboxes mínimas de 56×56px para guantes.
- **Alternativas consideradas**: Modo claro/oscuro toggle (descartado: riesgo de deslumbramiento nocturno, complejidad extra).
- **Consecuencias**: Todos los componentes deben usar los tokens CSS definidos en `src/shared/styles/tokens.css`. Prohibido hardcodear colores.
- **Superseded by**: [[ADR-019]] — la paleta neón "Telemetry & Freedom" fue reemplazada por "Asfalto Nocturno". El principio de fondo (modo oscuro obligatorio, hitbox 56×56px, tokens obligatorios) se mantiene; solo cambia la paleta/tipografía concreta.

## ADR-017: Adaptación a mobile (Android/iOS) con Tauri 2

- **Fecha**: 2026-07-08
- **Estado**: Aceptada
- **Contexto**: El proyecto se concibe como app móvil, aunque la plantilla original tauri-vanilla-ts está orientada a desktop.
- **Decisión**: Usar Tauri 2 con su soporte nativo para Android e iOS. Configuración de ventana adaptada a dimensiones móviles (400×800, min 360×640). Los iconos y bundle se generarán con `tauri icon` y `tauri build`.
- **Alternativas consideradas**: Usar Capacitor (descartado: no ofrece backend nativo Rust), mantener solo desktop (descartado: el usuario pide explícitamente mobile).
- **Consecuencias**: Para compilar para Android se necesita Android SDK + NDK. Para iOS se necesita Xcode + macOS. El comando `npm run tauri:android` inicia en dispositivo/emulador Android.

## ADR-018: Target Android como prioridad

- **Fecha**: 2026-07-08
- **Estado**: Aceptada
- **Contexto**: El usuario quiere compilar para Android de momento. iOS queda para más adelante.

## ADR-019: Reemplazo de filosofía visual — "Asfalto Nocturno" sustituye a "Telemetry & Freedom"

- **Fecha**: 2026-07-11
- **Estado**: Aceptada
- **Contexto**: El usuario entregó un paquete de diseño completo (`moto-routes-design/`: screens de referencia, `DESIGN_PHILOSOPHY.md`, `STYLE_GUIDE.html`, `css/global.css`) que redefine la identidad visual de la app. La filosofía anterior ([[ADR-016]], "Telemetry & Freedom": dial circular, negro puro, acentos neón verde/rojo/azul, Segoe UI) queda sustituida por "Asfalto Nocturno": cuero oscuro cálido, ámbar como único acento vivo, óxido de apoyo, tipografía de señalética (Roboto Slab + Barlow + Barlow Semi Condensed tabular). El único componente construido en `src/` era el cockpit (grabación de ruta), correspondiente a `moto-routes-design/screens/grabacion-ruta.html`.
- **Decisión**: Renombrar `src/shared/styles/tokens.css` a la nomenclatura del paquete de diseño (`--bg-top`, `--panel`, `--amber`, `--ink`, `--font-display/ui/data`, etc.) en vez de mantener los nombres antiguos con valores nuevos — evita que un token como `--color-neon-go` pase a significar "ámbar", que sería confuso. Auto-alojar un subset `.woff2` de las 3 familias tipográficas en `src/assets/fonts/` (Roboto Slab 600, Barlow 400/500/600/700, Barlow Semi Condensed 700/800) en vez de depender de Google Fonts vía CDN, porque la app es Tauri offline con CSP `font-src 'self'`. Reescribir `src/cockpit/cockpit.element.ts`/`.css` con el nuevo lenguaje visual, preservando toda la lógica funcional existente (long-press de 1.5s para finalizar, pausa/reanudar, modo invisible, overlay de permiso GPS) que no tiene equivalente en los mockups estáticos. No se implementan las pantallas de listado/detalle de ruta ni la botonera inferior (`bottom-nav`) — no existe routing ni más pantallas montadas todavía; quedan documentadas en `specs/ui/design-system.md` como pendientes.
- **Alternativas consideradas**: Mantener "Telemetry & Freedom" y tratar la entrega de diseño como opcional/futura (descartada: el usuario pidió explícitamente sustituir el cockpit por el nuevo sistema). Mantener los nombres de token antiguos con los valores nuevos (descartada: desalinea nombre y significado, dificulta el mantenimiento — ver discusión en la sesión).
- **Consecuencias**: Todo trabajo de UI futuro (listado de rutas, detalle de ruta, garaje, etc.) debe partir de los tokens y componentes documentados en `specs/ui/design-system.md` v2, no de los tokens `--color-*`/`--glow-*` antiguos (eliminados). Cualquier regla de estilo pensada como "global" debe vivir en `tokens.css`, no en `src/index.css` — un Shadow DOM nunca hereda selectores de una hoja de estilos del documento ligero, solo lo que llega vía `@import` dentro del propio `*.element.css` del componente. Los componentes de UI (`.chip`, `.stat-tile`, `.control-btn`, etc.) permanecen en `cockpit.element.css` hasta que una segunda pantalla los reutilice, momento en el que se promueven a `src/shared/` (regla ya existente en `specs/ui/frontend-conventions.md`).

## ADR-020: Persistencia real de fotos de ruta en Android — plugin-fs real, lectura vía readFile (no convertFileSrc), ruta insertada como 'active' antes de grabar

- **Fecha**: 2026-07-20
- **Estado**: Aceptada
- **Contexto**: Las fotos de ruta (feature `fotos-ruta`, ver [[fotos-ruta]]) parecían subir sin error pero no se veían ni persistían de verdad en Android. Investigación en varias rondas reveló tres bugs independientes y acumulativos:
  1. `@tauri-apps/plugin-fs` nunca fue una dependencia real: `vite.config.ts` aliaba `@tauri-apps/plugin-fs` y `@tauri-apps/api/path` a stubs no-op de `src/__mocks__/` **incondicionalmente**, incluso en el build real de Android (`beforeBuildCommand` usa el mismo `vite.config.ts`). El plugin tampoco estaba registrado en `src-tauri/src/lib.rs`. Resultado: `writeFile()` "tenía éxito" sin escribir nada, sin lanzar excepción — de ahí "sube sin error pero no se guarda".
  2. Una vez arreglado (1), las fotos SÍ se escribían en `appDataDir` (confirmado con `adb run-as ... ls photos/`), pero se veían rotas al leerlas: `getPhotoUrl()` usaba `convertFileSrc()` + el protocolo `asset://`/`https://asset.localhost`. Pese a tener `assetProtocol.scope` y CSP correctos, el WebView de Android no servía el fichero de forma fiable.
  3. Las fotos capturadas **durante grabación activa** (antes de parar/guardar la ruta) violaban `FOREIGN KEY (route_id) REFERENCES routes(id)` de la tabla `photos`, porque la fila de `routes` no se inserta hasta `stopRecording()`.
- **Decisión**:
  1. Instalar `@tauri-apps/plugin-fs` como dependencia real (`pnpm add`), registrar `tauri_plugin_fs::init()` en `lib.rs`, añadir el feature `protocol-asset` a `tauri` en `Cargo.toml`, y permisos `fs:allow-*` escopados a `$APPDATA/photos/**` en `capabilities/default.json`. Quitar los alias de `vite.config.ts`/`tsconfig.json` — ya no hacen falta mocks para un paquete real.
  2. `getPhotoUrl()` (en `photo-storage.service.ts`) lee los bytes con `plugin-fs.readFile()` y construye un `blob:` URL en JS (`URL.createObjectURL(new Blob([...]))`) en vez de usar `convertFileSrc()`. Evita depender del protocolo de assets, que resultó frágil en este dispositivo Android pese a la configuración correcta.
  3. `CockpitState.routeId` se pre-genera al iniciar la grabación (no al guardar). `IRouteRepository.save()` es ahora un **upsert por id** (`route.id` opcional en `CreateRoute`; si ya existe, hace `UPDATE` en vez de `INSERT`, y los puntos/paradas se van añadiendo en sucesivas llamadas). `startRecordingAction()` inserta inmediatamente una fila `routes` con `status:'active'` y duración/distancia en 0; `stopRecordingAction()` la actualiza a `status:'completed'` con los datos finales. Así cualquier foto capturada en pleno directo siempre tiene una fila padre a la que referenciar.
- **Alternativas consideradas**: Quitar la `FOREIGN KEY` de la tabla `photos` (descartada: pierde el `ON DELETE CASCADE` al borrar una ruta, y además `CREATE TABLE IF NOT EXISTS` no migra instalaciones existentes — el dispositivo de pruebas ya tenía la tabla vieja creada). Guardar las fotos capturadas en pleno directo en un buffer aparte hasta que la ruta se guarde (descartada: más compleja, y arriesga perder fotos si la app se cierra antes de parar la grabación).
- **Consecuencias**: Cualquier flujo futuro que cree filas relacionadas con una ruta antes de que esta "termine" (fotos, y en el futuro quizá paradas en tiempo real) debe apoyarse en este patrón insertar-activa/actualizar-al-parar, no asumir que la ruta solo existe en BBDD al guardarse. Los rechazos de `invoke()` de Tauri no son instancias de `Error` de JS (suelen ser strings/objetos planos) — usar `toErrorMessage()` (`src/shared/utils/errors.ts`) en vez de `err instanceof Error ? err.message : fallback`, que se comió el mensaje real del primer intento de diagnóstico en esta misma sesión.

## ADR-021: Cierre de `fotos-ruta` — quality gates rotos sin detectar, gate de cobertura alineado a 80%, adopción de Claude Code en paralelo a Cline

- **Fecha**: 2026-07-22
- **Estado**: Aceptada
- **Contexto**: Al cerrar la ronda de trabajo de `fotos-ruta` (ver [[fotos-ruta]]) se pidió comprobar ESLint, tests y el gate de cobertura antes de abrir PR. Al ejecutar `pnpm lint` aparecieron ~24 "fatal parsing error" — `tsconfig.json` excluía `**/*.spec.ts`, y el `projectService` de `typescript-eslint` no puede tipar un fichero que no pertenece a ningún proyecto TS. Al arreglarlo y limpiar los warnings reales que salieron a la luz, se comprobó el lado Rust: `clippy.toml` tenía una clave `max_fn_params` que no existe en la versión de Clippy instalada (rompía la compilación antes de llegar a lintar nada), y además `cargo build`/`clippy`/`test` fallaban por separado porque `src-tauri/icons/icon.ico` (y el resto de iconos del bundle desktop) eran placeholders de 22-70 bytes que el compilador de recursos de Windows (RC.EXE) rechazaba. Ninguno de los tres bugs se había detectado antes porque el pre-commit hook (`.husky/pre-commit`) solo ejecutaba ESLint + Vitest, pese a que la documentación (ADR-015, `docs/06-seguridad.md`) siempre dijo que cubría también Rust.
- **Decisión**:
  1. `tsconfig.json`: se quita `**/*.spec.ts` de `exclude` (los specs SÍ se tipan ahora). No hay riesgo de contaminar `dist/` porque `vite build` sobrescribe por completo lo que `tsc` haya emitido antes.
  2. `eslint.config.js`: se ignoran `**/*.d.ts` (declaraciones ambient sin código ejecutable, rompían el `projectService` igual que los specs) y se añade un override para `**/*.spec.ts` desactivando `max-lines`, `max-lines-per-function` y `@typescript-eslint/unbound-method` — ruido esperado en tests (`describe` con muchos `it()`, `expect(obj.method)`), no señal de complejidad real.
  3. `clippy.toml`: se elimina la clave inválida `max_fn_params` (ya existía la equivalente correcta `too-many-arguments-threshold`).
  4. `src-tauri/icons/*`: regenerados con `pnpm tauri icon <fuente>` a partir de un icono Android real ya existente en el repo (`gen/android/.../mipmap-xxxhdpi/ic_launcher.png`). Se revirtieron explícitamente los iconos de `gen/android/` que ese mismo comando también sobreescribió — esos ya estaban verificados en dispositivo y no hacía falta (ni convenía, por posible pérdida de calidad) regenerarlos.
  5. `vitest.config.ts`: se excluyen del coverage los contratos puros sin código ejecutable (`route.types.ts`, `photo.types.ts`, `route.repository.ts`, `photo.repository.ts`, `shared/models/index.ts`, `**/*.d.ts`) — mismo criterio que ya existía para `cockpit.types.ts`. El umbral de cobertura sube de 70% (valor "provisional" de ADR previo, nunca vuelto a subir) a 80%, el que ya documentaba `memory/context.md` como objetivo. Cobertura real tras limpiar exclusiones y añadir tests a `toast.ts`/`route-detail-photo.service.ts`/`route-map-photos.ts` (antes 6-12% cada uno): 85.71%.
  6. `.husky/pre-commit`: se añaden `cargo fmt --check`, `cargo clippy -- -D warnings` y `cargo test`, alineando el hook real con lo que ADR-015 siempre dijo que hacía.
  7. Se crea `CLAUDE.md` (raíz) + `.claude/agents/*.md` + `.claude/commands/*.md` como equivalente nativo de Claude Code al setup de `.clinerules` + `agents/*.md` que ya existía para Cline+DeepSeek. Ambos coexisten: mismo SDD, misma `specs/`, misma `memory/` — solo cambia qué asistente los consume y cómo se invocan (subagentes/slash commands nativos en vez de `@agent:nombre` en el prompt).
- **Alternativas consideradas**: Usar `--no-verify` para saltarse el pre-commit roto en vez de arreglarlo (descartada: es exactamente el antipatrón que llevó a que estos tres bugs pasaran desapercibidos — el repo ya tenía el permiso `git commit --no-verify` usado en sesiones anteriores). Dejar el gate de cobertura en 70% para no arriesgar (descartada: la cobertura real ya superaba el 80% documentado una vez arregladas las exclusiones; mantenerlo en 70% habría dejado el número de `memory/context.md` desalineado del `vitest.config.ts` real, que es justo el tipo de deriva que este cierre pretendía evitar).
- **Consecuencias**: `pnpm lint`, `pnpm test:coverage`, `pnpm rust:lint`, `pnpm rust:format` y `pnpm rust:test` pasan limpios y ahora si alguno se rompe, el pre-commit lo va a atrapar de verdad. Cualquier fichero de test nuevo debe seguir dentro de `src/` (ya lo estaba) para quedar cubierto por `tsconfig.json`; cualquier tipo/interfaz puramente declarativo nuevo bajo `shared/models/` debe añadirse también a la lista de exclusión de `vitest.config.ts` si no tiene código ejecutable, o el coverage lo contará como "0%" y arrastrará la media hacia abajo de forma engañosa. Quedan 5 issues documentados en `specs/features/fotos-ruta.review.md` (popup de marcador, desagrupación de cluster al zoom, swipe en el visor, test de EXIF con GPS real, y la desviación de AC-007 centroide-vs-último-punto) para una iteración siguiente.

## ADR-022: Refactor `mejoras-tecnicas` — BaseElement unificado, eventos centralizados, servicio de foto deduplicado

- **Fecha**: 2026-07-22
- **Estado**: Aceptada
- **Contexto**: Tras cerrar `fotos-ruta`, se decidió una ronda de mejoras dividida en dos specs: una técnica (refactor sin cambio de comportamiento) y otra de usabilidad. Ver [[mejoras-tecnicas]]. La técnica debía ir primero porque la de usabilidad necesitaría un módulo de feedback y una galería compartida, y convenía que la base (clase base, tokens, helper de DOM) ya estuviera unificada.
- **Decisión**: Los 9 custom elements pasan a extender `BaseElement` (antes 5 extendían `HTMLElement` directamente), que gana un helper `renderShadow(styles, ...nodes)` para no repetir el patrón `<style>+innerHTML=''+append`. Se centralizan los eventos de navegación en `shared/app-events.ts` (constantes + `dispatchAppEvent` tipado). Se elimina `shared/utils/dom.ts` (código muerto). Se deduplica la lógica de captura de foto (`validar→geolocalizar→guardar→persistir`, antes casi idéntica en cockpit y detalle) en `shared/services/photo-persist.service.ts`. Se saca el CSS inline a hojas de estilo con tokens (nueva `shared/styles/overlays.css` para overlays en `document.body`).
- **Alternativas consideradas**: Hacer la de usabilidad primero y refactorizar sobre la marcha (descartada: mezclar refactor con features nuevas dificulta revisar cuál cambio es cuál).
- **Consecuencias**: Cualquier componente nuevo debe extender `BaseElement` y usar `renderShadow`. Cualquier evento de navegación nuevo se añade a `app-events.ts`, nunca como string suelto. El pipeline de foto compartido (`photo-persist.service.ts`) es la única vía de "validar+geolocalizar+guardar+persistir" — los flujos específicos (cockpit, detalle) solo aportan la estrategia de fallback de ubicación y cómo notifican el resultado. Verificado visualmente (Cypress + screenshots) en cockpit y listado, no solo con tests unitarios.

## ADR-023: `mejoras-usabilidad` — flujo de parada en dos fases, y el borrado de rutas nunca había cascadeado de verdad

- **Fecha**: 2026-07-22
- **Estado**: Aceptada
- **Contexto**: Ver [[mejoras-usabilidad]]. Al implementar el borrado de rutas (AC-008) y el descarte al parar (AC-005) — ambas, primera vez que `IRouteRepository.delete()`/`IPhotoRepository.delete()` se llaman desde la UI real, no solo desde tests de contrato — se descubrió que el `ON DELETE CASCADE` del esquema SQLite (`route_points`/`route_stops`/`photos` → `routes`) era inerte: SQLite tiene `foreign_keys` en `OFF` por defecto (es una pragma **por conexión**, no por fichero) y la app nunca lo activaba. En producción (Android), borrar una ruta habría dejado huérfanos sus puntos/paradas/fotos.
- **Decisión**:
  1. Se activa `PRAGMA foreign_keys = ON;` en `ensureSchema()` de `SqliteRouteRepository` y `SqlitePhotoRepository` (defensa en profundidad: cualquiera de las dos conexiones podría ejecutar el DELETE).
  2. Se crea `shared/services/route-deletion.service.ts` (`deleteRouteAndPhotos`) que **no confía solo en el cascade SQL**: borra explícitamente cada foto (archivo vía `deletePhotoFile` + fila) antes de borrar la ruta. Necesario además porque `MemoryRouteRepository`/`MemoryPhotoRepository` (navegador/tests) son dos stores completamente independientes que no cascadan nada entre sí.
  3. El long-press de parar ya no hace "stop = persistir + resetear" en un solo paso. `CockpitService.stopRecording()` se sustituye por `prepareStop()` (congela tick/GPS, sin tocar BBDD ni resetear) + `confirmSaveRecording()` (persiste como completed y resetea) + `discardStop()` (solo resetea — el borrado real lo hace el llamador con `deleteRouteAndPhotos` antes de llamarlo). Esto permite mostrar el diálogo "¿Guardar la ruta?" con los datos finales congelados antes de decidir.
  4. El diálogo de guardar/descartar se implementa con `closable: false` en `<confirm-dialog>` — parar una ruta obliga a decidir, nunca deja el estado indeterminado.
- **Alternativas consideradas**: No arreglar el pragma y confiar solo en el borrado explícito en código (descartada: `route_points`/`route_stops` sí dependen únicamente del cascade SQL, `deleteRouteAndPhotos` no los toca directamente). Mantener `stopRecording()` como un único paso y mostrar el diálogo *después* de persistir con opción de deshacer (descartada: más complejo, y persistir-luego-quizá-deshacer es más propenso a estados intermedios raros que congelar-decidir-aplicar).
- **Consecuencias**: Cualquier borrado futuro de una ruta debe pasar por `deleteRouteAndPhotos`, nunca por `routeRepo.delete()` a pelo (se perdería la limpieza de fotos en el backend Memory). El API de `CockpitService` para parar es ahora de tres pasos (`prepareStop`→`confirmSaveRecording`|`discardStop`), no uno — cualquier otro llamador futuro del flujo de parada debe seguir esa secuencia, no puede saltarse `prepareStop()`. Pendiente verificar en dispositivo Android real que el pragma cascada de verdad `route_points`/`route_stops` (los tests usan un mock de `SqlDb` en JS, no SQLite real — ver ISSUE-001 de `specs/features/mejoras-usabilidad.review.md`).

## ADR-025: `mejoras-guardado-rutas` — diálogo propio `cockpit-save-route-dialog` en vez de ampliar `<confirm-dialog>`

- **Fecha**: 2026-07-27
- **Estado**: Aceptada
- **Contexto**: Ver [[mejoras-guardado-rutas]]. AC-001 a AC-009 piden que el diálogo "¿Guardar la ruta?" (mostrado tras el long-press de parada, `resolveStopDecision` en `cockpit-stop.service.ts`) incluya un campo de texto para el nombre de la ruta. El componente compartido `<confirm-dialog>` (`src/shared/feedback/confirm-dialog.element.ts`) no soporta hoy un input embebido en `ConfirmDialogOptions`, y lo usan 3 consumidores más (`route-list.element.ts`, `photo-delete.service.ts`, y el propio flujo de parada) con un contrato `Promise<string | null>` cubierto por 8+ tests, marcado como "CRÍTICO en review" en `mejoras-usabilidad.md`.
- **Decisión**: Se crea `cockpit-save-route-dialog` en `src/cockpit/` (único consumidor: el dominio de grabación) en vez de ampliar `ConfirmDialogOptions`/`confirmDialog()` para devolver también un valor de texto. El nuevo diálogo replica deliberadamente (no extrae a `shared/`) el patrón visual (`.overlay`/`.dialog`/`.actions`/`.action*`, tokens de `tokens.css`) y de foco (`trapFocus`, `closable: false` fijo — parar una ruta obliga a decidir, igual que hoy) de `confirm-dialog.element.ts`, añadiendo un bloque `.field`/`.input` para el nombre. Expone `openSaveRouteDialog({ message }): Promise<{ action: 'save' | 'discard'; name: string }>`, con título y acciones fijos (no configurables, a diferencia de `confirmDialog()`).
- **Alternativas consideradas**: Ampliar `ConfirmDialogOptions` con un campo `input?: { placeholder, maxLength }` y cambiar `confirmDialog()` para resolver `{ action: string | null; value: string }` en vez de `string | null` (descartada: obliga a tocar los 3 consumidores existentes y su suite de tests por un caso de uso que solo necesita uno de ellos; además mezclaría en un componente "confirmar sí/no genérico" un caso de uso mucho más específico). Esperar a que aparezca un segundo diálogo con el mismo patrón "confirmar + campo de texto" antes de decidir si extraer un `focus-trap.ts` compartido (aplazada, no descartada — ver Notas de Implementación del plan: hoy solo lo usa `cockpit`, prematuro promoverlo a `shared/` con un único consumidor).
- **Consecuencias**: Hay duplicación deliberada del fragmento de focus-trap/overlay/dialog entre `confirm-dialog.element.ts` y `cockpit-save-route-dialog.element.ts` — cualquier cambio futuro en el patrón de foco/accesibilidad de uno debe revisarse también en el otro hasta que, si aparece un tercer caso, se justifique extraer un helper común a `shared/feedback/` o `shared/`. `<confirm-dialog>` no cambia su contrato en absoluto — los 3 consumidores existentes y sus tests quedan intactos.

## ADR-026: `deuda-tecnica-auditoria` AC-007 — token `--amber-glow` para el resplandor ámbar puntual, no contradice ADR-019

- **Fecha**: 2026-07-28
- **Estado**: Aceptada
- **Contexto**: Ver [[deuda-tecnica-auditoria]]. La auditoría técnica encontró 6 literales `oklch(...)` hardcodeados (5 en `cockpit.element.css`, 1 en `nav-bar.element.css`) sobrevivientes de antes de ADR-019 ("Asfalto Nocturno" sustituye a "Telemetry & Freedom", que prohíbe explícitamente "neón/glow" como lenguaje visual difuso). Estos literales no compartían el mismo valor exacto (variaban entre `oklch(60% 0.17 45 / 0.4)`, `oklch(70% 0.17 45 / 0.8)`, `oklch(70% 0.17 45 / 0.35)` y `oklch(60% 0.17 45 / 0.45)` ×2), así que un único token no puede reproducir bit a bit las 4 combinaciones de lightness/alpha sin sintaxis de color relativo (`oklch(from var(...) ...)`).
- **Decisión**: Se crea el token `--amber-glow: oklch(60% 0.17 45 / 0.45)` en `tokens.css`, derivado de la misma familia OKLCH que ya usa `--amber` (hue ~45-48, chroma 0.17) — no una segunda fuente de verdad de color. Los 6 sitios pasan a consumir `var(--amber-glow)`. Se acepta una variación menor de intensidad en 4 de los 6 sitios respecto al literal original (más marcada en `.chip__dot` de `chip-recording`, que pasa de alpha 0.8 a 0.45), priorizando una única fuente de verdad sobre la reproducción exacta de cada matiz. El resplandor ámbar puntual en elementos de estado activo (dial en grabación, chip "En ruta", botones de control, marcador del nav-bar) no contradice la prohibición general de "neón/glow" de ADR-019 al quedar acotado a un único token con significado semántico claro (estado activo/grabando), no a un lenguaje visual difuso aplicado sin criterio.
- **Alternativas consideradas**: Sintaxis de color relativo `oklch(from var(--amber) l c h / <alpha>)` para preservar cada alpha exacto por sitio — descartada por riesgo de soporte no verificado en el WebView de Android (target prioritario del proyecto, ver ADR-018). Eliminar el resplandor por completo — descartada porque el usuario confirmó explícitamente mantener el efecto visual (2026-07-28, ver AC-007 de la spec).
- **Consecuencias**: Cualquier resplandor ámbar futuro (nuevo estado activo, nuevo componente) reutiliza `--amber-glow`, nunca introduce un literal `oklch(...)` nuevo. `cockpit.element.css` y `nav-bar.element.css` quedan sin ningún literal de color hardcodeado.

## ADR-024: AC-007 de `fotos-ruta` — se confirma el centroide de la ruta como fallback de ubicación, no "la última ubicación conocida"

- **Fecha**: 2026-07-26
- **Estado**: Aceptada
- **Contexto**: El review de `fotos-ruta` ([[fotos-ruta-review]], ISSUE-005) dejó anotado que AC-007 pedía literalmente "la última ubicación GPS conocida de la ruta" para fotos sin EXIF añadidas fuera de una grabación activa, pero `extractPhotoLocation()`/`route-detail-photo.service.ts` ya implementaban (y AC-013, ya aprobada y testeada, ya documentaba) el centroide — promedio de lat/lon de **todos** los puntos de la ruta — como ese fallback. Era una desviación de diseño nunca registrada formalmente como ADR, solo anotada como nota al margen en la spec.
- **Decisión**: Se confirma el centroide como el comportamiento definitivo (no se toca el código). AC-007 se reescribe en `specs/features/fotos-ruta.md` para decir "se usa el centroide de la ruta" en vez de "la última ubicación conocida", alineándola con AC-013 en vez de contradecirla.
- **Alternativas consideradas**: Cambiar la implementación para usar el último punto de `routePoints` en vez del centroide (descartada: el centroide es más representativo/estable para una ruta ya completada — no depende de en qué extremo de la ruta "termina" cronológicamente el array de puntos, y para rutas circulares o con vuelta atrás el último punto puede estar arbitrariamente lejos de donde de verdad se tomó la foto sin GPS propio).
- **Consecuencias**: `route-detail-photo.service.ts`/`extractPhotoLocation()` no cambian. Cualquier persona que lea AC-007 y AC-013 en `fotos-ruta.md` las verá coherentes entre sí, sin desviación implícita sin explicar.

## ADR-027: Elección de framework SDD — evaluación de GitHub Spec Kit, OpenSpec y BMAD frente al SDD propio

- **Fecha**: 2026-07-30 (ratificada 2026-08-01)
- **Estado**: Aceptada — framework elegido: **OpenSpec**
- **Contexto**: Hasta hoy el proyecto usa un **SDD propio, hecho a medida** (documentado en `docs/01`–`07`, `CLAUDE.md`, `.clinerules`, `agents/` y `.claude/`), no un framework externo. Nació para **DeepSeek + Cline** y desde [[ADR-021]] se sirve además a **Claude Code** sobre el mismo `specs/` + `memory/`. Funciona (6 fases: Spec→Plan→Tasks→Impl→Review→Test, TDD estricto, quality gates en pre-commit, memoria persistente), pero todo su mantenimiento recae en el equipo: cada mejora del flujo la escribimos y sostenemos nosotros, sin comunidad ni actualizaciones externas. En 2026 el ecosistema SDD ha madurado mucho (30+ frameworks catalogados). Antes de seguir invirtiendo en el flujo propio conviene decidir formalmente si adoptamos un estándar mantenido por una comunidad o seguimos con el nuestro. Esta ADR evalúa los **tres frameworks SDD más consolidados** del momento (Spec Kit, OpenSpec, BMAD) junto al SDD propio, para elegir uno y descartar el resto.

- **Criterios de decisión (específicos de este proyecto, no genéricos)**:
  1. **Multi-agente / CLI-agnóstico** — imprescindible: debe servir *a la vez* a Cline+DeepSeek y a Claude Code desde una única fuente de specs (es justo lo que [[ADR-021]] montó). Este es el criterio eliminatorio.
  2. **Coste en tokens** — DeepSeek tiene ventana de 128K y el proyecto es explícitamente *token-aware* (ver `docs/04-token-management.md`). Un flujo caro en tokens es un mal encaje.
  3. **Brownfield** — el repo ya tiene 14 ADRs y ~10 features cerradas; el framework debe encajar en un proyecto en marcha, no asumir greenfield.
  4. **Ceremonia proporcionada** — equipo muy pequeño (prácticamente solo); nada de procesos de "equipo simulado" pesados.
  5. **Coste de migración** vs. lo ya invertido en el flujo propio.
  6. **Gates de calidad integrados** (review obligatorio, TDD, cobertura) — el proyecto ya los exige y no quiere perderlos.

- **Opciones evaluadas**:
  - **A — GitHub Spec Kit** (github/spec-kit). CLI en Python. Flujo de 4 fases: **Specify → Plan → Tasks → Implement**. Concepto central de *"constitution"*: un fichero de principios no negociables que heredan todas las specs (equivalente conceptual a nuestro `CLAUDE.md`). Soporta 30+ agentes (Claude Code, Copilot, Gemini CLI…). El más adoptado con diferencia (**124.657** en GitHub, a 30-jul-2026). *Contras*: setup opinado y front-loaded; los cambios upstream rompen scripts antiguos; requiere disciplina de "constitution".
  - **B — OpenSpec** (Fission-AI/OpenSpec). Ligero y **CLI-agnóstico** (funciona incluso con agentes sin soporte nativo, vía `AGENTS.md`). Flujo de cambios: **Propose → Apply → Archive**, con **delta specs** (ADDED/MODIFIED/REMOVED en estilo EARS) que documentan solo lo que cambia; al archivar, los deltas se funden en la spec viva. Separa `openspec/specs/` (verdad actual) de `openspec/changes/` (propuestas). Pensado para **brownfield** y velocidad, baja ceremonia (**63.215**). *Contras*: poco andamiaje de handoff entre roles; **sin gates de review/compliance por defecto**.
  - **C — BMAD-METHOD** (bmad-code-org). Orquesta 12+ agentes como un **equipo ágil simulado**: Analyst → PM → Architect → Dev → QA, produciendo PRD, arquitectura, epics y stories como artefactos versionados (sirven de evidencia de auditoría). Multi-IDE (Claude Code, Cursor, Copilot, Windsurf), MIT (**51.303**). *Contras*: **la opción más cara en tokens (~$800–2.000+/dev/mes según terceros)**, setup pesado, lento en tareas pequeñas, fricción en legacy. Orientado a plataformas greenfield complejas y entornos regulados.
  - **D — SDD propio (statu quo)**. Ya integrado, dual-tool, con review obligatorio + TDD + gates en Husky + memoria persistente. *Contras*: 100% auto-mantenido, sin comunidad ni evolución externa; reinventa lo que ya existe estandarizado.

  | Framework | ★ GitHub (30-jul-2026) | Enfoque | Multi-agente (Cline+CC) | Tokens | Ceremonia | Brownfield | Gates review/TDD | Veredicto |
  |-----------|--:|---------|:---:|:---:|:---:|:---:|:---:|-----------|
  | Spec Kit | 124.657 | Constitution + 4 fases | Parcial (agentes soportados) | Media | Alta (front-loaded) | Media | No nativos | Descartado |
  | **OpenSpec** | 63.215 | **Delta specs, propose/apply/archive** | **Sí (agnóstico)** | **Bajo** | **Baja** | **Alta** | No (se conservan los nuestros) | **Recomendado** |
  | BMAD | 51.303 | Equipo ágil simulado | Sí | **Muy alto** | Muy alta | Baja | Sí (QA agent) | Descartado |
  | SDD propio | N/A (repo privado) | 6 fases a medida | Sí | Medio | Media | Alta | Sí | Base a sustituir/absorber |

- **Decisión (recomendación de esta propuesta)**: **Adoptar OpenSpec como framework SDD**, y **conservar por encima los quality gates propios** (review-agent obligatorio con sección CRÍTICO, TDD RED-GREEN-REFACTOR y el pre-commit de Husky con cobertura ≥80%). Es decir: OpenSpec aporta la **estructura de specs y el flujo de cambios** (delta specs, propose→apply→archive, spec viva que crece al archivar); nuestro flujo aporta los **gates de calidad** que OpenSpec no trae de fábrica. Racional:
  1. **Criterio eliminatorio (multi-agente/agnóstico)**: OpenSpec es explícitamente CLI-agnóstico y funciona con agentes sin soporte nativo — el mejor encaje para servir *a la vez* a Cline+DeepSeek y a Claude Code, que es la premisa de [[ADR-021]]. Spec Kit depende de que el agente esté entre los soportados; BMAD también, con mucho más peso.
  2. **Tokens**: OpenSpec es el más ligero; BMAD es directamente incompatible con la restricción de token-awareness del proyecto (DeepSeek 128K).
  3. **Brownfield + delta specs**: encaja con un repo ya en marcha; el modelo de deltas es casi idéntico en espíritu a cómo ya trabajamos feature a feature con `<feature>.md`/`.plan.md`/`.review.md`.
  4. **Ceremonia proporcionada** al tamaño del equipo; migración incremental (se puede convivir con el flujo propio durante la transición).

- **Alternativas consideradas (y por qué se descartan)**:
  - **BMAD — descartado.** Su modelo de "equipo ágil simulado" y su coste en tokens (el más alto del mercado) están dimensionados para plataformas complejas, equipos grandes y entornos regulados. Para una app móvil Tauri llevada por (prácticamente) una persona y consciente del gasto de tokens, es sobreingeniería que además choca de frente con el criterio 2.
  - **GitHub Spec Kit — descartado (pese a ser el más popular).** Su *constitution* + setup opinado y front-loaded aportan poco sobre lo que ya nos da `CLAUDE.md`, y su soporte multi-agente es "por agente soportado" en vez de agnóstico, peor encaje para la mitad Cline+DeepSeek. Sumado a que los cambios upstream rompen scripts antiguos, el coste de adopción no compensa frente a OpenSpec para *este* proyecto. (Popularidad ≠ mejor encaje aquí.)
  - **Mantener el SDD propio sin cambios — descartado como recomendación principal, pero es el fallback seguro.** Funciona, pero nos deja manteniendo en solitario un flujo que la comunidad ya ha estandarizado mejor. Si la evaluación práctica (spike) revelara que la migración a OpenSpec cuesta más de lo que ahorra, esta es la opción a la que se revierte sin drama.

- **Consecuencias**:
  - Si se ratifica: se hará un **spike acotado** migrando **una** feature al modelo OpenSpec (`openspec/specs/` + `openspec/changes/` con delta specs) antes de mover el resto, para medir coste real de migración y encaje con Cline+DeepSeek y Claude Code. Solo tras un spike verde se migra el resto y se actualizan `CLAUDE.md`/`.clinerules`/`docs/` para reflejar el nuevo flujo.
  - `memory/` y los quality gates de Husky **se conservan** — OpenSpec no los sustituye.
  - Los `.claude/agents/` y `agents/` propios se **realinean** al flujo OpenSpec en vez de eliminarse (el review-agent y el impl-agent TDD siguen siendo nuestros; cambian los artefactos de spec sobre los que operan).
  - Esta ADR queda en `Propuesta`: **no se toca código ni estructura de `specs/` hasta que el equipo la apruebe** (regla de `CLAUDE.md`: no modificar `specs/` sin petición explícita).

- **Ratificación (2026-08-01)**: el usuario confirma explícitamente adoptar OpenSpec. Investigación adicional en el momento de ratificar (README + `docs/cli.md` + `docs/existing-projects.md` de `Fission-AI/OpenSpec`, vía `gh api`) confirma dos cosas que ajustan el plan original:
  1. **La CLI real es `@fission-ai/openspec`** (no el paquete `openspec` de npm, un placeholder de 2019 sin relación con el proyecto — cuidado al instalar). El flujo se invoca como `/opsx:propose` → `/opsx:apply` → `/opsx:archive`, con `openspec/config.yaml` como configuración del proyecto — sigue encajando con el modelo "Propose → Apply → Archive, delta specs" ya descrito arriba.
  2. **Se redefine el alcance del spike**: la guía oficial de adopción brownfield de OpenSpec dice explícitamente *"You do not document your whole codebase to start. You write specs only for what you're about to change"* — desaconseja migrar specs cerradas como ejercicio de prueba, que era justo lo que este ADR proponía como spike inicial. En vez de migrar retroactivamente una feature ya cerrada, la ratificación de 2026-08-01 se limita a **instalar y verificar el tooling** (`openspec init` con `--tools claude,cline`, sin tocar `specs/features/*` ni `CLAUDE.md`/`.clinerules`), y el primer `/opsx:propose` real se hará sobre la próxima feature que se aborde — un cambio real, no uno de mentira. Esta sesión de instalación en sí no genera deltas de comportamiento (encaja con el caso `skip_specs: true` que la propia CLI reserva para tooling/refactors).

- **Actualización (2026-08-02) — migración ejecutada, desviación en la suerte de los agentes**: se completa la migración con el cambio `migrar-sdd-a-openspec` (primer `/opsx:propose` real del proyecto, `skip_specs: true` por ser tooling y documentación). `openspec/config.yaml` pasa a ser el **source of truth** de la metodología: absorbe stack, convenciones, diseño, seguridad, disciplina TDD (`operations.apply.guidance`) y el gate de revisión (`operations.archive.guidance`). `CLAUDE.md` baja de 98 a 39 líneas y `.clinerules/00-project-rules.md` de 90 a 43, quedándose solo con lo que aplica fuera del flujo de artefactos — que es residuo irreducible, porque `config.yaml` únicamente se inyecta al escribir un artefacto o al ejecutar `apply`/`archive`, mientras que esos dos ficheros se cargan en cada turno.
  **Desviación respecto a las Consecuencias de esta ADR**, que decían que los agentes se *realinearían* en vez de eliminarse: al bajar al detalle, cuatro de los siete (`spec`, `plan`, `impl`, y `task` sin sustituto) se disolvían por completo en los artefactos y operaciones de OpenSpec, `init-agent` quedaba obsoleto, y `test-agent` se solapaba con el paso de cobertura del `review-agent`. Realinear los tres restantes habría dejado dos fuentes de criterio para lo mismo — justo el problema que causó esta migración cuando el borrado de `agents/` (commit `801fdd2`) dejó el criterio de revisión existiendo solo para Claude. Se eliminan los 7 subagentes y los 7 comandos `sdd-*`. Constancia de que ninguna regla operativa se perdió: `notas-migracion-agentes.md` del propio cambio — 10 reglas rescatadas como entradas nuevas de `config.yaml`, 9 descartadas con motivo explícito.
  **Trade-off asumido**: se pierde la revisión en *contexto fresco* que daba `review-agent` como subagente independiente; `/opsx:archive` corre en el mismo contexto que acaba de implementar. `archive.guidance` exige por escrito re-ejecutar la suite y no fiarse del resumen de implementación, pero es una instrucción, no una garantía estructural. Si resulta caro, la vuelta atrás definida es reintroducir un subagente fino que solo diga "ejecuta el gate de `archive.guidance`", sin duplicar criterio — no rompe la agnosticidad. `specs/features/` queda **congelado** (no migrado, no borrado, ver `specs/README.md`), y con la eliminación de `task-agent` se deja de crear issues de GitHub: `tasks.md` es la única trazabilidad de progreso.

## ADR-028: `perfil-usuario` — sin `@tauri-apps/plugin-http` para consultar la API pública NHTSA vPIC

- **Fecha**: 2026-08-01
- **Estado**: Aceptada
- **Contexto**: Ver [[perfil-usuario]]. Es la primera vez que el proyecto consume una API pública externa (NHTSA vPIC, `https://vpic.nhtsa.dot.gov`) desde el frontend, vía el cliente HTTP compartido `fetchJson` (`src/shared/http/external-api.service.ts`, Paso 4 del plan). Para que el WebView de Tauri 2 (especialmente en Android, target prioritario según ADR-018) pueda completar esas peticiones, el host exacto debe añadirse a `connect-src` en la CSP (`app.security.csp` de `src-tauri/tauri.conf.json`, ADR-014) — pero quedaba por decidir si, además de la CSP, hacía falta instalar `@tauri-apps/plugin-http` con permiso explícito en `capabilities/default.json` (como se hace para otras capacidades nativas del proyecto, p. ej. `plugin-fs`/`plugin-sql`) o si el `fetch()` nativo del WebView bastaba.
- **Decisión**: No se instala `@tauri-apps/plugin-http`. `fetchJson`/`fetchVehicleMakes`/`fetchVehicleModels` (Pasos 4 y 5 del plan) usan directamente el `fetch()` nativo del WebView, sujeto únicamente a la CSP (`connect-src` con el host exacto `https://vpic.nhtsa.dot.gov`, añadido en este Paso 6). Existe precedente real y ya verificado en Android del propio proyecto: `route-map.element.ts` pasa la URL `https://tiles.openfreemap.org/styles/dark` directamente a MapLibre GL, que internamente hace sus peticiones de estilo/tiles con `fetch()` nativo, sin ningún plugin Tauri de por medio, y funciona en dispositivo Android real (ver `memory/context.md`). Una petición `fetch()` normal a un host ya permitido por `connect-src` no necesita el plugin — `plugin-http` solo aporta valor cuando se necesita evitar CORS reescribiendo la petición a nivel nativo, caso que no aplica aquí (vPIC no impone restricciones CORS problemáticas para esta integración).
- **Alternativas consideradas**: Instalar `@tauri-apps/plugin-http` con permiso `http:default` en `capabilities/default.json` (descartada: añade una dependencia y una superficie de permisos nuevas — más código a auditar en `cargo audit`/`npm audit` — para resolver un problema, el de peticiones bloqueadas, que la CSP ya resuelve sin plugin; no hay ninguna necesidad de CORS bypass ni de streaming/descarga de archivos que sí justificaría el plugin).
- **Consecuencias**: Cualquier integración HTTP futura con una API externa que ya funcione bajo `connect-src` (host permitido, sin necesidad de eludir CORS) debe seguir el mismo patrón — `fetch()` nativo vía `fetchJson`/`external-api.service.ts`, sin plugin — antes de justificar la instalación de `@tauri-apps/plugin-http`. Si una integración futura sí necesitara evitar CORS o acceso a APIs HTTP más avanzadas (streaming, certificados custom), esa sería la primera vez que se justificaría revisar esta decisión.

## ADR-029: Flujo de Git explícito tras la migración a OpenSpec (rama + PR obligatorios, solo disciplina documentada por ahora)

- **Fecha**: 2026-08-02
- **Estado**: Aceptada
- **Contexto**: El SDD propio anterior documentaba explícitamente `Ramas: feature/<nombre> desde main` en las "Convenciones" de `CLAUDE.md`. La migración a OpenSpec (ver ADR-027) redujo `CLAUDE.md`/`.clinerules/00-project-rules.md` a lo mínimo y esa convención se perdió por el camino — ni `openspec/config.yaml` ni los skills de `propose`/`apply`/`archive` mencionan git en ningún momento (confirmado leyendo sus instrucciones completas). En una sesión real se llegó a ejecutar el ciclo completo `propose → apply → archive` de un cambio (`auditoria-seguridad`) directamente sobre `master`, sin que nada lo señalara, y solo se creó rama y PR al final porque el usuario lo pidió explícitamente. Revisando además el repositorio: `master` no tiene branch protection en GitHub (`404 Branch not protected`), y el único workflow de CI (`Docs`) no ejecuta ningún gate de calidad — todo el enforcement real (ESLint, tsc, Vitest, Clippy, Cargo, auditoría de dependencias) vive únicamente en el hook local `.husky/pre-commit`, saltable con `--no-verify`.
- **Decisión**: Se documenta explícitamente en `CLAUDE.md` y `.clinerules/00-project-rules.md` (sección nueva "Flujo de Git", idéntica en ambos) que toda spec nueva se trabaja en `feature/<nombre-del-cambio>` desde `master` y se cierra con PR a `master` — nunca push directo, ni siquiera tras un `/opsx:archive` con veredicto `APPROVED`. Se corrige además una guía obsoleta en `openspec/config.yaml` (`operations.apply.guidance`) que afirmaba que Cypress estaba desactivado en el pre-commit — ya no es así, `pnpm test:e2e` corre y bloquea de verdad desde hace tiempo.
  **Nivel de enforcement elegido explícitamente con el usuario** (vía pregunta directa, tres opciones planteadas: solo documentado / documentado + hook técnico que rechace commits en `master` / documentado + hook + branch protection real en GitHub): se elige **solo documentado**, sin hook ni branch protection por ahora. Igualmente se decide **no** crear un workflow de CI en GitHub Actions nuevo (quality gate server-side) y **no** automatizar la creación de rama/apertura de PR dentro de los propios skills de OpenSpec — sigue siendo un paso manual que se pide explícitamente al cierre de cada cambio, igual que se ha hecho hasta ahora.
- **Alternativas consideradas**: (1) Hook técnico (`pre-commit`/`pre-push`) que rechace commits directos en `master` — descartada por ahora, se puede saltar con `--no-verify` y añade fricción sin garantía real. (2) Branch protection en GitHub (bloquea push directo a `master` para cualquier colaborador, exige PR) — descartada por ahora por ser un cambio de alcance compartido (afecta a todo el repo, no solo a este agente) que requiere además un CI real como status check para tener sentido. (3) CI nuevo en GitHub Actions con lint/tsc/tests/cargo (y Cypress) como gate visible en cada PR — descartada por ahora, aunque el usuario confirmó que si se creara sí incluiría Cypress. (4) Automatizar rama+PR dentro de los skills `.claude/skills/openspec-propose`/`openspec-archive-change` — descartada: más frágil, una futura actualización de la CLI de OpenSpec (`openspec update` o reinstalación) podría sobrescribir esos ficheros y perder el cambio silenciosamente.
- **Consecuencias**: El cumplimiento de rama+PR depende 100% de que el agente o el humano que commitea lo recuerde — no hay ningún mecanismo técnico que lo fuerce, y `CLAUDE.md`/`.clinerules` lo dicen explícitamente para que nadie asuma lo contrario. Si en el futuro se decide subir el nivel de enforcement (hook, branch protection, CI), revisar primero esta ADR y las tres alternativas ya evaluadas y descartadas aquí, en vez de re-discutirlas desde cero.

## ADR-030: GitHub Project como tablero de visibilidad, a granularidad de cambio (no de tarea)

- **Fecha**: 2026-08-02
- **Estado**: Aceptada
- **Contexto**: Tras fijar el flujo de Git (ADR-029) se planteó si añadir GitHub Projects para dar visibilidad de conjunto entre los dos colaboradores del repo (`GonzaloCarmenado`, `viictoryraves`) — algo que OpenSpec no aporta hoy: `tasks.md` trackea el progreso *dentro* de un cambio, pero no hay ningún sitio que muestre qué cambios están en qué fase, ni un backlog de ideas que todavía no son un cambio formal (hasta ahora vivían como prosa suelta "Pendiente"/"Próximos pasos" en `memory/context.md`). Al investigar el estado real: el repo `moto-routes` pertenece a la organización `crzverde` (no a un usuario), que no tenía ningún Project propio — solo existían 2 Projects personales de `GonzaloCarmenado`, sin relación (uno vacío, el otro con issues de un repo distinto, `dccredit-gestion`). Además había 2 issues huérfanos de antes de la migración a OpenSpec (#53 reorganizar `specs/features/`, #51 cobertura E2E) ya resueltos por trabajo posterior pero nunca cerrados.
- **Decisión**: Se crea el Project **"Moto Routes"** en la organización `crzverde` ([github.com/orgs/crzverde/projects/1](https://github.com/orgs/crzverde/projects/1)), vinculado al repo. **Una card por cambio de OpenSpec, nunca por tarea de `tasks.md`** — la ADR-027 ya decidió explícitamente no crear un issue por tarea (eso hacía el `task-agent` del SDD viejo, se eliminó a propósito) y esta decisión lo respeta en vez de reintroducirlo por la puerta de atrás. Campo custom `Fase` (el campo `Status` por defecto de GitHub no se puede borrar ni editar sus opciones vía `gh` CLI, solo desde la web — se crea `Fase` en paralelo en vez de pelear con esa limitación): `Backlog` → `Propuesto` → `En progreso` → `En revisión` → `Hecho`, mapeado 1:1 al ciclo de vida real de un cambio OpenSpec + su PR. Gestión **manual, a petición explícita** (mismo criterio elegido en ADR-029 para rama/PR): sin automatización dentro de los skills de OpenSpec, por el mismo motivo de fragilidad ante actualizaciones de la CLI. Se cierran además los issues huérfanos #53 y #51 con comentario explicando su estado real, como limpieza previa.
- **Alternativas consideradas**: (1) Reutilizar uno de los 2 Projects personales existentes — descartada, están sucios (uno con datos de otro repo) y no son del owner correcto para un repo de organización. (2) Una card por tarea de `tasks.md` (paridad con el `task-agent` del SDD viejo) — descartada explícitamente, contradice la ADR-027. (3) Automatizar la creación/movimiento de cards dentro de `.claude/skills/openspec-propose`/`openspec-archive-change` — descartada por el mismo motivo de fragilidad que en ADR-029 (una actualización de la CLI de OpenSpec podría sobrescribirlo en silencio). (4) Repurponer el campo `Status` por defecto en vez de crear `Fase` — descartada, `gh project field-delete` rechaza los campos no-custom (`Only custom fields can be deleted`) y no hay `field-edit` para cambiar sus opciones desde la CLI.
- **Consecuencias**: Requiere el scope `project`/`read:project` en el token de `gh` (no estaba concedido por defecto — se amplió en esta misma sesión vía `gh auth refresh -h github.com -s project -s read:project`, login interactivo). El campo `Status` por defecto de GitHub queda sin uso deliberado para las cards de cambios (algunas automatizaciones nativas de GitHub que dependen de él, como el auto-archivado al cerrar un issue enlazado, no aplicarán a `Fase`); si en el futuro se quiere aprovechar esas automatizaciones nativas, habría que editar `Status` a mano desde la web con las mismas opciones que `Fase`, en vez de mantener los dos campos en paralelo.

## ADR-031: CI/CD real en GitHub Actions — un workflow con 3 jobs, sin firma de release, trigger por tag

- **Fecha**: 2026-08-02
- **Estado**: Aceptada
- **Contexto**: Ver [[ci-cd-pipeline]] (`openspec/changes/ci-cd-pipeline/`). El único workflow existente (`docs.yml`) estaba roto (dependencias de sistema para `cargo doc` en target desktop, nunca instaladas) y no ejecutaba ningún gate de calidad. Todo el enforcement real vivía solo en `.husky/pre-commit`, saltable con `--no-verify` y nunca corrido server-side sobre el código de otros colaboradores. `master` tampoco tiene branch protection (confirmado en ADR-029). La ADR-021 ya documentó un caso real de gates rotos semanas sin detectar precisamente por falta de verificación independiente del entorno de quien commiteaba.
- **Decisión**: Un único `.github/workflows/ci.yml` con 3 jobs — `quality-ts` y `quality-tauri` en cada push a `master` y cada PR (mismos comandos y umbrales que `.husky/pre-commit`, sin relajar nada); `build-and-release` (`needs: [quality-ts, quality-tauri]`, `if` acotado a tags `v*`) compila el APK con la CLI de Tauri y lo publica como asset de un GitHub Release. **Sin firma de release real** (confirmado con el usuario): el APK sigue siendo el debug de siempre, sin keystore ni secretos nuevos que gestionar — limitación aceptada: cada release usa un keystore de debug distinto generado en el runner efímero, así que actualizar una instalación previa puede requerir desinstalar antes. Runner `ubuntu-latest` para el job de release (estándar de la comunidad Tauri/Android CI, más barato y rápido que Windows).
  **Corrección real encontrada durante `propose`**: `src-tauri/.cargo/config.toml` tenía hardcodeada la ruta de Windows del linker del NDK de la máquina de esta sesión — se resuelve sobreescribiendo `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` por variable de entorno del job, sin tocar el fichero (sigue haciendo falta tal cual en local).
  **3 gaps reales encontrados en la primera ejecución real en GitHub Actions** (tag de prueba `v0.0.1-test`), ninguno detectable por el test estructural local — la razón de por qué el plan incluía explícitamente un paso de verificación en CI real y no se dio nunca el pipeline por bueno solo con el test: (1) `sdkmanager` no está en `PATH` por defecto en `ubuntu-latest` aunque el SDK viene preinstalado — resuelto localizándolo con `find` en vez de asumir una subruta de versión; (2) `${{ env.ANDROID_HOME }}` en un campo estructurado de GitHub Actions (`path:` de `actions/cache`) es una expresión inválida si la variable no está declarada en un bloque `env:` del propio workflow — las variables de entorno del runner en tiempo de ejecución no cuentan ahí, hay que promocionarlas explícitamente vía `$GITHUB_ENV`; (3) el `GITHUB_TOKEN` automático solo tiene `contents: read` por defecto, `softprops/action-gh-release` fallaba con 403 — resuelto con `permissions: contents: write` acotado solo al job `build-and-release`, no a todo el workflow.
- **Alternativas consideradas**: (1) 3 workflows separados (uno por job) — descartada, `needs:` (la dependencia real entre quality gates y release) solo funciona dentro del mismo fichero; 3 ficheros habrían necesitado `workflow_run`, más lento y frágil, lo contrario del objetivo explícito de "eficiente". (2) Firma de release con keystore real — descartada por ahora (confirmado con el usuario), sin secretos nuevos que gestionar de entrada. (3) `windows-latest` para el job de Android — descartado, más caro/lento y sin ventaja real ya que el hallazgo del linker obligaba de todas formas a no depender de rutas de la máquina local. (4) `cargo install cargo-audit --locked` en el job de Rust — descartado por lento (compila desde fuente), se usa `taiki-e/install-action@v2` (binario precompilado).
- **Consecuencias**: Cualquier cambio futuro al workflow debe re-verificarse con un tag de prueba real antes de darlo por bueno — el test estructural (`src/shared/ci/ci-workflow.spec.ts`) solo protege contra regresiones de la estructura ya conocida, no contra gaps nuevos del entorno real de GitHub Actions (los 3 gaps de esta sesión son prueba de ello). El `versionCode` de Android sigue reseteándose a 1000 en cada build (limitación conocida, sin resolver — ver `memory/context.md` § Build Android) y no se ataca aquí porque, combinado con la firma de debug efímera, arreglar solo el `versionCode` no daría una actualización in-place funcional de todas formas.

## ADR-032: `entorno-api-docker` — monorepo (`apps/mobile` + `apps/api`), backend Java/Spring Boot + Maven, imágenes Docker Debian 13 (trixie)

- **Fecha**: 2026-08-03
- **Estado**: Aceptada
- **Contexto**: Ver [[entorno-api-docker]] (`openspec/changes/entorno-api-docker/`). Hasta ahora Moto Routes solo existe como app móvil (Tauri + frontend) con persistencia local en SQLite, sin ningún backend propio. Primer paso hacia un servidor real: un entorno mínimo de API + BBDD, reproducible en local con Docker, y coherente con el servidor de producción real (Debian 13). Al introducir una segunda aplicación de naturaleza distinta (servicio Java frente a app Tauri/TypeScript), el repositorio deja de tener sentido como paquete único en la raíz.
- **Decisión**:
  1. **Monorepo por `apps/`**: `apps/mobile/` (todo el contenido actual de raíz relativo a la app móvil, movido sin cambio de comportamiento) + `apps/api/` (servicio Java nuevo) + `infra/docker/` (orquestación local). `src-tauri/` y `src/` NO se separan entre sí — son una sola app, Tauri empaqueta ese mismo frontend. `openspec/`, `specs/`, `docs/`, `memory/`, `.github/` se quedan en la raíz, transversales al monorepo.
  2. **Backend**: Spring Boot + Maven (wrapper `mvnw`). Se prioriza la base convencional de Java (REST + JDBC) sobre un servidor mínimo con `HttpServer` del JDK, asumiendo que esta API va a crecer más allá del endpoint de prueba inicial — evita reescribir la base cuando llegue esa funcionalidad real.
  3. **Imágenes Docker alineadas con Debian 13 (trixie)** para paridad dev/prod: Postgres usa la variante oficial `postgres:16-trixie` (confirmada existente en Docker Hub). La imagen Java NO puede ser `eclipse-temurin` con tag trixie — verificado que esa imagen oficial de OpenJDK todavía no publica variante Debian trixie (solo Ubuntu noble/jammy, Alpine, UBI) — así que la imagen de `apps/api` parte de `debian:trixie-slim` con el JDK instalado vía `apt` (Debian 13 trae `openjdk-21-jdk-headless` en sus repos), no de una imagen Java de otra distribución.
  4. **Sin herramienta de migraciones dedicada (Flyway/Liquibase) por ahora**: la única tabla dummy se crea vía script SQL en `docker-entrypoint-initdb.d/` (mecanismo nativo de la imagen oficial de Postgres), sin dependencia nueva. Revisar cuando el esquema deje de ser trivial.
- **Alternativas consideradas**: (1) Separar `src/` (frontend) y `src-tauri/` (Rust) en apps distintas — descartada, son una sola app, Tauri empaqueta ese mismo frontend, separarlas solo añadiría complejidad de build sin beneficio real. (2) `HttpServer` plano del JDK sin framework — descartada por el usuario explícitamente: menor huella inicial, pero cualquier crecimiento futuro (routing, validación, JSON) habría que construirlo a mano. (3) Gradle en vez de Maven — descartado, Maven es más ubicuo en documentación/tutoriales de Spring Boot y no hay ya experiencia previa con Gradle en el equipo. (4) Reorganizar el monorepo como cambio previo separado, antes de añadir la API — descartada explícitamente por el usuario: la reorganización solo tiene motivo por la llegada de la API, hacerla aparte habría sido un cambio de "mover carpetas" sin justificación propia documentada.
- **Consecuencias**: Blast radius real de la reorganización a verificar en `apply`: `pnpm-workspace.yaml` (hoy sin campo `packages:`, pasa a apuntar a `apps/mobile`), `.github/workflows/ci.yml`, `.husky/pre-commit`, scripts de `docs/` — todo lo que hoy asume rutas relativas a la raíz del repo. Sin dependencias npm/Cargo nuevas (solo Maven, ecosistema Java independiente). Ningún despliegue real al servidor Debian 13 de producción entra en el alcance de este cambio — queda para una spec posterior.

## ADR-033: `despliegue-servidor-tailscale` — Docker vía repo oficial (no `docker.io` de Debian), API atada a la interfaz Tailscale, reutiliza el PostgreSQL nativo ya existente

- **Fecha**: 2026-08-03
- **Estado**: Aceptada
- **Contexto**: Ver [[despliegue-servidor-tailscale]] (`openspec/changes/despliegue-servidor-tailscale/`). Primer despliegue real de `apps/api` (nacido en `entorno-api-docker`, ver [[ADR-032]]) en el servidor de producción: un Debian 13 doméstico sin IP pública, alcanzable solo por Tailscale (`[tailscale-ip-redactada]`) y por la LAN local del usuario. Investigación real por SSH en esta sesión (no asumida): ni Docker ni Git instalados; ya existe un PostgreSQL 17 **nativo** (no Docker) con `appdb`/`appuser` creados de antemano por el propio usuario específicamente para este despliegue, solo aceptando conexiones por loopback (`pg_hba.conf` sin exposición de red); Debian trixie solo empaqueta `docker-compose` v1 (Python, EOL), no el plugin `docker compose` v2 que ya usa el entorno local.
- **Decisión**:
  1. **Docker vía el repositorio oficial de Docker**, no `docker.io`+`docker-compose` v1 de Debian — verificado con `curl` en esta sesión que `download.docker.com` sirve paquetes reales para `trixie` (había reportes contradictorios sobre si trixie ya estaba soportado; se comprobó en vez de asumir). Da `docker-ce`+`docker-compose-plugin` (comando `docker compose`, coherente con el entorno local).
  2. **El contenedor de `apps/api` usa el PostgreSQL nativo ya existente**, nunca uno nuevo en Docker — `network_mode: host` para que `127.0.0.1` dentro del contenedor sea el loopback real del host (ya permitido por `pg_hba.conf` tal cual está), sin tocar su configuración. Nuevo fichero `infra/docker/docker-compose.prod.yml` (solo servicio `api`), no se reutiliza el `docker-compose.yml` local (que levanta su propio Postgres y chocaría por el puerto 5432 ya ocupado por el nativo).
  3. **La API solo escucha en la interfaz de Tailscale**: nueva propiedad `server.address=${SERVER_ADDRESS:0.0.0.0}` en `apps/api/src/main/resources/application.properties` (default `0.0.0.0` para no romper el entorno local, que nunca define `SERVER_ADDRESS`); en producción se fija a la IP de Tailscale del servidor. Con `network_mode: host`, Spring Boot expondría 8080 en todas las interfaces (incluida la LAN doméstica) si no se restringe explícitamente — la propia aplicación acota su exposición, no un firewall aparte.
  4. **Build en el propio servidor**: clonar el repositorio (público) y construir con el mismo `Dockerfile` de `apps/api`, sin registro de contenedores ni credenciales nuevas — coherente con que este cambio explícitamente no incluye CI/CD de despliegue todavía.
  5. **Credenciales**: la contraseña de `appuser` se regeneró en esta sesión (`ALTER USER`) y vive solo en `infra/docker/.env.prod` (no versionado, creado a mano por SSH) — mismo patrón que `infra/docker/.env` de `entorno-api-docker`, con `.env.prod.example` versionado como plantilla.
- **Alternativas consideradas**: (1) `docker.io`+`docker-compose` v1 de Debian — descartada, herramienta ya sin mantenimiento activo y con un comando distinto (`docker-compose` vs `docker compose`) al que ya usa el entorno local. (2) Postgres nuevo en Docker en el servidor — descartada, hay que reutilizar el que el propio usuario ya preparó para esto, y evita gestionar dos instancias de Postgres en la misma máquina. (3) Exponer la API en todas las interfaces confiando en un firewall aparte (`ufw`/`iptables`) — descartada como mecanismo principal: más superficie de configuración externa que mantener sincronizada; se prefiere que la propia aplicación no escuche donde no debe, dejando un firewall como capa adicional posible pero no la única barrera. (4) TLS/HTTPS en este endpoint — descartada por ahora, el tráfico ya viaja cifrado dentro del túnel de Tailscale y añadir TLS sería sobre-ingeniería para un endpoint de prueba interno.
- **Consecuencias**: Sin pipeline de CI/CD, cada actualización de `apps/api` en el servidor requiere repetir `git pull` + `docker compose -f docker-compose.prod.yml up -d --build` a mano — candidato claro para un cambio futuro dedicado. `application.properties` pasa a ser compartido entre local y producción vía `SERVER_ADDRESS` con default seguro; cualquier cambio futuro a ese fichero debe preservar el default `0.0.0.0` para no romper `infra/docker/docker-compose.yml` (entorno local).

## ADR-034: `migrar-api-golang` — sustitución de Java/Spring Boot por Go en `apps/api`, con `chi`+`pgx`+`golang-jwt`+`bcrypt`, runner de migraciones propio y rate limiting en memoria

- **Fecha**: 2026-08-04
- **Estado**: Aceptada
- **Contexto**: Ver [[migrar-api-golang]] (`openspec/changes/migrar-api-golang/`). [[ADR-032]] eligió Java 21 + Spring Boot + Maven para `apps/api` asumiendo que la API crecería más allá del endpoint de prueba, sin conocer todavía qué funcionalidad concreta traería ese crecimiento. Ahora sí se conoce: validación/autenticación de usuarios, un apartado de seguridad explícito y, a futuro, almacenamiento de blobs tipo Azure Blob Storage y notificaciones en tiempo real tipo SignalR. Esta ADR **sustituye la elección de lenguaje/framework de ADR-032**, sin invalidar el resto de sus decisiones (estructura de monorepo por `apps/`) ni las de [[ADR-033]] (despliegue vía Tailscale, reutilización del PostgreSQL nativo).
- **Decisión**:
  1. **Go en vez de Java o Rust**: SDK oficial de Azure Blob Storage más maduro en Go que en Rust, librerías de JWT/OAuth más asentadas, y las goroutines encajan de forma natural con un servidor de notificaciones en tiempo real (mismo motivo por el que Centrifugo, sustituto habitual de SignalR, está escrito en Go).
  2. **Router: `chi` sobre `net/http` estándar**, no un framework completo (Gin/Echo/Fiber) — una sola dependencia pequeña, compatible con `http.Handler` estándar, necesaria para encadenar middleware (autenticación por token, cabeceras de seguridad, límite de intentos de login) de forma idiomática. No reemplaza `net/http`, lo complementa.
  3. **Autenticación: JWT firmado (HMAC) vía `golang-jwt/jwt/v5`, contraseñas con `golang.org/x/crypto/bcrypt`** — reimplementar a mano el parseo/verificación de JWT es código de seguridad de alto riesgo; se prefiere una librería madura y auditada. `bcrypt` vive bajo `golang.org/x/crypto`, mantenido por el propio equipo de Go, no un paquete de terceros con el mismo perfil de riesgo que uno cualquiera.
  4. **Cliente de PostgreSQL: `jackc/pgx/v5`** — activamente mantenido, con pool de conexiones propio (`pgxpool`); sustituye a `lib/pq`, hoy en mantenimiento mínimo.
  5. **Migraciones de esquema: runner propio mínimo** (ficheros `.sql` versionados + tabla `schema_migrations`), no `golang-migrate`. ADR-032 pospuso una herramienta de migraciones "hasta que el esquema deje de ser trivial" — con la tabla de usuarios de `user-auth` deja de serlo, pero un runner propio de ~30 líneas cubre la necesidad sin añadir una dependencia nueva.
  6. **Límite de intentos de login: contador en memoria** (mapa + mutex), no un store compartido tipo Redis — `apps/api` sigue siendo un único contenedor sin réplicas (ADR-033); se pierde el contador si el proceso reinicia, aceptado mientras eso no cambie.
  7. **Imagen Docker final: se mantiene `debian:trixie-slim`**, no `scratch`/distroless pese a que un binario Go estático no lo necesita — prioriza paridad operativa con el resto del monorepo (mismas herramientas de diagnóstico disponibles vía `docker exec`) sobre el tamaño mínimo de imagen.
- **Alternativas consideradas**: (1) Rust — descartado pese a que el proyecto ya lo usa en `apps/mobile/src-tauri` (con `cargo audit`/`clippy`/`rustfmt` ya cableados en CI); el ecosistema de Azure SDK y de librerías de auth está menos maduro que en Go, y el desarrollo de una API CRUD con estos requisitos sería más lento. (2) Mantener Java/Spring Boot y solo añadir la funcionalidad nueva — descartada, no resuelve el motivo de fondo (preparar el terreno para blob storage y tiempo real con el mejor ecosistema disponible). (3) Gin/Echo/Fiber en vez de `chi` — descartados, frameworks completos con más superficie de la necesaria para esta API. (4) `golang-migrate` en vez de runner propio — descartado por ahora, dependencia de más para lo que resuelve un script simple con el tamaño de esquema actual. (5) Redis para el límite de intentos de login — descartado, infraestructura nueva injustificada mientras el servicio sea una sola instancia.
- **Consecuencias**: `apps/api/Dockerfile`, `infra/docker/docker-compose*.yml`, `.github/workflows/ci.yml` y toda la disciplina de pre-commit (auditoría de dependencias) ganan un segundo ecosistema de build (Go) además de TS/Rust — mismo patrón multi-lenguaje que ya introdujo ADR-032 con Java. El runner de migraciones propio y el rate limiting en memoria son decisiones explícitamente revisables: la primera si el esquema crece mucho más, la segunda si el servicio deja de ser una sola instancia.

## ADR-035: `catalogo-tipos-parada` — primera llamada real de `apps/mobile` a `apps/api`, iconos como emoji, timeline pasa de recalcular a leer paradas persistidas

- **Fecha**: 2026-08-04
- **Estado**: Aceptada
- **Contexto**: Ver [[catalogo-tipos-parada]] (`openspec/changes/catalogo-tipos-parada/`). Hasta ahora `apps/mobile` nunca ha llamado a `apps/api` — son dos aplicaciones que coexisten en el monorepo desde [[ADR-032]] pero sin integración real entre ellas. Este cambio introduce la primera: un catálogo de tipos de parada servido por el backend y consumido por el móvil.
- **Decisión**:
  1. **URL base de `apps/api` en el móvil: variable de entorno de build (`VITE_API_BASE_URL`), con `http://localhost:8080` como único valor versionado** (`apps/mobile/.env.example`), no un mecanismo de descubrimiento ni configuración en tiempo de ejecución. El host real de producción (interfaz Tailscale del servidor) **nunca se comitea** — el repositorio es público y ese dato ya se trata como sensible en el proyecto (redactado incluso en la documentación de [[ADR-033]]) — vive solo en `apps/mobile/.env.local` (nuevo patrón `.env*.local` de Vite, gitignored) en la máquina donde se construye el APK de producción. La CSP (`tauri.conf.json`/`index.html`) sigue el mismo patrón: `connect-src` versionado solo permite `http://localhost:8080`; el build de producción real añade el host verdadero vía `tauri android build --config <fichero-json-local-no-versionado>` (merge de Tauri sobre la config base), nunca escrito en un fichero versionado.
  2. **Iconos del catálogo como carácter emoji** (columna `icon TEXT`), no un sistema de iconos SVG/font nuevo. La app no tiene hoy ningún sistema de iconos propio (`shared/route-map/` dibuja marcadores con `div`/CSS, no iconografía); un emoji se renderiza nativo sin pipeline de assets ni dependencia nueva, coherente con "dependencias mínimas".
  3. **El timeline deja de recalcular paradas desde `route_points` y pasa a leer `route_stops` persistidas** — cambio de comportamiento observable deliberado (antes mostraba cualquier parada detectada por velocidad, incluidos semáforos; ahora solo paradas manuales con tipo asignado). `specs/features/timeline-ruta.md` (histórico congelado) no se edita, pero su comportamiento documentado queda superado a partir de este cambio.
  4. **`GET /api/stop-types` es el único endpoint de `apps/api` sin autenticación además de `/api/ping`** — dato de referencia no sensible, ver `design.md`.
  5. **`GET /api/stop-types` responde con `Access-Control-Allow-Origin: *`** (`internal/httpmw/cors.go::PublicCORS`, aplicado solo a esa ruta) — gap real encontrado durante la verificación E2E de este cambio (grupo 8, `apps/api` real vía Docker Compose + Cypress contra el backend real, no mockeado): sin cabeceras CORS, el navegador bloqueaba en silencio el `fetch` cross-origin desde `apps/mobile` (`http://localhost:1420` en desarrollo, `tauri://localhost`/host de Tailscale en producción) contra `apps/api` (`http://localhost:8080` / IP de Tailscale) — `refreshStopTypesCache` lo capturaba como fallo de red normal (best-effort) y la caché se quedaba vacía sin ningún error visible, ni siquiera en consola. Wildcard aceptado porque el endpoint es público, sin autenticación ni credenciales (mismo criterio que el punto 4) — **no usar `*` en ningún endpoint autenticado futuro**, que necesitará reflejar un origen concreto.
  6. **El trigger de "marcar parada manual" es el botón "Pausar" existente, no un control dedicado aparte** — corrección de UX tras verificación en dispositivo Android real (grupo 8.3): un icono nuevo junto a la cámara generaba confusión, el usuario esperaba que "el botón de parada" fuera el mismo que ya pausa la grabación. `handlePauseResume()` pausa y (solo al pausar, nunca al reanudar) abre también el modal de tipo — cancelarlo no revierte la pausa, son independientes. Ver corrección en `tasks.md` grupo 4.
  7. **Corrección al punto 1**: `tauri android build --config <fichero-json-local-no-versionado>` **NO** reescribe el `<meta http-equiv="Content-Security-Policy">` de `index.html` empaquetado en el APK de Android — verificado durante la build de verificación del grupo 8.3 (el CSP del `assets/index.html` real dentro del APK seguía siendo literalmente el de `apps/mobile/index.html`, pese a pasar `--config` con un `security.csp` distinto). En Android, el CSP que de verdad aplica el WebView es el de la etiqueta `<meta>` de ese HTML estático, no el campo `tauri.conf.json`→`app.security.csp` (ese campo sí controla otros mecanismos de Tauri, pero no reescribe el HTML empaquetado para este target). Para una build de verificación puntual en local con un host no versionado (p. ej. la IP LAN del PC de desarrollo), la única vía que funciona es editar temporalmente `apps/mobile/index.html` **y** `src-tauri/tauri.conf.json` a la vez, revertir ambos con `git checkout` en cuanto termine la prueba, y no comitear nunca ese host.
  8. **La release real de GitHub Actions (`.github/workflows/ci.yml::build-and-release`, se dispara al pushear un tag `v*`) no tenía ningún mecanismo para apuntar al servidor de producción** — gap real encontrado al preguntar el usuario "¿la release del Action apunta al servidor?": el job corría `pnpm tauri android build` sin `--config`, sin `VITE_API_BASE_URL` ni ningún secret, así que cualquier APK publicado en un GitHub Release habría apuntado a `localhost:8080` (inútil en el móvil de quien lo instala) — nadie lo había notado porque hasta este cambio `apps/mobile` nunca llamaba a `apps/api`. Corregido con un nuevo step `Configure production apps/api host` que lee el secret `MOBILE_PROD_API_BASE_URL` (a configurar por el usuario en Settings → Secrets and variables → Actions, no fijado por ningún agente — el valor real del host nunca lo ha visto este agente, ver [[ADR-033]]), falla el job explícitamente si el secret no está definido (mejor un release que no se publica que uno que se publica roto), inyecta `VITE_API_BASE_URL` vía `GITHUB_ENV` y parchea con `sed` el `connect-src` de `index.html` y `tauri.conf.json` — igual que el fix manual del punto 7, pero automático y en un checkout efímero (nunca se escribe de vuelta al repo). El step de verificación existente ("bundles the freshly built frontend") se amplía para comprobar también que el CSP empaquetado en el APK final contiene el host real, no solo que el JS esté actualizado — habría atrapado este gap automáticamente si hubiera existido antes.
- **Alternativas consideradas**: (1) Configurar la URL de `apps/api` en tiempo de ejecución (pantalla de ajustes) — descartada por sobre-ingeniería, no hay hoy más de un servidor real al que apuntar. (2) Icono SVG propio alineado con "Asfalto Nocturno" — más consistente visualmente, descartado por ahora: exige diseñar un set de iconos nuevo y un pipeline de assets que no existe, coste no justificado para una primera versión. (3) Mantener el timeline recalculando desde GPS y filtrar en el momento de renderizar — descartada, mezclar "parada efímera detectada" con "parada real persistida con tipo" en la misma función habría sido más confuso que separar limpiamente ambas fuentes. (4) Comitear la IP de Tailscale del servidor en `tauri.conf.json`/código — descartada explícitamente durante `apply`, al caer en la cuenta de que el repositorio es público justo antes de comitearla; contradice el patrón ya establecido de no escribirla ni en la documentación (ver [[ADR-033]]). (5) Mantener el botón "Marcar parada" dedicado — descartado tras feedback real de usuario en dispositivo (punto 6), la confusión observada pesa más que la separación conceptual "pausar ≠ tipar parada".
- **Consecuencias**: primera vez que `apps/mobile` depende de la disponibilidad de `apps/api` para algo, aunque sea de forma opcional y cacheada — la app SHALL seguir funcionando sin red y sin backend disponible. Nueva entrada en `connect-src` de la CSP (`tauri.conf.json` + `index.html`) con `http://localhost:8080` únicamente; el host real de producción solo existe en ficheros locales no versionados (`apps/mobile/.env.local`, config JSON local para `tauri android build --config`) — quien construya el APK de producción por primera vez necesita crear esos ficheros a mano (documentado en `apps/mobile/.env.example` y en `tasks.md` de este cambio). La decisión de URL fija por Tailscale (no descubrimiento de servicio) es explícitamente revisable si la app llega a tener usuarios reales fuera del tailnet del desarrollador — no es objetivo de este cambio resolverlo.

## ADR-036: Release `v0.1.0` rota en producción real — servidor desactualizado (rama y binario) y secret `MOBILE_PROD_API_BASE_URL` sin esquema/puerto

- **Fecha**: 2026-08-05
- **Estado**: Aceptada
- **Contexto**: El usuario reportó que, en la primera release real (`v0.1.0`, publicada tras cerrar [[catalogo-tipos-parada]]/ADR-035), pausar para marcar una parada no mostraba el catálogo de tipos. Era la primera vez que el mecanismo completo (servidor real + release de CI + APK instalado en un móvil real) se ejercitaba de punta a punta — el "MINOR ISSUE" ya anotado en el review de ADR-035 ("el mecanismo de CI que apunta al servidor real aún no se ha probado en un runner real") resultó ser solo la punta de un problema más largo, con tres causas independientes y acumulativas, cada una enmascarando la siguiente hasta corregir la anterior:
  1. El servidor Debian de producción (ver [[ADR-033]]) estaba apagado — confirmado con `tailscale status` desde esta misma máquina de desarrollo (también en el tailnet desde ADR-033), que mostraba el nodo `debian` como `offline`.
  2. Una vez encendido, `GET /api/stop-types` devolvía `404`: el checkout del servidor estaba en `feature/migrar-api-golang` (commit `742d04c`, anterior a que existiera el endpoint) — el despliegue de ADR-033/034 nunca se repitió después de mergear [[catalogo-tipos-parada]]. El `master` local del propio servidor tenía además historia divergente de `origin/master` (129 vs. 146 commits), arrastrada desde el despliegue original — se resolvió con `git reset --hard origin/master`, aceptable porque ese checkout es solo material de build, sin commits propios de valor.
  3. Con el backend ya al día, el catálogo seguía sin llegar al móvil: el bundle JS de la release (`v0.1.0`, descargada e inspeccionada con `unzip`/`grep`) tenía horneado literalmente `"100.114.190.36"` como base de la API — el secret de GitHub `MOBILE_PROD_API_BASE_URL` estaba guardado sin `http://` ni `:8080`. `fetch("100.114.190.36/api/stop-types")` es una URL relativa sin esquema, resuelta contra el origen de la propia app, nunca contra el servidor real — fallo silencioso, capturado por el `try/catch` best-effort de `refreshStopTypesCache` (ver ADR-035), indistinguible desde la UI de "sin red".
  4. Efecto colateral al instalar `v0.1.1` (con el secret ya corregido) sobre el `v0.1.0` ya puesto en el móvil de pruebas: cada build de CI genera un keystore de debug distinto (ya documentado en el cuerpo de cada Release) — una instalación con firma distinta a la ya presente puede fallar en silencio y dejar corriendo la app vieja, indistinguible en la UI de "la release sigue rota". Confirmado como la explicación más probable de por qué la primera prueba de `v0.1.1` "no funcionaba igual" pese a que el APK descargado, inspeccionado aparte, ya llevaba la URL correcta.
- **Decisión**:
  1. Redesplegar `apps/api` en el servidor real (`git checkout master && git reset --hard origin/master && docker compose -f docker-compose.prod.yml up -d --build`), mismo mecanismo ya documentado en ADR-033 — sin cambiarlo, solo repetirlo. No se automatiza el despliegue en este cambio (fuera de alcance, ya anotado como pendiente en ADR-033).
  2. Corregir el secret `MOBILE_PROD_API_BASE_URL` a `http://100.114.190.36:8080` (esquema + puerto) y publicar `v0.1.1` para hornear el valor correcto — un secret mal formado no se corrige retroactivamente en una release ya publicada.
  3. **No se endurece en este cambio** el paso `Verify the APK bundles...` de `ci.yml` (ADR-035, punto 8), pese a que su `grep -qF "$PROD_API_BASE_URL"` es exactamente el punto ciego que dejó pasar el secret roto sin detectarlo (comprueba que el literal aparezca en algún sitio del HTML empaquetado, no que sea una URL absoluta válida usable en `fetch()`) — deuda técnica anotada aquí, no arreglada, para no mezclar una investigación de incidente con una mejora de CI en la misma sesión.
- **Alternativas consideradas**: Automatizar el despliegue del servidor (webhook/GitHub Action que haga `ssh`+`git pull`+`docker compose up` en cada push a `master`) — descartado por ahora, mismo criterio que ADR-033 (ceremonia no automatizada por defecto en este proyecto, ver ADR-029/030) y fuera del alcance de una investigación de incidente puntual.
- **Consecuencias**: El servidor de producción **no se actualiza solo** al mergear una PR — sigue siendo un paso manual (`git pull` + `docker compose up -d --build`) que hay que recordar tras cualquier cambio a `apps/api`, ahora con precedente real de que olvidarlo rompe producción en silencio. Cualquier secret de URL futuro (`MOBILE_PROD_API_BASE_URL` u otro) debe verificarse como URL absoluta completa (`scheme://host:port`), no solo como string no vacío — candidato claro para el endurecimiento de CI diferido en el punto 3.

- **Actualización (2026-08-05, más tarde en la misma sesión) — gap de diseño real: la API solo era alcanzable desde el tailnet del desarrollador, no para un usuario real cualquiera**: con `v0.1.1` ya sirviendo el catálogo correctamente al probarlo desde el propio dispositivo de desarrollo, apareció un cuarto problema, esta vez de diseño y no operativo — señalado por el propio usuario al ver que hacía falta instalar Tailscale en el móvil de pruebas: `100.114.190.36` es una IP de Tailscale (rango CGNAT `100.64.0.0/10`), solo enrutable para dispositivos dentro de ese tailnet — confirmado que el móvil de pruebas no tenía el paquete Tailscale instalado (`adb shell pm list packages`) ni interfaz `tun0`. ADR-033 ya decidió deliberadamente "solo alcanzable por Tailscale" partiendo de que el servidor no tiene IP pública — válido para uso interno del propio desarrollador, pero incompatible con el propósito real de una release pública: cualquier usuario que instale el APK necesitaría además unirse a la red privada del desarrollador, algo que no tiene sentido pedir.
  **Decisión**: activar **Tailscale Funnel** en el servidor (`sudo tailscale funnel --bg http://100.114.190.36:8080` — el target por defecto, `127.0.0.1:8080`, no sirve porque `apps/api` solo escucha en la IP de Tailscale, nunca en loopback, ver ADR-033 punto 3) en vez de port-forwarding en el router o un dominio con IP pública/DDNS. Expone `apps/api` como `https://debian.taildf3dab.ts.net`, genuinamente público (verificado resolviendo el nombre por DNS público de Google, `8.8.8.8`, y con `curl` obteniendo `200` con certificado válido, sin necesidad de estar en el tailnet) — preserva la razón original de ADR-033 (sin IP pública, sin abrir puertos en el router) mientras resuelve el problema real (acceso público de verdad). Secret `MOBILE_PROD_API_BASE_URL` actualizado a esa URL HTTPS; publicada `v0.1.3`.
  **Alternativas consideradas**: Port-forward del puerto 8080 (o 443 con reverse proxy) en el router doméstico + dominio propio (DDNS o IP fija si el ISP la diera) — descartada por ahora: más superficie expuesta directamente a internet sin la capa de Tailscale de por medio, y depende de que el ISP no haga CGNAT (sin confirmar). Documentar el gap sin tocar la red de producción — descartada, el usuario prefirió resolverlo ya al ser un defecto de diseño real, no cosmético.
  **Consecuencias**: Cualquier release futura debe seguir apuntando a la URL de Funnel (`https://debian.taildf3dab.ts.net`), no a la IP de Tailscale directamente — si el servidor cambiara de máquina o de nombre en el tailnet, hay que repetir `tailscale funnel --bg` con el nuevo target y actualizar el secret. Funnel depende de que `tailscaled` sega corriendo en el servidor (mismo proceso que ya se asume disponible desde ADR-033); no depende de que el contenedor Docker se reinicie. Sigue pendiente decidir si en algún momento conviene pasar a un dominio propio con TLS gestionado aparte — Funnel es la solución mínima suficiente por ahora, no necesariamente la definitiva a largo plazo.

## ADR-037: Overlay de permiso GPS con falso positivo — `probeGeolocationPermission()` sustituye a la Permissions API, encallada en el WebView real de Android

- **Fecha**: 2026-08-05
- **Estado**: Aceptada
- **Contexto**: El usuario reportó que el overlay "debes dar permiso" saltaba en el cockpit pese a que el permiso de ubicación ya estaba concedido — comportamiento ya anotado como sospechoso, pero sin investigar, en ADR-035 (grupo 8.2: "el overlay de permiso GPS parecía 'colgado'"). Diagnóstico real en el dispositivo de pruebas (Realme `75fe536b`): `adb shell dumpsys package com.motoroutes.app` confirmaba `ACCESS_FINE_LOCATION: granted=true` a nivel de SO, mientras que `navigator.permissions.query({name:'geolocation'})` (el mecanismo que usaba `checkPermissions()` desde su introducción — ver el test de regresión ya existente sobre el crash real de `RecordingService.kt` sin permiso) seguía devolviendo `'prompt'` de forma indefinida — confirmado inyectando un toast de diagnóstico temporal y capturando pantalla por `adb exec-out screencap`, tras comprobar que el propio proceso satura `logcat` con logging JNI en modo verbose (`LOGS OVER PROC QUOTA... DROPPED`), inutilizando esa vía de diagnóstico. Es un comportamiento conocido de los WebView de Android: la Permissions API para geolocalización refleja un estado interno del propio WebView (ligado a `onGeolocationPermissionsShowPrompt`), no el permiso real del sistema operativo.
- **Decisión**:
  1. `checkPermissions()`/`requestPermissions()` de `createBrowserGpsProvider` (`cockpit-browser-gps.service.ts`) pasan a compartir `probeGeolocationPermission()`: piden una localización real con `getCurrentPosition({ timeout: 8000 })` y solo tratan `error.code === PERMISSION_DENIED` como permiso denegado de verdad — `TIMEOUT`/`POSITION_UNAVAILABLE` (sin señal todavía) ya no se confunden con falta de permiso. 8s de techo porque una localización de red (sin `enableHighAccuracy`) suele resolver en 1-3s con datos/WiFi; cubre el caso sin ninguna de las dos sin ser percibido como colgado.
  2. **No se bloquea el primer render con esta comprobación** — primer intento de la sesión (esperar `checkGpsPermission()` antes de `render()` en `initAndRender()`) se revirtió tras comprobar que rompía `cockpit.cy.ts`/`cockpit-mark-stop.cy.ts` en Cypress (Electron headless no resuelve geolocalización real sin stub, así que el render quedaba bloqueado hasta el timeout) — el mismo riesgo aplica en producción real con señal lenta: dejar el cockpit entero en blanco al abrir la app es peor que el problema que se intentaba arreglar.
  3. `handleStartStop()` usa `hasGpsPermission` en caché (poblado en segundo plano al abrir la app, sin bloquear) como camino rápido, y repite el sondeo real justo antes de decidir si esa caché aún no ha resuelto (`startIfPermitted()`) — elimina la condición de carrera original (pulsar "Iniciar" antes de que la comprobación de fondo resuelva mostraba el overlay con el permiso ya concedido) sin arriesgar el crash nativo documentado (`RecordingService.kt` con `@SuppressLint("MissingPermission")`, sin guarda propia) de arrancar `startRecording()` sin saber de verdad si hay permiso.
  4. Nuevo comando Cypress compartido `stubGpsPermissionGranted` (`cypress/support/commands.ts`), aplicado en `cockpit.cy.ts` y añadido al `stubGeolocation` ya existente de `cockpit-mark-stop.cy.ts` — mismo motivo por el que ese spec ya stubeaba `watchPosition` (Electron headless no puede dar una localización real), extendido ahora a `getCurrentPosition`.
- **Alternativas consideradas**: (1) Comando Tauri nativo (Kotlin/Rust) que consulte `ContextCompat.checkSelfPermission` directamente — la señal más correcta en teoría, descartada por alcance: requiere tocar la capa nativa Android para un bug que ya tiene arreglo suficiente en JS; queda como mejora futura si `probeGeolocationPermission()` demostrara ser insuficiente. (2) Valor inicial optimista (`hasGpsPermission: true` por defecto) en vez de `false` — descartada, reintroduce el escenario de crash real ya documentado (permiso realmente revocado, p. ej. tras reinstalar el APK) sin la comprobación de fondo todavía resuelta. (3) Bloquear el render inicial con la comprobación — descartada, ver punto 2 de la Decisión.
- **Consecuencias**: "Iniciar ruta" ya no es instantáneo en todos los casos — si la caché de fondo no ha resuelto todavía (apertura de la app seguida de un tap muy rápido), hay una espera real (típicamente 1-3s, hasta 8s en el peor caso) antes de arrancar la grabación o mostrar el overlay. Cualquier spec Cypress nuevo que pulse el botón de inicio del cockpit debe usar `stubGpsPermissionGranted` (o extender su propio stub de geolocalización, como ya hace `cockpit-mark-stop.cy.ts`), o quedará sujeto al mismo bloqueo de 8s que rompió `cockpit.cy.ts` en esta sesión. Verificado en dispositivo real (build local instalada por USB, verificación de hash de bundle + CSP antes de instalar, arranque limpio con proceso matado de verdad): arranca en grabación sin overlay. PR #95 → `master`, release `v0.1.2`.

## ADR-038: `confirmacion-email-usuarios` — login exige email verificado, envío vía Resend sin SDK, dominio propio verificado tras fallo silencioso del sandbox

- **Fecha**: 2026-08-06
- **Estado**: Aceptada
- **Contexto**: Ver [[confirmacion-email-usuarios]] (`openspec/changes/confirmacion-email-usuarios/`). El registro/login de [[ADR-034]] ya funcionaba, pero cualquiera podía crear una cuenta con un email que no controla. Antes de proponer nada se investigó `apps/api/internal/auth/` y se confirmó que la mayor parte de auth ya existía (spec `user-auth`) — lo único que faltaba de verdad era la confirmación de email en sí.
- **Decisión**:
  1. **El login pasa a rechazar cuentas con `email_verified = false`** (403, mensaje distinto del de credenciales incorrectas) — **BREAKING** respecto al comportamiento previo, confirmado explícitamente con el usuario antes de escribir la spec (se ofrecieron ambas opciones: bloquear login o verificación puramente informativa).
  2. **El enlace de confirmación es un `GET` servido directamente por `apps/api`** (`GET /api/auth/verify-email/confirm?token=...`, responde HTML mínimo), no un `POST` — un email solo puede disparar una acción sin JavaScript mediante un enlace clicable, y no hay frontend todavía para esta spec (alcance ya acotado a "solo backend" en la sesión de propuesta). Mitigación del riesgo de prefetch por escáneres de email: el token es de un solo uso, un consumo accidental solo obliga a pedir un reenvío.
  3. **Token de verificación: `crypto/rand` (256 bits) + hash `sha256`, no `bcrypt`** — a diferencia de una contraseña (baja entropía, necesita hash lento), un token ya de alta entropía no necesita encarecer la búsqueda; solo se persiste el hash, nunca el token en claro.
  4. **Envío vía la API REST de Resend con `net/http` estándar, sin el SDK `resend-go`** — la superficie usada (un `POST` JSON con un header) no justifica una dependencia nueva, mismo criterio que cualquier otra decisión de dependencias mínimas del proyecto.
  5. **Rate limiting del endpoint de solicitud reutilizando `LoginRateLimiter`** (`ratelimit.go`) — ya era genérico por clave `string` pese a su nombre; se instancia una segunda vez con límites propios en vez de duplicar la lógica de ventana deslizante. Rename pendiente anotado como deuda menor, no bloqueante.
  6. **Registro dispara el primer envío de verificación best-effort**: un fallo de envío no impide crear la cuenta (el usuario puede pedir un reenvío) — pero sí queda logueado server-side (nunca al cliente, nunca el token en claro) para poder diagnosticarlo, corregido durante la propia verificación de este cambio tras detectar que se descartaba en silencio.
- **Tres gaps reales encontrados verificando contra Resend de verdad, ninguno detectable sin un proveedor externo real**:
  1. **`debian:trixie-slim` (etapa runtime del `Dockerfile` de `apps/api`) no traía `ca-certificates`** — cualquier llamada HTTPS saliente nueva fallaba con `x509: certificate signed by unknown authority`. Nunca hizo falta hasta ahora porque la única dependencia externa era Postgres, sin TLS en este despliegue. Corregido instalando el paquete en la etapa runtime.
  2. **Los fallos de envío se descartaban en silencio** (`_ = sender.Send(...)`) pese a que el propio `design.md` de la propuesta ya prometía loguearlos como mitigación — corregido añadiendo `log.Printf` en los tres puntos de fallo posibles de `issueAndSendVerificationToken`.
  3. **El remitente sandbox de Resend (`onboarding@resend.dev`) solo entrega de verdad una vez** (o un número de envíos de prueba muy limitado — coincide con las cabeceras `x-resend-daily-quota`/`x-resend-monthly-quota` observadas) — a partir de ahí, Resend acepta la petición con `200` (por eso nuestro manejo de errores, que solo comprueba el status HTTP síncrono, no lo detectaba) pero la entrega real falla de forma asíncrona por `Domain is not verified`. Es una limitación global del ecosistema de email (SPF/DKIM/DMARC), no específica de Resend — cualquier proveedor serio (SendGrid, Mailgun, Postmark, SES) exige lo mismo. **Resuelto comprando un dominio propio** (`motor-routes.com`, registrado en Cloudflare Registrar — precio de coste, sin margen), verificándolo en Resend (registros DNS añadidos en Cloudflare) y actualizando `RESEND_FROM_ADDRESS` a `no-reply@motor-routes.com` en `infra/docker/.env.prod` del servidor.
- **Despliegue real verificado end-to-end, no solo local**: local (`docker compose up --build`, registro real con `gonzalocarmenado@gmail.com`, email recibido, token extraído del enlace y confirmado contra `localhost:8080` — el enlace real `https://localhost` no es alcanzable en local, limitación esperada y documentada en `.env.example`) y **producción real, desplegado desde `feature/confirmacion-email-usuarios` sin fusionar** (mismo patrón que [[ADR-034]]: imagen anterior etiquetada `docker-api:pre-confirmacion-email-usuarios` para rollback, migración `0003` aplicada sola). En producción, con el dominio ya verificado: registro real → email recibido de verdad → enlace de confirmación pulsado **desde fuera del tailnet** (`https://debian.taildf3dab.ts.net`, Tailscale Funnel de [[ADR-036]]) → login pasa de 403 a 200 → token reutilizado se rechaza (400). Cuenta de prueba borrada de la base de datos de producción tras verificar (`DELETE FROM users`, cascada a `email_verification_tokens`), confirmado `count(*) = 0` en ambas tablas.
- **Alternativas consideradas**: (1) Verificación puramente informativa sin bloquear login — descartada explícitamente por el usuario, prioriza evitar cuentas fantasma. (2) SMTP propio en el servidor doméstico — descartado dos veces en esta sesión (ya en la decisión original de "Resend, no SMTP propio", y de nuevo cuando el usuario preguntó si podía montarlo él mismo): reputación de IP residencial, bloqueo habitual del puerto 25 por el ISP, DNS inverso no personalizable — y de todas formas seguiría exigiendo un dominio propio, no evita el problema que lo originó. (3) Relay vía Gmail SMTP con contraseña de aplicación — descartado por cambiar de arquitectura (API REST → SMTP) y por los límites de envío de una cuenta personal (500/día), evaluado pero no necesario una vez decidido comprar el dominio. (4) SDK oficial `resend-go` — descartado, ver punto 4 de la Decisión.
- **Consecuencias**: `config.Load()` exige ahora `RESEND_API_KEY`, `RESEND_FROM_ADDRESS` y `PUBLIC_API_BASE_URL` (esta última validada como `https://` — mismo tipo de comprobación que ADR-036 ya lamentó no tener desde el principio) — cualquier entorno que arranque `apps/api` sin definirlas falla explícitamente al inicio, en vez de arrancar con un envío de email roto en silencio. Las cuentas creadas antes de esta migración quedan con `email_verified = false` por defecto (columna nueva, `DEFAULT false`) — sin backfill especial porque hoy el único usuario real es el propio desarrollador; un proyecto con usuarios reales antes de un cambio así necesitaría un plan de comunicación explícito, fuera de alcance aquí. Producción depende ahora de un dominio real (`motor-routes.com`) verificado en Resend — si se pierde el control del dominio o expira sin renovar, el envío de verificación dejará de entregar (mismo tipo de dependencia operativa ya aceptado con Tailscale Funnel en ADR-036).

## ADR-039: `reset-contrasena` — página web real con el estilo de la app, token de 1h, cuenta derivada solo del token

- **Fecha**: 2026-08-06
- **Estado**: Aceptada
- **Contexto**: Ver [[reset-contrasena]] (`openspec/changes/reset-contrasena/`). Continuación directa de [[ADR-038]] — quedó explícitamente aparcado como "spec aparte más adelante". A diferencia de la confirmación de email (un enlace basta), un reset de contraseña necesita un formulario real para escribir la contraseña nueva — el usuario pidió explícitamente que esta página ya llevara el diseño "Asfalto Nocturno" de la app, no HTML plano, y que se garantizaran tres propiedades de seguridad concretas antes de implementar: caducidad del enlace, que no se pueda cambiar la contraseña de otra cuenta, y que el enlace no lleve email/username, solo un token opaco.
- **Decisión**:
  1. **Token de reset caduca en 1 hora** (`resetTokenTTL`), más corto que el de verificación de email (24h, ADR-038) — un token de reset da control total de la cuenta si se filtra, riesgo mayor que uno de verificación.
  2. **La cuenta afectada se determina exclusivamente por el token**, nunca por ningún campo del formulario — `ResetPasswordConfirmHandler` solo lee `token`/`password`/`password_confirmation` de `r.PostFormValue`, el `user_id` viene siempre de `PasswordResetTokenStore.FindByHash`. Verificado con un test dedicado que intenta colar un `email`/`user_id` de otra cuenta en el `POST`: solo cambia la cuenta dueña del token real.
  3. **El enlace enviado por email lleva únicamente el token** — sin email ni ningún identificador de cuenta en la URL, verificado con un test que inspecciona el HTML del email enviado.
  4. **La página de confirmación es HTML + `<form>` estándar, sin JavaScript**, servida directamente por `apps/api` (mismo criterio que la confirmación de email — no hay frontend para esto). El `POST` reprocesa y vuelve a renderizar el formulario con el motivo si algo falla (contraseñas no coinciden, política débil, token inválido).
  5. **Estilo "Asfalto Nocturno" embebido como CSS inline en Go, sin importar `tokens.css`** — `apps/api`/`apps/mobile` son paquetes de build independientes sin pipeline compartido; los valores `oklch()` de color se copian como constantes en `reset_password_page.go`, con comentario apuntando a la fuente de verdad. Sin auto-hospedar los `.woff2` reales — *fallback stacks* del sistema (`"Roboto Slab", "Georgia", serif` / `"Barlow", "Segoe UI", sans-serif`), decisión explícita del usuario de mantenerlo simple.
  6. **Completar un reset también verifica el email si no lo estaba** — completar el reset ya demuestra control del buzón, mismo nivel de prueba que confirmar un email de verificación.
  7. **Rename de `generateVerificationToken`/`hashVerificationToken` a `generateOneTimeToken`/`hashOneTimeToken`** (`verification_token.go`) — a diferencia del rename pendiente de `LoginRateLimiter` (ADR-038, dejado como deuda por ser incómodo con un único segundo consumidor), aquí el rename es barato (dos funciones puras) y este mismo cambio introduce el segundo consumidor real (token de reset), así que se hizo en el momento en vez de acumular más deuda.
  8. **Tabla y tipos propios (`password_reset_tokens`, `PasswordResetTokenStore`)**, no se reutiliza `email_verification_tokens` — un token de reset y uno de verificación no deben ser intercambiables.
- **Nuevo método en `UserStore`**: `UpdatePasswordHash` — no existía, necesario para sustituir el hash de contraseña; implementado en `PostgresUserStore` y el `fakeUserStore` de test, mismo patrón que `MarkEmailVerified`.
- **Gap real encontrado verificando en local, no en tests**: `infra/docker/.env` seguía con el remitente sandbox `onboarding@resend.dev` de antes de verificar el dominio (ADR-038) — ya había agotado su envío de prueba único, así que el primer intento de reset local dio el mismo error `Domain is not verified` que motivó comprar `motor-routes.com`. Corregido actualizando el `.env` local al mismo remitente ya verificado que usa producción.
- **Verificación real end-to-end en dos entornos**: local (formulario visto y confirmado visualmente por el usuario en un navegador real — fondo oscuro, panel, botón ámbar — enviado con una contraseña real, login con la contraseña anterior rechazado y con la nueva aceptado) y producción real, desplegada sin fusionar desde `feature/reset-contrasena` (imagen anterior etiquetada `docker-api:pre-reset-contrasena`, migración `0004` aplicada sola). En producción: registro real → solicitud de reset → email recibido → formulario completado por el usuario (primer intento con una contraseña de 6 caracteres rechazado de verdad server-side, confirmando la política mínima en producción) → login con la contraseña nueva desde fuera del tailnet. Cuenta de prueba borrada después, `count(*) = 0` en `users` y `password_reset_tokens`.
- **Alternativas consideradas**: (1) Reutilizar `email_verification_tokens` con un campo de "tipo" — descartada, dos tablas separadas es más simple y evita cualquier comprobación adicional de tipo en cada handler (ver punto 8). (2) Invalidar sesiones JWT ya emitidas al completar un reset — descartada, el esquema `TokenIssuer` es completamente stateless sin lista de revocación; añadir eso es un cambio de arquitectura mayor, no justificado solo por esta spec (documentado como Non-Goal en `design.md`). (3) Auto-hospedar los ficheros `.woff2` reales para la página — descartada por complejidad no justificada para una única página, confirmado con el usuario ("nada complejo").
- **Consecuencias**: una sesión JWT abierta antes de un reset sigue siendo válida hasta que expira (máx. 24h) — si el motivo del reset es que alguien más conoce la contraseña antigua y ya tiene sesión activa, esa sesión no se revoca; aceptado explícitamente, ver alternativa (2). El estilo de la página vive duplicado (valores de color copiados en Go) — si la paleta de `tokens.css` cambia, hay que actualizar `reset_password_page.go` a mano, sin mecanismo de sincronización automático. Precedente sentado para la próxima spec de frontend: estilizar el resto de páginas de `apps/api` (verificación de email, que sigue en HTML plano) con el mismo criterio.

## ADR-040: `rutas-en-la-nube` — upsert nunca sobrescribe silenciosamente el `id` de otra cuenta, límite de puntos concreto, e ids de puntos/paradas de la nube sintetizados solo para presentación

- **Fecha**: 2026-08-07
- **Estado**: Aceptada
- **Contexto**: Ver [[rutas-en-la-nube]] (`openspec/changes/rutas-en-la-nube/`). Primer cambio que persiste datos de usuario propios (no solo la cuenta) en `apps/api`: rutas grabadas en `apps/mobile`, subidas a la cuenta autenticada. `design.md` dejaba sin resolver el valor concreto del límite de puntos (Open Question) y no detallaba el mecanismo exacto para el Goal "aislamiento estricto por cuenta, ninguna ruta de otro usuario alcanzable ni adivinando un id" en el caso concreto de `POST /api/routes` (upsert), solo lo cubría explícitamente para las lecturas (`GET`).
- **Decisión**:
  1. **`PostgresRouteStore.Upsert` nunca sobrescribe un `id` que ya pertenece a otra cuenta, ni siquiera en silencio.** El `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE routes.user_id = $2` deja la fila intacta si el propietario no coincide (0 filas afectadas); el store comprueba `RowsAffected() == 0` tras el intento y devuelve `ErrRouteOwnedByAnotherUser` en vez de continuar como si hubiera insertado o actualizado — sin este chequeo, dos cuentas que generaran (por casualidad o a propósito) el mismo UUID de ruta podrían pisarse los datos entre sí sin ningún error visible. Verificado con un test dedicado (`TestPostgresRouteStore_UpsertNeverOverwritesAnotherUsersRoute`) que confirma que la ruta de la víctima queda intacta.
  2. **`MaxPoints = 50000`** (orden de magnitud: un trayecto de un día entero a 1 punto/seg) resuelve la Open Question de `design.md`. El handler traduce `ErrTooManyPoints` a 400.
  3. **Inserción de puntos/paradas en bloques de 500 filas por `INSERT` multi-valor**, no `unnest()`/arrays ni un único `INSERT` gigante — con `MaxPoints` puntos a 6 parámetros cada uno, un solo `INSERT` se acercaría al límite de 65535 parámetros por *statement* de PostgreSQL. Trocear en bloques de tamaño fijo evita ese límite sin necesitar tipos array de pgx.
  4. **Puntos/paradas de una ruta exclusiva de la nube se adaptan a `RoutePoint`/`RouteStop` con `id`/`routeId` sintetizados (`crypto.randomUUID()`) solo en memoria**, nunca persistidos ni reenviados al servidor (`cloudRouteDetailToLocal`) — permite reutilizar el mismo `route-detail.element.ts` (mapa, timeline) sin una rama de renderizado paralela para datos de la nube.
- **Alternativas consideradas**: (1) Servidor genera el id de la ruta y lo devuelve al cliente — descartada en `design.md` (Decisión 1), confirmada al implementar: el UUID del cliente ya es único de sobra y evita una tabla de mapeo `local_id ↔ server_id`. (2) `unnest()` con arrays de pgx para la inserción masiva de puntos — descartado por la complejidad de tipado de arrays con nulos (paradas con `end_time`/`stop_category_id` opcionales) frente al enfoque más simple de trocear en bloques.
- **Consecuencias**: si dos cuentas distintas generan por pura coincidencia el mismo UUID de ruta (probabilidad despreciable con `crypto.randomUUID()`), la segunda cuenta en subir recibe un 409 en vez de una ruta — comportamiento correcto pero sin mensaje específico para ese caso tan raro, aceptado por su rareza. El límite de 50 000 puntos es una constante, no un valor configurable por variable de entorno — subirlo en el futuro es un cambio de una línea, no de diseño.

## ADR-041: `hardening-despliegue-servidor` — contenedor no-root, script de despliegue versionado y documentación de MinIO

- **Fecha**: 2026-08-07
- **Estado**: Aceptada
- **Contexto**: La auditoría de seguridad del servidor de producción (2026-08-07, resumida en `docs/informe-tecnico-seguridad.md`) encontró tres hallazgos: (1) el contenedor de `apps/api` ejecutaba el proceso como `root`; (2) el servicio **MinIO** corría en el servidor sin ningún ADR que lo documentara (provisión anticipada para blob storage, sin código que lo use todavía); (3) el servidor no se había redesplegado tras el merge de `rutas-en-la-nube` — faltaba la migración `0005` y `/api/routes` devolvía `404`, patrón ya vivido en [[ADR-036]] (despliegue manual que se olvida).
- **Decisión**:
  1. **El contenedor de `apps/api` ejecuta el proceso como usuario no-root (`appuser`)** definido en la propia imagen (`apps/api/Dockerfile`, etapa runtime). El servicio escucha en `:8080` (>1024) y no persiste nada en el contenedor (Postgres es externo por loopback), así que ningún privilegio de root es necesario.
  2. **Nuevo script versionado `scripts/deploy-prod.sh`** que automatiza el despliegue: `ssh` por Tailscale → `git pull --ff-only origin master` → `docker compose -f docker-compose.prod.yml up -d --build` → verificación de salud (`curl` a la URL pública). Los datos de conexión (`SERVER_HOST`, `SERVER_USER`, `PUBLIC_API_URL`) **no se versionan** (repo público, ADR-033/035): se resuelven por orden desde variables de entorno o desde `scripts/.env.deploy.local` (no versionado, gitignored).
  3. **MinIO queda documentado**: es provisión anticipada para el blob storage futuro de fotos (ADR-034 lo menciona como objetivo pendiente). Hoy corre como servicio `systemd` (`minio.service`, usuario `minio-user`, escuchando solo en loopback `127.0.0.1:9000/9001`) y **no tiene ningún código consumidor**. Su uso real requiere un cambio con su propia ADR y cambio OpenSpec.
- **Alternativas consideradas**: (1) Quitar MinIO del servidor — rechazada: el usuario confirmó en una auditoría previa que es provisión intencionada; eliminarlo sería destructivo y prematuro mientras el blob storage sigue pendiente. (2) Automatizar el despliegue vía webhook/GitHub Action con `ssh` — rechazada, contradice la ceremonia manual por defecto de ADR-029/030/036; el script sigue siendo una invocación manual, solo que reproducible. (3) Script PowerShell nativo — rechazado: los precedentes del proyecto usan Bash y el servidor es Debian.
- **Consecuencias**: el contenedor deja de poder escribir donde antes podía (no aplica: sin volúmenes de escritura); cualquier despliegue futuro debe hacerse con el script o el equivalente manual documentado, y la imagen no-root exige revisar permisos si algún día se añaden volúmenes. MinIO queda como deuda documentada: si no se usa en un plazo razonable, reevaluar si sigue mereciendo la pena mantenerlo encendido.

## ADR-042: `almacenamiento-fotos-backend` — primer uso real de MinIO, cifrado de aplicación AES-256-GCM, nunca URLs directas al almacenamiento

- **Fecha**: 2026-08-07
- **Estado**: Aceptada
- **Contexto**: MinIO llevaba desde [[ADR-041]] documentado como "provisión anticipada sin consumidor". `rutas-en-la-nube` ([[ADR-040]]) subió solo metadatos/puntos/paradas de una ruta, dejando explícitamente las fotos fuera de alcance (dos `// TODO` en `route-detail.element.ts`) hasta que existiera blob storage. Este cambio le da a MinIO su primer uso real: subir/listar/descargar/borrar fotos de una ruta vía API — solo backend, verificado con `curl`.
- **Decisión**:
  1. **Cliente `github.com/minio/minio-go/v7`** (SDK oficial de MinIO, S3-compatible) envuelto en una interfaz `BlobStore` propia — el resto del código nunca importa el SDK directamente, mismo aislamiento que `routes.Store` sobre `pgx`.
  2. **Cifrado de aplicación, no de MinIO**: cada foto se cifra completa en memoria con AES-256-GCM (`crypto/aes`/`crypto/cipher`, librería estándar de Go) antes de subirla, y se descifra al servirla. La clave (`PHOTO_ENCRYPTION_KEY`, 32 bytes codificados en base64) vive únicamente en `apps/api` — nunca en MinIO ni en su almacenamiento. Se descartó el cifrado nativo SSE-S3 de MinIO precisamente porque ahí la clave y los datos cifrados conviven en el mismo sistema; el objetivo es que un compromiso de MinIO solo (credenciales o disco) no baste para reconstruir una foto.
  3. **Ninguna foto se sirve por URL directa de MinIO ni por presigned URL**: toda descarga pasa por `GET /api/routes/{id}/photos/{photoId}`, que descifra y devuelve los bytes tras `RequireAuth` + comprobación de que la ruta es del usuario — cada petición vuelve a pasar por el control de acceso, sin ninguna URL que siga funcionando tras filtrarse.
  4. **`route_photos`**: mismo patrón que `routes`/`route_points` — `id` UUID cliente-generado, `route_id` con `ON DELETE CASCADE`, propiedad resuelta siempre vía `route_id` contra `routes.user_id` (nunca duplicada en la tabla de fotos).
  5. **Límites server-side nuevos**: 100 fotos/ruta (ya existía solo en el cliente) y 15MB/foto, con el body de la petición acotado con `http.MaxBytesReader` antes de leer el fichero completo.
- **Alternativas consideradas**: (1) `aws-sdk-go-v2` con el cliente S3 — descartado, mucho más SDK del necesario para un bucket y cuatro operaciones; `minio-go` es el cliente de referencia del propio proyecto MinIO. (2) SSE-S3 nativo de MinIO — descartado, ver punto 2 de la Decisión. (3) Presigned URLs con TTL corto — descartadas, ver punto 3. (4) Cifrado en streaming — descartado, complejidad innecesaria para fotos de cámara de móvil (unos pocos MB, se cifran/descifran completas en memoria sin problema real de rendimiento).
- **Consecuencias**: **perder `PHOTO_ENCRYPTION_KEY` hace irrecuperables todas las fotos ya subidas, para siempre** — sin mecanismo de rotación de clave en este cambio, mismo tipo de dependencia operativa ya aceptada con el dominio de Resend ([[ADR-038]]). Borrar una foto borra primero en MinIO y solo si tiene éxito borra la fila de Postgres, para no dejar objetos huérfanos invisibles en MinIO. Sin borrado en cascada al borrar una ruta o una cuenta — ninguno de esos dos endpoints existe todavía en `apps/api`, así que no hay nada que limpiar hasta que existan (deuda documentada, no un gap silencioso). Nuevo servicio `minio` en CI (`ci.yml`) y en `docker-compose.yml` local — mismo criterio que `dbtest.Connect` contra Postgres real: un fake de `BlobStore` no detectaría problemas reales de configuración/protocolo con MinIO.

## ADR-043: `subida-fotos-mobile` — `PublicCORS` debe declarar cada método HTTP nuevo explícitamente, no solo cuando falla en `curl`

- **Fecha**: 2026-08-09
- **Estado**: Aceptada
- **Contexto**: `subida-fotos-mobile` cierra los dos `// TODO` de `route-cloud-sync` subiendo/borrando de verdad el archivo de una foto contra el backend de `almacenamiento-fotos-backend` ([[ADR-042]]). La subida (`POST`) y el borrado (`DELETE`) pasaron 963/963 Vitest y 54/54 Cypress (backend real) sin problema. Verificando en un dispositivo Android real (WebView real, no el navegador de Cypress) con una foto de cámara real, el borrado sincronizado nunca llegaba al servidor — la foto desaparecía localmente pero quedaba huérfana en remoto, indefinidamente.
- **Decisión**: Añadir `DELETE` a `Access-Control-Allow-Methods` en `httpmw.PublicCORS` (`apps/api/internal/httpmw/cors.go`), que desde su creación ([[ADR-035]]) solo declaraba `"GET, POST, OPTIONS"` — nunca se actualizó al introducir el primer endpoint `DELETE` real de la API. El propio comentario de `PublicCORS` queda actualizado documentando que esta es la **tercera vez** que este middleware se queda corto al añadir una capacidad nueva (primero `GET` sin preflight, después `POST`+`OPTIONS` de auth, ahora `DELETE`) — la lección no es "arreglar este caso", es que **cualquier endpoint nuevo con un método HTTP que `PublicCORS` no declare todavía se rompe en silencio en cualquier navegador real que aplique CORS con rigor**, sin que ningún test hasta ahora lo hubiera detectado.
- **Cómo se diagnosticó**: `curl` directo (sin preflight) y los 54/54 de Cypress (su navegador no aplica CORS con el mismo rigor que un WebView Android real — `chromeWebSecurity` u otra relajación equivalente) confirmaban el `DELETE` funcionando. Solo un `fetch()` crudo vía Chrome DevTools Protocol contra el WebView real del dispositivo reveló `TypeError: Failed to fetch` en `DELETE`/`PUT` mientras `GET`/`POST` funcionaban — aislando el problema al preflight antes de tocar ni una línea del código de la app.
- **Alternativas consideradas**: (1) Dejarlo como deuda y arreglarlo en un cambio aparte — descartado, es una línea, con test de regresión, y bloqueaba directamente el propio escenario que este cambio dice implementar (borrado sincronizado). (2) Un CORS más permisivo con `Access-Control-Allow-Methods: "*"` — descartado, más difícil de auditar qué métodos están realmente pensados para consumirse cross-origin, y no evita el problema de fondo (seguiría haciendo falta acordarse de revisar `PublicCORS` al añadir un método nuevo).
- **Consecuencias**: Nuevo test de regresión en `cors_test.go` que exige `DELETE` en la respuesta al preflight de `/api/routes/{id}/photos/{photoId}`. **Recordatorio para cualquier cambio futuro que añada un endpoint con un método HTTP no usado hasta ahora en la API** (`PUT`, `PATCH`, etc.): verificar `Access-Control-Allow-Methods` en `PublicCORS` explícitamente, no asumir que `curl`/Cypress lo habrían detectado — solo un WebView/navegador real con CORS estricto lo revela.

## ADR-044: `despliegue-automatico-backend` — despliegue automático vía GitHub Actions, revirtiendo deliberadamente ADR-033/036/041

- **Fecha**: 2026-08-09
- **Estado**: Aceptada
- **Contexto**: El despliegue de `apps/api` era 100% manual (`scripts/deploy-prod.sh` por SSH) desde su creación en [[ADR-041]]. La automatización se planteó y descartó explícitamente tres veces — [[ADR-033]], [[ADR-036]], [[ADR-041]] — por la filosofía de "ceremonia manual por defecto" del proyecto ([[ADR-029]]/[[ADR-030]]), quedando siempre anotada como deuda pendiente para "un cambio futuro dedicado". Este es ese cambio: decidido deliberadamente con el usuario tras pedirle explícitamente que revisara esas tres ADRs antes de proceder, con dos preocupaciones de seguridad explícitas del usuario resueltas en el diseño — exposición del repo público, y que solo él pueda autorizar un despliegue real.
- **Decisión**:
  1. **Nuevo job `deploy-prod` en `ci.yml`**, mismo trigger de tag `v*` que `build-and-release`, enganchado a un GitHub Environment `prod` con **Required reviewers = solo el propietario del repo** — cualquier ejecución queda pausada, sin acceso a los secrets del Environment, hasta su aprobación explícita. Mitiga que el repo tenga un segundo colaborador con permiso de `push` que podría empujar un tag hoy.
  2. **Autenticación de red**: `tailscale/github-action` (fijada a un SHA de commit) con un **cliente OAuth de Tailscale** (no un auth-key de larga duración), restringido a un tag dedicado `tag:ci-deploy` con scope `Devices Core` + **`Keys → Auth Keys`** (ambos con Write) — el segundo, no documentado en el diseño inicial, resultó indispensable: sin él, `tailscale up` falla con `403`.
  3. **Autenticación/restricción de comando — rediseñada en mitad de la implementación**: el plan original (clave SSH dedicada con `command=` forzado en `authorized_keys`) se descartó al verificar en el servidor real que **no hay `sshd` tradicional** — todo el acceso SSH pasa por Tailscale SSH, que no tiene equivalente al `command=` forzado de OpenSSH. Solución real: un usuario de sistema `ci-deploy` (sin `sudo`, grupo `docker`) cuya **shell de login** es el nuevo script versionado `scripts/deploy-local.sh` — cualquier comando pedido por el cliente SSH se ignora, solo se ejecuta ese script fijo. Como el checkout real vive en `/home/gonzalo/moto-routes` (no en el `$HOME` de `ci-deploy`), el acceso se acota con **ACLs POSIX** (`setfacl`): tránsito (`--x`, sin listar) sobre `/home/gonzalo`, lectura/escritura solo sobre `/home/gonzalo/moto-routes` — el resto del `$HOME` de `gonzalo` permanece inaccesible.
  4. **Tag dedicado del servidor (`tag:prod-server`)**: el primer intento de política ACL de Tailscale SSH apuntaba a `tag:ingress`, asumiendo que era el tag del servidor — error real: pertenecía a los nodos internos de infraestructura de Tailscale Funnel, no a `debian`, que no llevaba ningún tag. Corregido creando `tag:prod-server` dedicado, asignado desde el panel (no por SSH, para no resetear otros flags activos del nodo), con una regla `ssh` adicional que preserva explícitamente el acceso humano de `gonzalo` (que de otro modo se habría roto al dejar de contar como `autogroup:self` tras etiquetar el servidor).
  5. **Host real nunca hardcodeado en un fichero versionado** (ADR-035): `deploy-local.sh` resuelve su propia IP de Tailscale en tiempo de ejecución (`tailscale ip -4`); `ci.yml` la toma de un secret nuevo del Environment `prod` (`PROD_SERVER_HOST`) — un hardcodeo inicial de la IP se detectó y corrigió antes de abrir la PR.
- **Cómo se verificó**: extremo a extremo, con una release real (`v0.1.5`), no simulado. Costó **cuatro intentos reales** antes de un despliegue exitoso, cada uno revelando un bug real distinto (por este orden): falta el scope `Auth Keys` del cliente OAuth → falta el tag en el selector de ese scope concreto → `dst` de la regla `ssh` apunta a un tag equivocado (`tag:ingress`) → el commit del script se hizo desde Windows y perdió el bit de ejecución en git (`100644`), rompiendo la shell de login en cada `git pull` (fix dedicado, PR #113). El quinto intento completó con éxito: `git pull` + `docker compose up -d --build` + recreación real del contenedor + verificación de salud en `200`, con host y credenciales OAuth enmascarados en el log (`***`).
- **Alternativas consideradas**: ver el detalle completo, incluidas las descartadas explícitamente por el usuario (auth-key de larga duración, clave SSH sin restricción de comando, sin gate de aprobación), en `openspec/changes/archive/.../design.md` de este cambio.
- **Consecuencias**: el proyecto tiene ahora dos superficies de despliegue automatizado nuevas que auditar si algo falla — el Environment `prod` de GitHub y la política ACL de Tailscale (`tag:ci-deploy`, `tag:prod-server`) — además del riesgo residual ya documentado y no resuelto por este cambio: `ci-deploy` no tiene `sudo`, pero pertenecer al grupo `docker` es en la práctica equivalente a `root` sobre el host (vector de escalada ampliamente documentado del socket de Docker). `scripts/deploy-prod.sh` no se toca y sigue siendo el path manual desde fuera del servidor. Cualquier cambio futuro a `scripts/deploy-local.sh` debe volver a fijar explícitamente el bit de ejecución en git si se edita desde una máquina Windows (`git update-index --chmod=+x`) — no es automático.

## ADR-045: Incidente real — Tailscale Funnel dejó de resolver públicamente tras asignar `tag:prod-server` en el panel (ADR-044), sin que ningún health-check lo detectara

- **Fecha**: 2026-08-11
- **Estado**: Aceptada
- **Contexto**: El usuario reportó que la app móvil (release `v0.1.5`) no podía crear una cuenta ("no se pudo crear la cuenta"), preguntando si la release no apuntaba bien al servidor. La hipótesis inicial (release/CSP/URL horneada mal) se descartó verificando el APK real descargado del Release (`unzip`+`grep`, mismo patrón que ADR-036): CSP y `VITE_API_BASE_URL` correctos (`https://debian.taildf3dab.ts.net`), y `curl` contra esa URL respondía `200` — parecía todo sano.
  **El diagnóstico real exigió descartar un falso positivo propio primero**: la máquina de desarrollo está en el mismo tailnet que el servidor, así que Tailscale intercepta localmente la resolución de `*.ts.net` (MagicDNS/NRPT de Windows) — cualquier `curl`/`nslookup`/`Resolve-DnsName` ejecutado desde ahí "funciona" aunque el registro DNS público esté caído, dando una falsa sensación de salud. Se conectó por Chrome DevTools Protocol al WebView real de la app en el móvil del usuario (mismo patrón que ADR-036/ADR-043) mientras intentaba registrarse: la petición fallaba con `net::ERR_NAME_NOT_RESOLVED` antes de llegar siquiera al servidor. Confirmado con una consulta DNS-over-HTTPS genuinamente externa (Google DoH, resuelta desde fuera de cualquier red del usuario) que `debian.taildf3dab.ts.net` devolvía `NXDOMAIN` real, no solo un problema del dispositivo.
- **Causa raíz**: `sudo tailscale funnel --bg ...` en el servidor reveló el error real: *"Funnel is enabled, but the list of allowed nodes in the tailnet policy file does not include the one you are using"*. La asignación de `tag:prod-server` desde el panel de Tailscale durante [[ADR-044]] (2026-08-09) dejó al nodo fuera de la lista de nodos autorizados para Funnel en la ACL — el proxy seguía sirviendo correctamente dentro del tailnet (por eso `tailscale funnel status` seguía diciendo `Funnel on`, y por eso todas las verificaciones dentro del tailnet parecían sanas), pero el registro DNS público dejó de publicarse. Nadie lo notó durante casi dos días porque ninguna verificación de este proyecto —ni las de esta sesión, hasta el punto de descartar el falso positivo— prueba la URL pública desde fuera del tailnet.
- **Decisión / resolución**: (1) el usuario re-aprobó el nodo para Funnel desde el panel de Tailscale (acción de cuenta, no delegable a este agente); (2) se repitió `sudo tailscale funnel --bg http://100.114.190.36:8080` en el servidor, esta vez con éxito; (3) verificado con el mismo DNS externo genuino (Google DoH) que `debian.taildf3dab.ts.net` vuelve a resolver a IPs públicas reales de Funnel (`176.58.90.0/24`, no la IP privada `100.x` del tailnet); (4) verificado extremo a extremo con un registro de cuenta real contra producción (`201 Created`), cuenta de prueba borrada después.
- **Alternativas consideradas**: No se investigó ni se aplicó ningún cambio de arquitectura — es un incidente operativo puntual de una ACL, no un problema de diseño del sistema (Funnel en sí sigue siendo la solución elegida en [[ADR-036]]).
- **Consecuencias**: **Gap real confirmado, no resuelto todavía**: ningún mecanismo de este proyecto verifica la resolución/salud pública de `apps/api` desde fuera del tailnet tras un despliegue o un cambio de ACL — todas las comprobaciones existentes (`ci.yml`, verificaciones manuales previas) se ejecutan desde dentro del tailnet o contra la IP privada, y por tanto no habrían detectado este fallo. Candidato claro para un cambio futuro: un health-check periódico o post-deploy que resuelva `PROD_API_BASE_URL`/el host de Funnel vía un DNS público real (no el del propio runner/tailnet) y haga un `curl` real, alertando si falla. **Lección operativa**: cualquier edición futura de la ACL de Tailscale desde el panel (tags, reglas SSH, etc.) debe ir seguida de una verificación explícita de que Funnel sigue publicando el DNS público — no basta con `tailscale funnel status` local, que no valida contra el servidor de control.

## ADR-047: `optimizar-bundle-produccion` — el APK "release" publicado en cada GitHub Release era en realidad un build debug, corregido reutilizando la firma de depuración de siempre

- **Fecha**: 2026-08-12
- **Estado**: Aceptada
- **Contexto**: Ver [[optimizar-bundle-produccion]] (`openspec/changes/optimizar-bundle-produccion/`). El usuario pidió compilar e instalar la app para revisar el sistema de iconos SVG recién archivado ([[ADR-046]]) y de paso observó que el APK pesaba ~170MB — pidió investigar si merecía la pena actualizar el JDK, revisar el estado del build web de producción, y si se podía reducir el tamaño del bundle de Tauri. La investigación encontró que el job `build-and-release` de `.github/workflows/ci.yml` llevaba compilando siempre con `pnpm tauri android build --target aarch64 --debug` — el "release" publicado nunca había activado minify/R8, `shrinkResources`, ni el `profile.release` ya bien afinado de `Cargo.toml` (`lto`, `strip`, `opt-level="s"`, `panic="abort"`). Esto **contradice el efecto esperado, aunque no la decisión en sí, de [[ADR-031]]**: esa ADR aceptó deliberadamente no gestionar un keystore de firma real ("sin firma de release real... descartada por ahora") — el efecto colateral no buscado fue que además nunca se compiló en buildType `release`, dos cosas independientes que quedaron acopladas sin necesidad.
- **Decisión**:
  1. **El buildType `release` de Android reutiliza el mismo `signingConfig` de `debug`** (efímero, generado por AGP en cada runner) — `apps/mobile/src-tauri/gen/android/app/build.gradle.kts` (trackeado en git, confirmado que no hace falta ningún mecanismo especial de Tauri para persistir el cambio: CI nunca ejecuta `tauri android init`, solo hace checkout del fichero ya committeado). **Sin keystore ni secreto nuevo** — mantiene intacta la parte de ADR-031 que rechazaba gestionar firma real, corrige solo el efecto colateral no buscado.
  2. **`isShrinkResources = true` añadido junto al `isMinifyEnabled = true`** ya existente en el mismo buildType.
  3. **CI quita `--debug` del comando de build** y ajusta el resto del pipeline a las rutas `release` (force-sync con `assembleUniversalRelease`, verificación y publicación del APK desde `apk/universal/release/`).
  4. **Sourcemaps de producción desactivados** (`sourcemap: false` en `vite.config.ts`) — no hay infraestructura de crash-reporting que los consuma; suponían ~65% del peso de `dist/`.
  5. **Quality gate nuevo en CI**: paso "Check APK size budget" que falla el job si el APK release supera un umbral (`MAX_APK_SIZE_MB`, bash simple sin dependencia nueva) — mismo patrón que el resto de gates del proyecto (cobertura, AC coverage).
  6. **Script nuevo de conveniencia local** `apps/mobile/scripts/install-android.sh`: detecta la ABI del dispositivo/emulador conectado vía `adb shell getprop ro.product.cpu.abi`, la mapea al `--target` correcto de Tauri, y compila+instala en un solo paso — sin capability/spec propia (tooling puro, sin comportamiento observable de la app).
- **Gap real encontrado durante `apply`**: el primer build release local empaquetó 8 ficheros `.map` huérfanos de builds anteriores a este cambio — el copiado de assets de `pnpm tauri android build` no borra ficheros que ya no existen en el `dist/` actual (mismo gotcha ya documentado en `memory/context.md` § Build Android, para el que ya existía el paso "Force-sync" en `ci.yml`; aquí se confirmó que también afecta al buildType release, y que `install-android.sh` necesitaba el mismo force-sync para no heredarlo en cada iteración local).
- **Verificación real**: TDD en `ci-workflow.spec.ts` (rojo confirmado antes de tocar `ci.yml`, 35/35 en verde después). Medido real: `.so` nativo de 148MB (debug) a 6.7MB (release); APK de ~170/305MB a **9MB**, igual en local que en un tag de prueba real (`v0.0.1-optimizar-bundle-test`, run de GitHub Actions `31582905618`, `Build & release Android APK` en verde en 18m44s) — Release y tag borrados tras confirmar (`gh release delete --cleanup-tag`). Instalación y funcionamiento (grabación GPS, mapa, fotos) confirmados por el usuario en dispositivo real (`75fe536b`) sobre el build minificado, sin necesitar ninguna regla `-keep` nueva en `proguard-rules.pro`.
- **Alternativas consideradas**: (1) Keystore de release real gestionado vía GitHub Secret — descartada explícitamente con el usuario, reabre ADR-031 sin beneficio de tamaño adicional (minify/shrink/strip no dependen de qué keystore se use), solo tendría sentido de cara a Play Store. (2) ABI splitting (`--split-per-abi`) — descartado, CI ya compila un único target (`aarch64`), nunca fue universal en producción; no era la causa real del tamaño. (3) Actualizar/pinnar el JDK local — descartado de esta spec, es un problema de estabilidad del entorno de build (JBR de Android Studio autoactualizado a Java 25 rompiendo Gradle, incidente ya resuelto puntualmente con `JAVA_HOME` apuntando a JDK 24) sin relación con tamaño/rendimiento en producción; CI ya fija JDK 17. (4) Separar `maplibre-gl` en un chunk lazy — evaluado, no incluido en esta spec; candidato a spec futura si el bundle web necesita reducirse más.
- **Consecuencias**: Cualquier cambio futuro a `apps/mobile/src-tauri/gen/android/app/build.gradle.kts` debe recordar que es un fichero trackeado y editable directamente, no algo que se regenera con `tauri android init` en cada build. El umbral `MAX_APK_SIZE_MB: 20` (medido real: 9MB) puede necesitar subirse deliberadamente en una PR futura si el bundle crece por una razón legítima — no es un valor mágico, está documentado en el propio `ci.yml`. La app sigue sin firma de release real (limitación ya aceptada en ADR-031, no agravada ni corregida por este cambio): actualizar una instalación previa puede seguir requiriendo desinstalar antes por el keystore efímero rotando en cada runner.

## ADR-048: Criterio explícito de qué merece una ADR — inyectado en `rules.design`, redactado en propose

- **Fecha**: 2026-08-03
- **Estado**: Aceptada
- **Contexto**: Ver [[criterio-adr]] (`openspec/changes/criterio-adr/`). `openspec/config.yaml` mandaba crear ADRs desde tres claves distintas (`rules.design`, `rules.tasks`, `operations.archive.guidance`) sin que ninguna definiera el umbral — la única pista era «una decisión nueva de ese calado», sin explicar en ninguna parte. Dos de esas tres empujaban además la redacción al cierre del cambio, cuando lo que hay delante es evidencia de verificación y no una decisión pendiente. Efecto medible en este log: ADR-013 a ADR-018 promedian ~800 caracteres frente a los ~4.400 de ADR-031 a ADR-033 y los 12.872 de ADR-027, con la diferencia ocupada por narrativa de sesión que `memory/context.md` ya recoge en paralelo.
- **Decisión**:
  1. **El criterio vive en `rules.design` de `openspec/config.yaml`**, que es su source of truth ([[ADR-027]]) y no se duplica aquí. Tres disparadores, basta con uno: coste de reversión alto, alternativas reales evaluadas y descartadas, o hallazgo contraintuitivo que el código no muestra. Con lista negativa explícita — es lo único que separa una ADR de `memory/context.md`.
  2. **Va en `rules.design` y no en `rules.proposal`** porque `rules:` está indexado por artefacto, no por comando: verificado ejecutando `openspec instructions design`, que devuelve las 4 entradas de `rules.design` y ninguna de `rules.proposal`. Como `/opsx:propose` escribe también `design.md`, ésa es la vía por la que el criterio llega al momento de proponer, y es además la única clave que ya mandaba crear la ADR.
  3. **`archive` verifica, no redacta**: `operations.archive.guidance` pasa a comprobar que la decisión quedó registrada durante propose, y a añadir ADR nueva solo si surgió de verdad durante `apply` — caso frecuente aquí, donde [[ADR-031]], [[ADR-032]] y [[ADR-033]] nacieron de hallazgos de implementación.
  4. **Nada retroactivo**: ADR-013 a ADR-047 quedan intactas en contenido, orden y numeración, incluidos el hueco 001-012 y el desorden 026/024 — el rango se amplió de ADR-033 a ADR-047 respecto a la redacción original (2026-08-03) por el tiempo transcurrido hasta fusionar este cambio, sin afectar la decisión. El criterio rige de ADR-049 en adelante.
- **Alternativas consideradas**: (1) Colocarlo en `rules.proposal` — descartada, se inyecta antes de que existan las decisiones técnicas que podrían merecer ADR. (2) Duplicarlo en varias claves para no fallar — descartada, dos fuentes del mismo criterio es exactamente el problema que causó [[ADR-027]]. (3) Dejar `archive` como estaba y añadir solo el criterio en `design` — descartada, no ataca la causa de la inflación: seguirían existiendo dos momentos válidos de redacción y ganaría el último, por tener la evidencia delante. (4) Un único criterio de «significancia arquitectónica» al estilo Nygard — descartada, dejaría fuera las ADRs de proceso ([[ADR-029]], [[ADR-030]]) e infraestructura ([[ADR-031]]) que este log sí quiere contener; de ahí «duraderas» y no «de arquitectura». (5) Sanear el log existente (reordenar, resumir las infladas, explicar el hueco) — descartada, editar ADRs aceptadas destruye la propiedad que las hace valer: poder leer qué se creía antes y qué cambió. (6) Test estructural sobre el YAML, con el precedente de `ci-workflow.spec.ts` — descartada, aquél afirma sobre estructura ejecutable, éste afirmaría sobre prosa destinada a reformularse y penalizaría mejorarla.
- **Consecuencias**: El criterio se inyecta en cada `/opsx:propose` sin que nadie tenga que acordarse, pero no se puede forzar — mismo nivel de enforcement elegido conscientemente en [[ADR-029]] y [[ADR-030]]. Una ADR redactada en propose puede quedar desmentida por `apply`: es el comportamiento correcto, y la desviación se anota en una ADR nueva en vez de editar la anterior (precedente: las Consecuencias de [[ADR-027]] anunciaban que los agentes se *realinearían* y el `apply` acabó eliminándolos).

## ADR-049: `metricas-sdlc-agente` — log JSONL de fallos del SDLC (no de la app, tokens ni productividad), taxonomía cerrada de 5 categorías, sin gate técnico

- **Fecha**: 2026-08-17
- **Estado**: Aceptada
- **Contexto**: Ver [[metricas-sdlc-agente]] (`openspec/changes/metricas-sdlc-agente/`). `memory/context.md` documenta hallazgos puntuales dentro de la narrativa de cada sesión, pero no existe ningún sitio que agregue por categoría o frecuencia dónde falla el propio proceso de trabajar con un agente en este repo — ni ningún mecanismo, técnico o documentado, para detectarlo. El objetivo es una fase de recopilación de datos únicamente; el análisis es un cambio futuro aparte.
- **Decisión**:
  1. **Ubicación `memory/metrics/` nueva**, separada de `context.md`: un log de eventos de grano fino (varios por sesión) no encaja en la narrativa de una entrada por sesión sin romper legibilidad ni capacidad de procesarse mecánicamente.
  2. **Formato JSON Lines** (`events.jsonl`, un objeto por línea, append-only): analizable sin parser propio, y cada línea nueva no reescribe el fichero, minimizando conflictos de merge entre sesiones/ramas.
  3. **Taxonomía cerrada de 5 categorías** (`memory-miss`, `gate-bypass`, `scope-violation`, `spec-drift`, `rework`) con válvula de escape `other`: permite agregar por categoría sin normalizar texto libre primero, sin bloquear el registro de lo que no encaje todavía.
  4. **Registro proactivo del propio agente, sin hook técnico**: mismo criterio ya elegido conscientemente en [[ADR-029]]/[[ADR-030]] (disciplina documentada, no forzada) — un hook solo podría cubrir mecánicamente parte de `gate-bypass`, ninguna de las otras cuatro categorías (son de juicio, no de estructura), lo que no simplifica lo suficiente para justificar la complejidad en esta fase.
  5. **Regla en `CLAUDE.md`, no solo en `openspec/config.yaml`**: varios de los fallos a capturar ocurren fuera del flujo `/opsx:*` (donde se inyectan las reglas de `config.yaml`) — un `git push` suelto, un fix puntual sin cambio abierto. `CLAUDE.md` se lee siempre.
- **Alternativas consideradas**: (1) `docs/` en vez de `memory/` — descartada, `docs/` es documentación generada/transversal, no memoria activa escrita cada sesión. (2) Tabla markdown dentro de `context.md` — descartada, mezcla dos granularidades y formatos, y cualquier campo con `|` o saltos de línea la rompe. (3) SQLite local — descartada, dependencia de tooling nueva sin beneficio real a la escala de unas decenas/cientos de eventos, y deja de ser diffable en git. (4) Categorías abiertas desde el principio — descartada, exigiría normalizar manualmente strings parecidos antes de poder contar nada; la taxonomía cerrada con `other` da lo mejor de ambas. (5) Hook técnico en `.husky/pre-commit` para `gate-bypass` — descartada por ahora, cubre una sola de cinco categorías y contradice el alcance de esta fase (solo recopilación).
- **Consecuencias**: El log depende de que cada sesión recuerde la regla de `CLAUDE.md` — sin gate técnico, puede quedar subalimentado; el campo `detected_by` (`self`/`user`) existe para medir ese sesgo de autoinforme en el análisis posterior, no para evitarlo ahora. La taxonomía es una apuesta inicial sin datos: candidata a revisarse en el cambio de análisis futuro según lo que aparezca realmente en `other`. Revertir el formato más adelante (p. ej. a SQLite tras acumular datos) obligaría a migrar el log ya recopilado — coste aceptado conscientemente por mantenerlo simple mientras no hay datos que lo justifiquen.

## ADR-050: `notificaciones-push-fcm` — FCM como transporte, backend propio como dueño de la lógica

- **Fecha**: 2026-08-18
- **Estado**: Aceptada
- **Contexto**: Ver [[notificaciones-push-fcm]] (`openspec/changes/notificaciones-push-fcm/`). `compartir-rutas` ya avisaba dentro de la app (badge numérico, [[contador-invitaciones-pendientes]]) pero solo si el usuario abría la app y navegaba al listado — nada llegaba con la app en segundo plano o cerrada. Android no tiene alternativa de sistema operativo a FCM para ese despertar real; investigado a fondo en sesión de exploración previa (ver `memory/context.md`, 2026-08-17) antes de proponer nada. Esto ya estaba anticipado sin bloquearse: [[ADR-034]] eligió Go en parte pensando en "notificaciones en tiempo real tipo SignalR" — este cambio lo concreta, con FCM como transporte (no SignalR/WebSocket propio, inviable en background/cerrado) y no como sustituto de la lógica de negocio.
- **Decisión**: Firebase Cloud Messaging transporta un **"data message" opaco** (`{"type": "route_share_invite", "invitation_id": "...", "route_id": "..."}`) — nunca el nombre de la ruta ni el email del emisor en texto plano; `FcmService.kt` construye el texto real de la notificación en el dispositivo, sin que Firebase lo vea ni lo guarde. El backend Go/Postgres sigue siendo el único dueño de quién, cuándo y con qué contenido se notifica, exactamente igual que con todo lo demás — capa **genérica** desde el principio (tabla `device_tokens` + tipo de evento, no acoplada solo a `compartir-rutas`), aunque `route_share_invite` sea el único tipo implementado hoy.
- **Alternativas descartadas**: (1) **UnifiedPush** — sin dependencia de Google, pero exige que el usuario instale una app "distribuidora" aparte (`ntfy` u otra); fricción real sin beneficio para el perfil de esta app (uso personal/entre conocidos). (2) **Foreground service propio sin FCM** — ya existe uno para GPS (`RecordingService.kt`), pero solo sobrevive porque `location` es una categoría protegida por Android; uno "siempre vivo para notificaciones" no lo es, Doze lo mataría en minutos. (3) **WebSocket/polling propio** — funciona solo con la app en foreground, mismo problema que (2) en background/cerrada; no sustituye a FCM, es una capa distinta ya descartada porque el objetivo explícito es funcionar con la app cerrada.
- **Consecuencias**: Verificado de punta a punta en dispositivo real (dos sesiones, `75fe536b`): permiso, token, push real recibido, tap navegando a Invitaciones ya con los datos cargados, rotación de token re-registrada sola. La verificación en dispositivo, no solo con mocks, encontró tres bugs reales que ningún test unitario/E2E cubría (`app.element.ts` está excluido de cobertura por ser composition root): (1) el plugin Rust `tauri-plugin-notification` nunca se había cableado (`Cargo.toml`/`lib.rs`/`capabilities`), así que el permiso jamás se pedía en silencio; (2) el tap de la notificación llamaba a un método privado en vez de `dispatchAppEvent(APP_EVENTS.VIEW_SHARING)`, así que abría Invitaciones siempre vacía; (3) `MainActivity.onCreate()` no manejaba el cold start (app cerrada del todo), solo `onNewIntent()` — corregido con el mismo patrón "pendiente en SharedPreferences + consulta desde JS cuando ya está listo" que ya usaba (sin conectar hasta ahora) el refresco de token FCM tras una rotación. Primera dependencia nativa Android fuera de Tauri/Google Play Services (`com.google.gms.google-services` + `firebase-messaging`); primer secreto de backend con formato multilínea del proyecto (`FCM_SERVICE_ACCOUNT_JSON`), gotcha real la primera vez que se pegó en `.env` (JSON multilínea rompe el formato de una sola línea `CLAVE=VALOR`, solo la `{` se leía). Toda la implementación de este cambio (dos sesiones completas) permaneció sin ningún commit hasta el cierre — riesgo de pérdida real, sin relación con la decisión técnica en sí, registrado aparte en `memory/metrics/events.jsonl`.

## ADR-051: `normalizar-y-exportar-rutas` — OSRM self-hosted como motor de map-matching para corregir puntos GPS

- **Fecha**: 2026-08-19
- **Estado**: Aceptada
- **Contexto**: Ver [[normalizar-y-exportar-rutas]] (`openspec/changes/normalizar-y-exportar-rutas/`). Los puntos GPS grabados en el móvil llegan con el ruido propio de un GPS de smartphone en moto (túneles, zonas urbanas densas, dosel forestal) — puntos sueltos desplazados de la carretera real, a veces atravesando edificios. `apps/api` no aplicaba ninguna corrección antes de persistir `route_points` ([[ADR-040]]), y este cambio quería además exportar rutas a GPX estándar — exportar ruido sin corregir habría propagado el problema a ficheros que el usuario comparte fuera de la app.
- **Decisión**: Servicio **OSRM** self-hosted (`osrm-backend`, imagen oficial), con su endpoint `match` (map-matching basado en HMM) llamado desde un cliente HTTP propio (`internal/mapmatch`, sin SDK — `net/http` de la librería estándar) dentro del mismo request síncrono de `UpsertHandler`, best-effort (si OSRM falla o no responde, la ruta se guarda igual con los puntos crudos). Extracto OSM de España (Geofabrik) preprocesado una vez, contenedor solo alcanzable dentro de la red interna de Docker, nunca expuesto a internet ni al host. Perfil de enrutamiento `car` (OSRM no trae uno de moto de fábrica; a efectos de "pegar a la carretera" las vías que usa una moto de carretera coinciden con las de un coche). Detalle completo de troceado de puntos, columnas nuevas y umbral de descarte en `design.md` del cambio.
- **Alternativas descartadas**: **GraphHopper Map Matching** — mismo concepto (motor Java), pero más pesado de levantar que OSRM para este caso de uso (trazas de moto, no rutas urbanas densas donde GraphHopper destaca); revisitable si en el futuro hiciera falta un perfil de enrutamiento más sofisticado que `car`.
- **Consecuencias**: Primera dependencia de infraestructura del proyecto que no es ni la propia app ni su base de datos (un tercer servicio en `docker-compose.yml`, con datos de mapa que hay que regenerar manualmente si OSM cambia — sin automatizar en este cambio). Los puntos GPS originales nunca se sobrescriben ni se descartan — la normalización vive en columnas nuevas nullables (`matched_lat`/`matched_lng`), así que revertir el servicio OSRM no implica pérdida de datos ni migración inversa más allá de un `DROP COLUMN` opcional. **Bug real encontrado verificando en dispositivo Android real, no en tests**: el wiring de producción en `cmd/api/main.go` nunca fijó `HTTPClient` en `mapmatch.Client`, así que usaba `http.DefaultClient` (sin timeout). Con `osrm` parado de verdad (prueba deliberada del fallback), la petición se quedaba colgada hasta que el propio móvil cortaba por su timeout de 8s — el "best-effort" de la Decisión 6 de `design.md` no era tal en la práctica. Corregido con un `http.Client{Timeout: 5 * time.Second}` explícito en el wiring; verificado de nuevo con `osrm` parado: la ruta se guarda en ~4s, sin normalizar, sin error visible.

## ADR-052: `normalizar-y-exportar-rutas` — exportación de fichero en Android requiere `@tauri-apps/plugin-dialog`, la Web Share API no sirve

- **Fecha**: 2026-08-19
- **Estado**: Aceptada
- **Contexto**: `design.md` (revisado) asumía que la exportación de un fichero (GPX) desde el móvil podía resolverse sin ningún plugin Tauri nuevo, usando la Web Share API (`navigator.share`/`canShare`, nivel 2, compartir ficheros) con un `<a download>` de blob como fallback — ambas son API del navegador, sin dependencia. Verificado en dispositivo real (`75fe536b`) vía Chrome DevTools Protocol (mismo procedimiento que ADR de sesiones anteriores, ver `memory/context.md`): `navigator.share`/`canShare` son **`undefined`** en el WebView de Android de Tauri, y el fallback de `<a download>` con blob no dispara ninguna descarga (el WebView no tiene gestor de descargas registrado) — el botón no hacía nada, sin error visible.
- **Decisión**: Escribir el fichero directamente con `@tauri-apps/plugin-fs` (ya instalado). Primer intento — `writeFile` a `downloadDir()` — tampoco fue la solución completa: escribe sin error, pero Android resuelve `BaseDirectory.Download` a la carpeta *privada* de la app (`Android/data/com.motoroutes.app/files/Download/`, confirmado con `adb shell find`), invisible para un gestor de archivos normal. La solución real: **`@tauri-apps/plugin-dialog`** (`save()`, selector nativo "Guardar como" vía Storage Access Framework) para que el propio usuario elija la ruta, y `plugin-fs` `writeFile()` sobre la ruta devuelta — el único camino verificado que deja el fichero en un sitio que el usuario encuentra sin instrucciones especiales. Efecto colateral positivo: al pasar por un menú de confirmación en vez de una acción directa de un solo tap, el mismo punto de entrada queda preparado para elegir formato cuando haya más de uno (hoy solo GPX) sin rediseñar el botón.
- **Alternativas descartadas**: (1) Web Share API sin plugin — descartada, no soportada en este WebView (ver Contexto). (2) `writeFile` directo a `downloadDir()` sin diálogo — descartada, resuelve a una carpeta invisible para el usuario en Android (ver Contexto). (3) Dejar el fichero en `$APPDATA/photos`-equivalente (carpeta privada de la app, mismo scope ya concedido) sin selector — descartada explícitamente por el usuario: peor experiencia que un selector nativo real, y la spec original pedía "compartir o guardar con el selector nativo del dispositivo".
- **Consecuencias**: Segunda dependencia nativa de Tauri de este proyecto añadida a mitad de implementación (la primera fue `tauri-plugin-notification`, ver [[ADR-050]]) — mismo patrón: npm + crate Rust + registro en `lib.rs` + permiso en `capabilities/default.json` (`dialog:allow-save`, mínimo necesario, sin el `dialog:default` completo). El scope de `fs:allow-write-file`/`allow-mkdir`/`allow-exists` para `$DOWNLOAD/**` que se había añadido en el intento anterior se revirtió — ya no hace falta: la ruta que devuelve el diálogo lleva su propio permiso de escritura implícito, no depende de la lista estática de capabilities. Verificado de punta a punta en dispositivo real: selector nativo se abre, fichero se guarda donde el usuario elige, toast de confirmación.

## ADR-053: `desplegar-osrm-produccion` — servicio `osrm` en `docker-compose.prod.yml` vía `network_mode: host` con `--ip 127.0.0.1`, procesado de datos deliberadamente fuera del pipeline automático

- **Fecha**: 2026-08-21
- **Estado**: Aceptada
- **Contexto**: Ver [[desplegar-osrm-produccion]] (`openspec/changes/desplegar-osrm-produccion/`). [[ADR-051]] desplegó la normalización OSRM solo en local — `docker-compose.prod.yml` no tenía servicio `osrm`, y `MAPMATCH_OSRM_URL` seguía vacío en el `.env.prod` real del servidor. La spec `normalizacion-gps` ya cubre ese estado como best-effort ("servicio no disponible"), así que no era un incidente, pero la feature llevaba desde 2026-08-19 desplegada e inactiva.
- **Decisión**: Servicio `osrm` nuevo en `docker-compose.prod.yml`, `network_mode: host` (mismo patrón que `api`, que ya lo usa para alcanzar el PostgreSQL nativo del servidor por loopback). A diferencia del `osrm` de dev (red bridge de Compose, sin exposición al host salvo por `api`), en modo host el binario `osrm-routed` expone su puerto directamente en las interfaces del host — y por defecto escucha en `0.0.0.0`, lo que en un servidor con IP de Tailscale habría quedado alcanzable más allá de loopback. Corregido con `--ip 127.0.0.1` explícito en el comando (verificado en el log de arranque: `IP address: 127.0.0.1`), sin publicar `ports:`. El procesado de datos (`osrm-extract`/`partition`/`customize`, picos de ~11 GB de RAM) queda **fuera** de `scripts/deploy-local.sh` — ese script corre en cada push a `master` vía el usuario restringido `ci-deploy` (shell fija, sin acceso libre, ver [[ADR-044]]), y automatizar ahí un proceso de ese tamaño en un servidor que ya sirve tráfico real (`api`, Postgres, MinIO) es un riesgo operacional sin beneficio proporcional — se ejecuta manualmente, una vez, documentado en `infra/docker/osrm/README.md`.
- **Alternativas descartadas**: (1) **Automatizar el procesado dentro de `deploy-local.sh`** — descartada por el riesgo de RAM sin control en cada despliegue (ver Contexto). (2) **Job de GitHub Actions con SSH al servidor para el procesado** — descartada por ahora: añadiría credenciales SSH nuevas en CI para un proceso que se ejecuta, en la práctica, una vez cada varios meses — coste de mantenimiento desproporcionado frente a un paso manual documentado.
- **Consecuencias**: Verificado en local con Docker Desktop y los datos reales ya procesados (sesión `normalizar-y-exportar-rutas`): el contenedor arranca, el healthcheck marca `healthy`, y `/nearest` responde 200 con un match real. Activar la normalización en producción queda desacoplado del despliegue automático de código (no atómico con `git pull`), aceptado porque `.env.prod` ya era, en general, edición manual del servidor.
- **Actualización, misma sesión — ejecutado en producción real, con un hallazgo que cambió el plan**: el usuario autorizó acceso SSH real (Tailscale ACL + Tailscale SSH, aprobado desde el panel web) para completar el pendiente en el servidor real. Al comprobar `free -h` antes de lanzar nada (paso explícito de la Decisión 2), el servidor resultó tener solo **5.6 GiB de RAM total** — muy por debajo de los ~11.4 GB que picó `osrm-extract` en local — y aloja además `intercom-signaling`, un servicio de otro proyecto sin relación con moto-routes; ejecutar el procesado ahí habría arriesgado un OOM sobre un servicio ajeno. Sustituido por: copiar por `scp` los ficheros ya procesados en local (~3.4 GB, sin `.pbf` ni logs) al servidor — evita el pico de RAM por completo, mismo resultado final. El directorio `osrm/data` no existía y pertenecía a `ci-deploy` (checkout de `deploy-local.sh`) sin permiso de escritura para `gonzalo` — creado con `sudo mkdir`+`chown` (sudo sin contraseña disponible para ese usuario). Verificado con el servicio real corriendo en el servidor (`healthy`, `/nearest` responde 200, log confirma `IP address: 127.0.0.1`) sin afectar a `docker-api-1` ni a `intercom-signaling-signaling-1`. `MAPMATCH_OSRM_URL` añadido a `.env.prod` (variable que no existía en ese fichero — predata la feature) y `api` recreado, confirmado sano vía `/api/ping` (200). La normalización está activa en producción desde el cierre de esta sesión. Hallazgo colateral sin relación con este cambio: `FCM_SERVICE_ACCOUNT_JSON` tampoco está en el `.env.prod` real — las notificaciones push de [[ADR-050]] están inactivas en producción, sin abordar aquí.

## ADR-054: `fix/sqlite-insert-limit-puntos-gps` — INSERT local de puntos/paradas troceado en bloques de 500, mismo criterio que el backend

- **Fecha**: 2026-08-22
- **Estado**: Aceptada
- **Contexto**: Incidente real reportado por el usuario en producción — una ruta real (`Navacerrada, morcuera y Miraflores`, 213 km / 3h15min) se subió a la nube con sus estadísticas correctas (distancia/duración/velocidad media) pero **cero puntos GPS**, tanto en el servidor como localmente en el dispositivo. `SqliteRouteRepository.save()` (`apps/mobile/src/shared/repositories/sqlite-route.repository.ts`) guardaba todos los puntos de una ruta en un único `INSERT` multi-fila, sin trocear — a diferencia de `PostgresRouteStore` en el backend (`apps/api/internal/routes/postgres_store.go`), que ya trocea de 500 en 500 explícitamente por el límite de parámetros de PostgreSQL, con un comentario citando ese motivo. El equivalente local nunca tuvo el mismo tratamiento.
- **Decisión**: Trocear también el `INSERT` local de `route_points`/`route_stops` en bloques de 500 filas — mismo valor y mismo patrón que `insertChunkSize` del backend, por consistencia y porque 500×7 params (3500) queda con margen amplio bajo el límite real de SQLite. Además, `persistRouteOnStop` (`cockpit-persist.service.ts`) ahora muestra un toast visible si el guardado falla — antes el error se tragaba en silencio (solo un backup en `localStorage` que ningún código llega a leer nunca), que es la razón por la que este incidente pasó completamente desapercibido hasta que el usuario abrió la ruta días después.
- **Verificación real, no solo unit tests con mock**: reproducido el fallo exacto con `sqlx` 0.8.6 (misma versión que usa `tauri-plugin-sql`) contra una base SQLite real en memoria — confirmado el límite exacto de SQLite (`SQLITE_MAX_VARIABLE_NUMBER = 32766`): 4680 puntos (32760 parámetros) inserta bien, 4681 puntos (32767) falla con `too many SQL variables`. Con la tasa de muestreo GPS real medida en otra ruta del usuario (~1 punto/seg), eso son **~78 minutos** — cualquier ruta más larga que eso lo dispara, no es un caso extremo. Verificado también end-to-end en un dispositivo Android real, insertando y recuperando 11.552 puntos (el tamaño real de la ruta rota) a través de la IPC real de Tauri contra la base de datos real de la app, sin pérdida.
- **Recuperación de los datos originales, sin éxito**: comprobado `localStorage` del dispositivo real del usuario (vía `run-as` + LevelDB) — vacío, sin el backup esperado (probablemente el propio `localStorage.setItem` también falló para una cadena tan grande, o se sobrescribió con otra ruta después). `adb backup` tampoco sirvió — Android moderno + ColorOS devuelven un archivo vacío para apps de release no depurables. Los puntos GPS de esa ruta concreta se dan por irrecuperables.
- **Alternativas descartadas**: envolver `save()` en una transacción SQLite explícita (`BEGIN`/`COMMIT` como sentencias sueltas) para atomicidad completa — descartada por el riesgo de que `tauri-plugin-sql` no garantice la misma conexión entre llamadas `execute()` sucesivas (pool de conexiones), lo que podría romper la semántica de transacción de forma más sutil que el bug original. El troceado por sí solo ya cierra el caso real reportado sin ese riesgo añadido.
- **Consecuencias**: Cualquier ruta grabada localmente, sin importar su duración, se guarda ahora de forma fiable. Sigue existiendo un fallo de guardado *en teoría* posible (disco lleno, corrupción de SQLite) pero ahora nunca en silencio — el usuario lo sabrá en el momento, no días después al abrir la ruta.

## ADR-055: `unificar-perfil-cuenta` — el avatar de cuenta vive solo en MinIO (sin migración de BBDD), reutilizando el `BlobStore` cifrado ya existente de fotos de ruta

- **Fecha**: 2026-08-22
- **Estado**: Aceptada
- **Contexto**: Ver [[unificar-perfil-cuenta]] (`openspec/changes/unificar-perfil-cuenta/`). El nombre local de Perfil (`Profile.name`) queda redundante frente al `username` obligatorio de toda cuenta (ver `nombre-usuario`); el avatar (`Profile.avatarPath`) es puramente local, sin relación con la cuenta. `apps/api/internal/photos` ya tiene un mecanismo real de almacenamiento cifrado (MinIO + `Encrypt`/`Decrypt` con `cfg.PhotoEncryptionKey`) para fotos de ruta, con metadatos propios en una tabla (`route_photos`) porque cada foto tiene coordenadas y momento de captura.
- **Decisión**: El avatar de cuenta reutiliza el mismo `BlobStore` de MinIO y la misma clave de cifrado — sin bucket ni secreto nuevos — bajo una clave de objeto determinista `avatars/{userID}` (un único avatar por cuenta, sustituido con cada subida). **Sin ninguna migración de base de datos**: a diferencia de una foto de ruta, un avatar no tiene metadatos propios que consultar aparte de "existe o no" — su existencia se determina intentando leer el objeto (`NoSuchKey` de MinIO → 404 de la API). `GET /api/auth/me` no cambia; el cliente descubre si hay avatar descargándolo directamente, mismo criterio que ya usa el listado de fotos de ruta (nunca un flag "tienePhotos" embebido en la ruta).
- **Alternativas descartadas**: (1) **Columna `avatar_key`/`has_avatar` en `users`** — descartada: exigiría una migración y mantener esa columna sincronizada con el objeto real de MinIO en cada subida/borrado, con la posibilidad real de que diverjan (p. ej. una subida que falla a mitad). La clave determinista hace ese estado imposible por construcción. (2) **Bucket dedicado para avatares** — descartada por simplicidad operacional: un prefijo (`avatars/`) en el bucket ya existente no añade superficie de configuración nueva. (3) **Exponer `has_avatar` en `GET /api/auth/me`** — descartada para mantener `user-auth` sin tocar y esta capability autocontenida, igual que ya se decidió para las fotos de ruta.
- **Consecuencias**: Cero migraciones de Postgres para este cambio. El límite de tamaño del avatar (5MB, frente a los 15MB de una foto de ruta — una imagen de perfil no necesita ese margen) es la única defensa nueva de abuso; no se añade rate limiting dedicado porque no es un endpoint de autenticación (login/registro/token), mismo criterio ya aplicado a la subida de fotos de ruta. Los campos locales `Profile.name`/`avatarPath` dejan de leerse/escribirse en el cliente, pero sus columnas SQLite no se borran (`DROP COLUMN` nunca se ha usado en las migraciones locales de este proyecto — siempre aditivas, ver `ensureColumn`/`ensurePreviewPolylineColumn` en `sqlite-route.repository.ts` — el riesgo de una migración destructiva sobre dispositivos reales no está justificado por limpiar una columna ya sin uso).

## ADR-056: `agregar-amigos` — los ids de pestaña de `<tab-bar>` deben ser únicos en toda la app, no solo dentro de su propio componente

- **Fecha**: 2026-08-23
- **Estado**: Aceptada
- **Contexto**: `app.element.ts` monta **todas** las vistas de la app a la vez en el DOM al arrancar (`cockpit`, `routes`, `detail`, `profile`, `sharing`, `achievements`, `friends`...) y solo alterna cuál es visible con `style.display = 'none'` — nunca las crea/destruye al navegar (mismo patrón documentado ya varias veces en este fichero para `nav-bar`/`profile-view`). `<tab-bar>` (`shared/tab-bar/tab-bar.element.ts`) genera el `data-cy` de cada botón de pestaña como `tab-bar-btn-${tab.id}`, con el `id` elegido libremente por cada componente que lo usa. `route-sharing.element.ts` (ya existente) y `friends-view.element.ts` (este cambio) eligieron independientemente los mismos ids genéricos `recibidas`/`enviadas` para sus propias pestañas, sin ninguna coordinación entre ambos — cada uno razonable visto en aislamiento.
- **Decisión**: Los ids de pestaña de cualquier `<tab-bar>` nuevo deben ser únicos en toda la app (namespaced con el propio dominio, p. ej. `friends-recibidas` en vez de `recibidas`), no solo únicos dentro del propio componente — porque como todas las vistas conviven en el DOM a la vez, dos componentes con el mismo id de pestaña producen dos elementos con el mismo `data-cy`, y `cy.get()`/`cy.contains()` sin más scoping falla con "subject contained N elements" o, peor, interactúa con el elemento equivocado en silencio. Corregido renombrando los tres ids de `friends-view.element.ts` (`amigos`→`friends-amigos`, `recibidas`→`friends-recibidas`, `enviadas`→`friends-enviadas`) — nunca los de `route-sharing.element.ts`, capability ya en producción con su propio histórico de commits y su E2E ya verificado independientemente.
- **Cómo se encontró**: no en el análisis de diseño (`design.md` de este cambio no lo anticipó), sino al ejecutar la suite completa de Cypress (tasca 7.1) — `route-sharing.cy.ts`, que llevaba semanas en verde sin tocarse, empezó a fallar con `cy.click() can only be called on a single element` en cuanto `friends-view.element.ts` quedó montado permanentemente por `app.element.ts`. Sin ese paso de verificación de la suite *completa* (no solo el spec nuevo) este bug habría llegado a la PR sin detectar.
- **Alternativas descartadas**: (1) Scopear cada test con un selector padre (`[data-cy="friends-view-screen"] [data-cy="tab-bar-btn-enviadas"]`) en vez de renombrar los ids — descartada porque no arregla el problema de fondo (el `data-cy` real sigue duplicado en el DOM, cualquier futuro test o herramienta que no sepa scopear seguirá pisándose) y solo lo esconde en este spec concreto. (2) Que `<tab-bar>` genere un `data-cy` único por instancia (p. ej. con un prefijo aleatorio o basado en el propio custom element padre) — descartada por sobre-ingeniería: rompería la legibilidad de los `data-cy` existentes (`tab-bar-btn-enviadas` sigue siendo el nombre más simple posible) a cambio de resolver un problema que namespacing manual ya resuelve sin tocar el componente compartido.
- **Consecuencias**: Cualquier dominio nuevo que use `<tab-bar>` debe revisar los ids ya usados por otros componentes montados permanentemente por `app.element.ts` (hoy: `route-sharing`, `friends-view`) antes de elegir los suyos — no hay ningún chequeo automático que lo fuerce, es disciplina manual, mismo criterio que el resto de gaps de `data-cy` ya documentados en este fichero.

## ADR-057: `renovacion-token-sesion` — sesión de access token corto + refresh token opaco revocable, en vez de alargar el JWT stateless actual

- **Fecha**: 2026-08-23
- **Estado**: Aceptada
- **Contexto**: Ver [[renovacion-token-sesion]] (`openspec/changes/renovacion-token-sesion/`). Hoy la sesión es un único JWT stateless de 24h (`apps/api/cmd/api/main.go`, `tokenTTL`) — sin ningún mecanismo de renovación ni de revocación antes de su expiración natural, limitación ya señalada explícitamente al descartar la invalidación de sesiones en el reset de contraseña (ADR-036: *"el esquema `TokenIssuer` es completamente stateless sin lista de revocación; añadir eso es un cambio de arquitectura mayor"*). El usuario pidió una sesión larga sin repetir contraseña, "de manera segura", citando el criterio de apps tipo Instagram.
- **Decisión**: Dividir la sesión en dos componentes con propiedades distintas — un **access token** (el JWT ya existente, sin cambios de formato, solo baja su TTL de 24h a 30 min) y un **refresh token** nuevo, opaco y aleatorio (reutilizando `generateOneTimeToken()`/`hashOneTimeToken()` de `verification_token.go`, cero dependencias nuevas), respaldado por una tabla nueva (`refresh_tokens`, migración `0014`) con rotación de un solo uso en cada canje. El access token sigue verificándose sin tocar la BBDD (rápido, en cada petición); el refresh token es el único componente con estado, y por tanto el único revocable — exactamente la limitación que ADR-036 dejó pendiente.
- **Alternativas descartadas**: (1) **Alargar directamente el TTL del JWT actual** (p. ej. a 60 días) — la opción más simple, descartada porque un JWT robado seguiría siendo válido semanas sin ninguna forma de invalidarlo, justo el "cambio de arquitectura mayor" que ADR-036 ya identificaba como necesario para poder revocar. (2) **Segundo JWT de vida larga como refresh token** — descartada porque un JWT es auto-verificable sin BBDD por diseño; usarlo como refresh token tendría el mismo problema de no poder revocarse sin mantener igualmente una lista de exclusión, así que no aporta nada frente a un token opaco respaldado por tabla. (3) **Hacer también el access token con estado** (una fila por sesión verificada en cada petición) — descartada por anular la ventaja de usar JWT (verificar sin tocar la BBDD) sin necesidad real, ya que la revocación solo importa para el componente de vida larga.
- **Consecuencias**: Primer componente con estado explícito en el ciclo de vida de una sesión — la autenticación deja de ser 100% stateless. **BREAKING** de forma controlada: sesiones JWT de 24h ya emitidas antes del despliegue no tienen refresh token asociado y expiran sin poder renovarse; sus usuarios necesitan un único re-login tras el despliegue, momento en el que ya reciben el par access+refresh nuevo (ver design.md, Migration Plan). Cierra explícitamente la limitación que ADR-036 dejó documentada como pendiente, sin necesidad de revisar esa decisión (el reset de contraseña sigue sin invalidar sesiones activas del JWT, pero ahora si se quisiera abordar sería sobre la tabla `refresh_tokens`, no sobre el JWT).

## ADR-058: `selector-amigos` — la búsqueda de usuarios queda abierta a cualquier cuenta, no restringida a relaciones existentes

- **Fecha**: 2026-08-23
- **Estado**: Aceptada
- **Contexto**: Ver [[selector-amigos]] (`openspec/changes/selector-amigos/`). Nuevo componente `<friend-selector>` con autocomplete necesita un endpoint de búsqueda de usuarios que hoy no existe en absoluto (confirmado por búsqueda exhaustiva antes de proponer). El propósito de "amigos" es descubrir gente nueva dentro de la app, y compartir-rutas ya permite invitar a cualquier cuenta con email (sin exigir amistad previa) — ninguno de los dos casos de uso reales encaja con restringir la búsqueda a gente con la que ya existe alguna relación.
- **Decisión**: El endpoint `GET /api/users/search` deja ver, a cualquier cuenta autenticada, el `username` (nunca el email) de cualquier cuenta registrada cuyo username coincida parcialmente — sin exigir amistad, solicitud pendiente ni invitación previa entre ambas cuentas. Se mitiga el riesgo de cosecha masiva de usernames con rate limiting por cuenta autenticada (30 búsquedas/minuto, `userID` del JWT como clave del `LoginRateLimiter` genérico ya existente) y un límite duro de 10 resultados por búsqueda — nunca restringiendo a quién se puede buscar.
- **Alternativas descartadas**: (1) **Restringir la búsqueda a cuentas con las que ya existe alguna relación** (amistad o solicitud/invitación previa) — la opción más privada, descartada por contradecir el propósito de las dos funcionalidades que consumen el selector: ninguna de las dos existe para gestionar relaciones ya establecidas, existen para crearlas con gente nueva. (2) **Búsqueda exacta en vez de parcial** (como ya exige hoy `POST /api/friends`) — descartada porque anula el propósito del selector (confirmación visual antes de confirmar), que necesita mostrar coincidencias mientras se escribe, no solo validar un username ya completo.
- **Consecuencias**: El username de cualquier cuenta pasa a ser descubrible por cualquier otra cuenta autenticada sin relación previa — un cambio real de superficie respecto a hoy (donde encontrar un username exige ya conocerlo o verlo en un listado de una relación existente), aceptado explícitamente por el usuario antes de proponer este cambio. El email nunca se expone por este camino, ni antes ni después de esta decisión. Si en el futuro se decide restringir la búsqueda (p. ej. por abuso real detectado), es un cambio de esta misma decisión — requiere una ADR nueva que la supersede, no editar esta.
