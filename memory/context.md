# Contexto del Proyecto: Moto Routes

## Identidad
- **Nombre**: Moto Routes (Ride Tracker)
- **Propósito**: Aplicación móvil para motociclistas que combina navegación GPS, grabación de rutas y bitácora multimedia. Desde la sesión `entorno-api-docker` (2026-08-03), monorepo: app móvil (`apps/mobile/`) + API backend (`apps/api/`).
- **Repositorio**: d:\Git\Otros\moto-routes

## Stack Tecnológico
- **Lenguaje Frontend**: TypeScript 5.7 (strict mode) — `apps/mobile/`
- **Lenguaje Móvil/Desktop backend**: Rust (stable, edition 2021) — `apps/mobile/src-tauri/`
- **Lenguaje API backend**: Go 1.25 (chi router, pgx/v5, golang-jwt, bcrypt) — `apps/api/`. Migrado desde Java/Spring Boot en la sesión `migrar-api-golang` (2026-08-04, ver [[ADR-034]]) — el histórico Java/Maven queda solo en `git log`/ADRs, no en el árbol de trabajo.
- **BBDD API backend**: PostgreSQL 16 (Docker, imagen `postgres:16-trixie`)
- **Bundler**: Vite 6
- **Desktop/Mobile Framework**: Tauri 2
- **UI**: Web Components nativos (Custom Elements v1)
- **Testing Frontend**: Vitest 3 (jsdom, coverage v8) → 80% threshold
- **Testing Móvil backend**: cargo test (unit + integration)
- **Testing API backend**: `go test ./...` (unit + integración real contra Postgres, aislada por schema — `internal/dbtest`)
- **Linting TS**: ESLint 9 (strictTypeChecked + stylistic)
- **Linting Rust**: Clippy (deny warnings)
- **Formatting TS**: Prettier 3
- **Formatting Rust**: rustfmt
- **Git Hooks**: Husky 9 (pre-commit, en orden: `pnpm audit --audit-level=high` + `cargo audit` con excepciones documentadas → ESLint → Vitest → Clippy → rustfmt → cargo test → E2E Cypress vía `pnpm test:e2e`. El paso de auditoría real se cableó en la sesión `auditoria-seguridad` — antes solo estaba documentado en `docs/06-seguridad.md`, nunca implementado. Desde `entorno-api-docker`, todos los comandos de `apps/mobile` se ejecutan con `cd apps/mobile && ...`/`cd apps/mobile/src-tauri && ...`, el hook en sí sigue viviendo en `.husky/` de la raíz. Desde `skip-quality-gates-docs-only` (2026-08-20): si TODO lo staged es documentación (markdown en cualquier ruta, `openspec/**/*.yaml` de tracking o `memory/**/*.jsonl` de métricas), el hook salta directo sin correr nada de lo anterior — mismo patrón replicado en el job `detect-doc-only-change` de `.github/workflows/ci.yml`, que además gatea `quality-ts`/`quality-tauri`/`quality-go`; en un push de tag (`v*`) esas tres jobs corren siempre, ignorando ese output)
- **Package Manager**: pnpm (workspace: `packages: [apps/mobile, apps/web]` desde `dashboard-reporting`, 2026-08-27) + Cargo + Go modules (`go.mod`)
- **Security**: CSP estricto, permisos mínimos, sin eval, path validation (app móvil); sin secretos en código en `apps/api` (credenciales de Postgres vía `infra/docker/.env`, no versionado)
- **BBDD Local (app móvil)**: SQLite vía `@tauri-apps/plugin-sql` (archivo: `moto-routes.db`)
- **Docker**: `infra/docker/docker-compose.yml` (servicios `api`+`postgres`, ambos con imagen base Debian 13/trixie — ver [[ADR-032]]), solo para desarrollo local, sin despliegue real todavía

## Herramientas de Desarrollo
- **GitHub CLI**: `gh` (oficial, ya instalado) → issues, PRs, releases
- **rtk**: Proxy de comandos (https://github.com/rtk-ai/rtk) → reduce tokens 60-90% en comandos repetitivos
- **Cline**: Extensión VSCode con DeepSeek como modelo
- **`scripts/tag-release.sh <tag>`**: sustituye a `git tag` manual para releases — hace `git fetch origin master` y taguea/empuja siempre sobre `origin/master` recién fetcheado, nunca sobre el HEAD local de la rama en la que se esté trabajando (nace del incidente real de v0.1.14, ver `mejoras-proceso-sdlc` en "Estado Actual del Proyecto" y ADR-062).
- **`scripts/verify-prod-env.sh <example> <real>`**: antes de un despliegue a producción, compara los NOMBRES de clave (nunca los valores) entre un `.env*.example` versionado y un `.env*` real, y falla listando lo que falta. Solo local/CI por ahora — no se conecta por SSH al servidor de producción (nace del incidente real de v0.1.16, `.env.prod` sin `ADMIN_STATUS_TOKEN`/`RESEND_WEBHOOK_SECRET`).
- **`scripts/check-go-quality.sh` / `check-native-plugins.sh` / `check-docker-running.sh`**: chequeos automáticos de `scripts/pre-commit.sh` (pasos 4, 6 y 11) — no se invocan sueltos en el día a día, solo si hace falta depurar el propio pre-commit.

## Filosofía Visual: "Asfalto Nocturno"
- **Concepto**: Cuero oscuro, negro asfalto y ámbar cálido. Cuaderno de bitácora, no HUD de competición. **Prohibido**: neón, glassmorphism, azules fríos, diales circulares.
- **Source of truth**: `specs/ui/design-system.md` y `src/shared/styles/tokens.css`.
- **Tokens activos** (`--bg-top`, `--panel`, `--amber`, `--ink`, `--font-display/ui/data`). **No usar** `--color-*`, `--glow-*`, `--neon-*` (eliminados).
- **Modo oscuro obligatorio**: Por seguridad vial, sin modo claro.
- **Hitbox mínima**: 56×56px para uso con guantes de moto.
- **Paleta**: Asfalto/cuero oscuro (`--bg-top`/`--bg-bottom`), ámbar único acento (`--amber`), óxido de apoyo (`--rust-line`).
- **Tipografía**: Roboto Slab (titulares) + Barlow (interfaz) + Barlow Semi Condensed tabular (cifras). Self-hosted en `src/assets/fonts/`.
- **Shadow DOM**: Los estilos globales reales viven en `tokens.css` (importado en cada `*.element.css`). `index.css` solo alcanza DOM ligero.
- **Historial**: Sustituye a "Telemetry & Freedom" (ADR-019). Archivos legacy eliminados (`estilos_base.scss`, `filosofia de diseño.md`).

## Build Android
```powershell
cd apps/mobile
bash scripts/install-android.sh          # detecta la ABI del dispositivo conectado, compila release e instala en un paso
# o, equivalente a mano (release, igual que publica CI desde optimizar-bundle-produccion, 2026-08-12):
pnpm tauri android build --target aarch64
adb install -r src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release.apk
# debug (más rápido para iterar, ~148MB el .so sin stripear frente a los ~6.7MB del release):
pnpm tauri android build --target aarch64 --debug
adb install -r src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
```
**Desde `optimizar-bundle-produccion` (2026-08-12, ADR-047) el APK que publica CI ya no lleva `--debug`** — es un build `release` real (minify+shrinkResources+profile Rust optimizado), firmado con el mismo keystore de debug efímero de siempre. ~9MB medido real, frente a los ~170MB del debug que se publicaba antes. El gotcha de assets huérfanos de más abajo (§ "puede empaquetar frontend desactualizado") aplica igual al buildType release — `install-android.sh` ya hace el force-sync necesario, no hace falta a mano en local.

**Usar siempre este comando del CLI de Tauri — nunca `cargo build --target aarch64-linux-android` manual.** `scripts/build-apk.ps1` (que hacía justo eso, con copia manual de `dist/` a `app/src/main/assets/` y un `tauri.conf.json` "standalone" propio) se eliminó el 2026-08-02: su premisa era falsa. `tauri::generate_context!()` embebe `devUrl`/`frontendDist` en el binario Rust **en tiempo de compilación**, leyendo siempre `src-tauri/tauri.conf.json` (el real, con `devUrl: "http://localhost:1420"` para poder usar `pnpm tauri dev`). Un `cargo build` en profile `dev` (sin `--release`) hace que Tauri prefiera `devUrl` sobre `frontendDist` en tiempo de ejecución **sin importar qué JSON haya en la carpeta de assets del APK** — ese archivo no se relee en runtime. Síntoma exacto si esto pasa: la app abre con fondo negro y el texto `Failed to request http://localhost:1420/ — error sending request for url (http://localhost:1420/)`. El comando del CLI (`pnpm tauri android build --debug`) sí evita esto correctamente (usa `frontendDist`), es la única vía soportada.

**Gotcha del CLI**: cada `pnpm tauri android build` resetea `src-tauri/gen/android/app/tauri.properties` (`tauri.android.versionCode`) a `1000`. Si el dispositivo ya tiene instalado un `versionCode` mayor (de una build anterior), `adb install -r` falla con `INSTALL_FAILED_VERSION_DOWNGRADE`. No hay forma de evitarlo sin tocar el CLI — si pasa, `adb uninstall com.motoroutes.app` (pierde datos locales de prueba del dispositivo) y reinstalar.

**Gotcha grave (2026-08-02) — el build puede empaquetar frontend desactualizado sin avisar**: en builds sucesivas donde solo cambia el frontend (sin tocar Rust), `pnpm tauri android build` a veces **no vuelve a copiar el `dist/` recién generado dentro del APK** — el paso de `pnpm build` (`beforeBuildCommand`) sí se ejecuta y `dist/` queda correcto, pero el APK final sigue conteniendo el bundle JS de una build anterior (verificado con hashes de archivo distintos entre `dist/assets/index-*.js` y lo que de verdad contenía el APK). No hay ningún error ni warning — el build "termina bien" y el APK se instala sin problema, pero ejecuta código viejo. **Siempre verificar el contenido real del APK antes de dar una build por buena**:
```bash
unzip -p src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk assets/index.html
```
Comparar el hash del `<script src="/assets/index-XXXX.js">` con el de `dist/index.html` recién generado — si no coinciden, el APK está desactualizado. Fix que funciona de forma fiable: copiar `dist/*` a mano a `src-tauri/gen/android/app/src/main/assets/` (`rm -rf .../assets/assets && cp -r dist/assets .../assets/assets && cp dist/index.html .../assets/index.html`) y luego reempaquetar SOLO con Gradle, saltando las tareas Rust (que fallan fuera del wrapper del CLI de Tauri, ver gotcha siguiente):
```powershell
cd src-tauri/gen/android
.\gradlew.bat assembleArm64Debug -x :app:rustBuildArm64Debug -x :app:rustBuildArmDebug -x :app:rustBuildX86Debug -x :app:rustBuildX86_64Debug
```
El APK queda en `app/build/outputs/apk/arm64/debug/app-arm64-debug.apk` (ruta distinta a la del build vía CLI, que usa `apk/universal/debug/`). Reverificar con el mismo comando `unzip` antes de instalar. **No dar nunca una verificación visual del usuario por buena sin haber confirmado primero, con este comando, que el APK instalado contiene el código que se cree que contiene** — en esta sesión se le pidió al usuario que probara una build que en realidad era una versión vieja, y confirmó "funciona" sin haber probado el cambio real.

**Corrección (2026-08-07, sesión `rutas-en-la-nube`) — el "fix fiable" de arriba (copiar `dist/` a mano + reempaquetar solo con Gradle) NO fue fiable esta vez.** El `unzip` del APK confirmaba el JS nuevo (`index-BeQkRJd_.js`), `adb install -r` decía éxito, y hasta forzar `am force-stop` + borrar `app_webview`/`cache`/`code_cache` del propio paquete (`adb shell run-as com.motoroutes.app sh -c 'rm -rf ...'`) + relanzar — la app seguía ejecutando el JS de la build anterior. La verificación por `unzip` del APK **no es suficiente**: confirma qué hay empaquetado, no qué sirve de verdad el WebView de Tauri en runtime. Verificación real vía Chrome DevTools Protocol contra el WebView (mucho más fiable que `unzip` + capturas de pantalla):
```bash
adb shell cat /proc/net/unix | grep webview_devtools   # localiza @webview_devtools_remote_<pid>
adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>
curl -s http://localhost:9222/json                     # lista páginas, cada una con su id/webSocketDebuggerUrl
# con Node 18+ (WebSocket global), Runtime.evaluate sobre ese id:
#   document.querySelector('script').src  → confirma qué bundle sirve de verdad
```
Solo el build completo de la CLI (`pnpm tauri android build --target aarch64 --debug`, con Rust incluido, sin `-x`) hizo que el WebView sirviera el JS nuevo. **Hasta no tener una explicación mejor, tratar el atajo "solo Gradle" como no confiable para cambios de solo-frontend y usar siempre el build completo de la CLI, verificando con CDP (no solo con `unzip`) antes de dar una build por buena.**

**Corrección adicional, misma sesión — ni siquiera el build completo de la CLI es fiable por sí solo, cada vez.** En la misma sesión, repetidas veces (no una excepción puntual): `pnpm tauri android build` terminó "bien" pero el `assets/index.html` empaquetado en el APK seguía referenciando el hash JS de la build ANTERIOR (`dist/index.html` sí tenía el hash nuevo — confirmado con el mismo comando `unzip` de más arriba). Rutina que sí funcionó, de forma consistente, cada vez que se repitió: (1) build completo de la CLI, (2) comparar `grep -o 'index-[A-Za-z0-9_-]*\.js' dist/index.html` contra el mismo grep sobre `unzip -p .../app-universal-debug.apk assets/index.html`; si no coinciden, (3) copiar a mano `dist/assets`→`.../app/src/main/assets/assets` y `dist/index.html`→`.../assets/index.html` (mismo comando que el "fix fiable" de más arriba), y (4) volver a lanzar el build completo de la CLI una segunda vez (no basta con Gradle-only, ver corrección anterior) — esa segunda vuelta sí empaqueta bien. **Tratar esto como el procedimiento normal, no como una excepción: verificar el hash después de cada build y repetir el ciclo copiar+rebuild hasta que coincida, antes de instalar.** Verificación de que el WebView del dispositivo sirve de verdad lo esperado (no solo que el `.apk` lo contenga) vía Chrome DevTools Protocol:
```bash
adb shell cat /proc/net/unix | grep webview_devtools   # localiza @webview_devtools_remote_<pid> (pid cambia en cada relanzamiento)
adb forward tcp:PUERTO localabstract:webview_devtools_remote_<pid>
curl -s http://localhost:PUERTO/json                    # lista páginas — puede devolver vacío/colgarse la primera vez tras instalar, reintentar
# con Node 18+ (WebSocket global) contra el webSocketDebuggerUrl de la página "type":"page":
#   Runtime.evaluate con awaitPromise:true, expresión async con su propio try/catch
#   y un setTimeout de proceso — el canal CDP se queda colgado o se cae sin previo
#   aviso tras uso intensivo; si un eval trivial (`1+1`) no responde en unos segundos,
#   no seguir insistiendo con la misma conexión: `adb forward --remove-all` y
#   reabrir desde cero (nuevo `adb forward` + nueva conexión WebSocket).
```
Con la página cargada, `document.querySelector('script').src` confirma el bundle real servido; `elemento.getBoundingClientRect()` sobre elementos dentro de un Shadow DOM (`customElements` de esta app) permite medir alineación real en píxeles sin depender de capturas de pantalla ni de que el dispositivo esté desbloqueado — más rápido y más preciso que pedirle al usuario una captura para un ajuste visual fino.

**Gotcha adicional (2026-08-02, misma sesión) — el JBR de Android Studio se autoactualizó a mitad de sesión y rompió el build**: `pnpm tauri android build` empezó a fallar con `A problem occurred configuring project ':buildSrc'. > 25.0.2` / `Caused by: java.lang.IllegalArgumentException: 25.0.2` en `JavaVersion.parse` — el parser de versión de Java del plugin Kotlin DSL (bundlado con la versión de Gradle/AGP de este proyecto) no reconoce Java 25. Causa: `C:\Program Files\Android\Android Studio\jbr\bin\java.exe` (usado como `JAVA_HOME` en todos los builds de esta sesión) se autoactualizó de una versión más antigua a `25.0.2` mientras la sesión estaba en curso — build que llevaba horas funcionando con el mismo comando exacto de repente rompió sin que cambiara nada del proyecto. Limpiar `.gradle`/`app/build` **no lo arregla** (no es un problema de caché). Fix: usar un JDK más antiguo como `JAVA_HOME` en su lugar — `C:\Program Files\Java\jdk-24` (24.0.1) funcionó. Si ese tampoco existe, instalar cualquier JDK 17-21 y apuntar `JAVA_HOME` ahí. Si un build que antes funcionaba empieza a fallar con un error de parseo de versión de Java sin explicación, comprobar primero `& "$env:JAVA_HOME\bin\java.exe" -version` — puede haberse actualizado solo. **Reaparecido en `nombre-usuario` (2026-08-22)**: mismo error exacto (`> 25.0.2`), sin haber leído esta sección antes de tocar el build (ver evento `memory-miss` en `memory/metrics/events.jsonl`) — se perdió tiempo real re-verificando síntomas ya documentados en vez de aplicar el fix de `JAVA_HOME` directamente. **Antes de tocar el build de Android, leer esta sección entera** — CLAUDE.md ya lo pide explícitamente.

**El CSP real que sirve la app vive en `apps/mobile/index.html`, no en `src-tauri/tauri.conf.json`** (encontrado en `nombre-usuario`, 2026-08-22, verificando 7.4 contra LAN): `tauri.conf.json` también tiene un campo `app.security.csp` con el mismo contenido duplicado, pero para el pipeline de Android (`pnpm build` de Vite + `tauri android build`) es el `<meta http-equiv="Content-Security-Policy">` de `index.html` el que termina empaquetado de verdad en el APK — confirmado con `unzip -p ...apk assets/index.html`. Editar solo `tauri.conf.json` para un host temporal de LAN (patrón ya usado en sesiones anteriores, línea de arriba) no tiene ningún efecto observable; hay que editar `index.html`. Los dos ficheros deberían decir lo mismo siempre — si se toca uno para una prueba temporal, revertir también el otro si se llegó a tocar por error.

**Gotcha nuevo (2026-08-23) — el daemon de Kotlin puede fallar con "this and base files have different roots" sin que el build falle de verdad**: en este checkout, el proyecto vive en `D:\Git\Otros\moto-routes` pero las dependencias de Cargo (incluidos los plugins de Tauri con código Kotlin, p. ej. `tauri-plugin-fs`/`tauri-plugin-dialog`) se descargan en `C:\Users\<user>\.cargo\registry\...` — **unidades de disco distintas**. El compilador incremental de Kotlin (`RelocatableFileToPathConverter`) intenta calcular una ruta relativa entre ficheros de `C:\` y `D:\` para su caché incremental, lo cual no tiene sentido en Windows (dos raíces distintas) y lanza `IllegalArgumentException`. Gradle lo captura, imprime varias trazas que parecen fatales (`Daemon compilation failed`, `Failed to compile with Kotlin daemon`) y automáticamente reintenta con `Using fallback strategy: Compile without Kotlin daemon` — **el build termina en `BUILD SUCCESSFUL` de todas formas**, solo tarda un poco más. No es un fallo real, no hace falta ninguna acción — pero al leer el log en caliente parece que el build ha fallado (varias páginas de stacktrace de Kotlin) cuando no es así; comprobar siempre el código de salida real y el `BUILD SUCCESSFUL` final antes de asumir que hizo falta reintentar nada.
