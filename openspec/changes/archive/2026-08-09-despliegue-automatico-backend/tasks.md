## 2. Servidor: usuario `ci-deploy` restringido a `scripts/deploy-local.sh`

Hallazgo real durante esta tarea (invalida el diseño original de clave SSH con `command=` forzado): el servidor no tiene `sshd` tradicional — `sudo ss -tlnp | grep ':22 '` no devuelve nada, todo el acceso SSH pasa por la implementación embebida de Tailscale SSH, que no soporta forzar un comando vía ACL. Ver `design.md` Decisión 2 para el diseño corregido: la restricción se aplica fijando la **shell de login** del usuario, no la clave.

- [x] 2.1 Escribir `scripts/deploy-local.sh` (nuevo, distinto de `deploy-prod.sh`): pensado para ejecutarse ya dentro del servidor — `git pull --ff-only origin master` → `docker compose -f infra/docker/docker-compose.prod.yml up -d --build` → verificación de salud (`curl`, con reintentos cortos) contra la IP de Tailscale del servidor. `deploy-prod.sh` no se modifica, sigue siendo el path manual desde fuera. Dos hallazgos reales corregidos: (1) la API solo escucha en la IP de Tailscale del servidor (`network_mode: host`, sin bind a loopback) — `localhost:8080` nunca conecta aunque el script corra en el propio servidor; (2) la IP se había hardcodeado inicialmente en el script — corregido a resolverla en tiempo de ejecución (`tailscale ip -4`), ya que este repo es público y ADR-035 prohíbe explícitamente comitear el host/IP real (mismo criterio ya aplicado en `deploy-prod.sh` y en `MOBILE_PROD_API_BASE_URL`).
- [x] 2.2 Usuario de sistema `ci-deploy` creado en el servidor (`useradd -m -N -G docker -s /home/gonzalo/moto-routes/scripts/deploy-local.sh ci-deploy`, sin `sudo`, sin contraseña). Como el repo real vive en `/home/gonzalo/moto-routes` (no en el `$HOME` de `ci-deploy`), se usan ACLs POSIX (`setfacl`) para dar acceso quirúrgico: `--x` (solo tránsito, sin listar) sobre `/home/gonzalo`, y `rwX` recursivo + ACL por defecto sobre `/home/gonzalo/moto-routes` únicamente — el resto del `$HOME` de `gonzalo` (`.ssh`, etc.) permanece inaccesible. `git safe.directory` configurado para `ci-deploy` (repo con dueño distinto). Corregido además `REMOTE_DIR` en el script: usaba `$HOME` (que para `ci-deploy` no es `/home/gonzalo`), cambiado a ruta fija.
- [x] 2.3 Bloque `ssh` con `"action":"accept"` añadido a la política ACL de Tailscale, concediendo a `tag:ci-deploy` sesión como `ci-deploy` en el servidor. Varios errores de validación/diseño reales, corregidos en el orden en que aparecieron: (1) `dst` no admite una IP directa en un bloque `ssh` — solo tag/grupo/autogroup; (2) se probó `dst: ["tag:ingress"]` asumiendo que era el tag del servidor — **error real**: `tag:ingress` pertenece a los nodos internos de Tailscale Funnel (`funnel-ingress-node`), no a `debian`, que no llevaba ningún tag; (3) `tag:ingress` tampoco estaba declarado en `tagOwners`. Solución final: tag nuevo y dedicado `tag:prod-server`, asignado a `debian` vía el panel (no por SSH, para no resetear otros flags activos del nodo), con una regla `ssh` adicional en modo `check` para preservar el acceso SSH humano de `gonzalo` a su propio servidor (que se habría roto al dejar de contar como `autogroup:self` tras etiquetarlo). Ver `design.md` Decisión 2 para el detalle completo.
- [x] 2.4 Verificación real (no simulada), varias rondas: `ssh ci-deploy@debian "echo comando-ignorado"` desde una máquina ya en la tailnet (como `gonzalo`) — el comando pedido se ignoró siempre y solo se ejecutó `deploy-local.sh`. **Corrección posterior importante**: esas primeras rondas en realidad pasaban por la regla `check` preexistente (`autogroup:self` cubre a `autogroup:nonroot`, que incluye a `ci-deploy` como usuario local no-root) — no por la regla `tag:ci-deploy` nueva, que en ese momento aún no funcionaba (ver 2.3). La verificación real de la regla `tag:ci-deploy` específica solo se consiguió con el runner efímero real de GitHub Actions (grupo 5).
- [x] 2.5 Ninguna credencial nueva de este grupo (no hay clave privada en este diseño) se comitea; el único artefacto nuevo versionado es `scripts/deploy-local.sh`, que no contiene secretos.

**Hallazgo adicional (no relacionado con `ci-deploy` en sí)**: el checkout de producción estaba en `feature/almacenamiento-fotos-backend` en vez de `master` (residuo de pruebas de sesiones anteriores) — corregido con `git checkout master && git pull --ff-only` antes de la verificación 2.4. De no corregirse, cualquier despliegue automático habría fallado siempre en el paso `git pull --ff-only`.

## 5. Verificación end-to-end real

- [x] 5.1 Release real `v0.1.5` (tag anotado, empujado desde `master` tras mergear la PR #112). El job `deploy-prod` quedó en `waiting` en la pestaña Actions hasta la aprobación, confirmado vía `gh api .../pending_deployments`.
- [x] 5.2 Aprobado (`gh api --method POST .../pending_deployments`, revisor `GonzaloCarmenado`). Costó **cuatro intentos reales** antes de un despliegue exitoso — todos los fallos revelaron bugs reales del diseño/implementación, no problemas del propio job en sí:
  1. `403 calling actor does not have enough permissions` en `tailscale up` — al cliente OAuth le faltaba el scope `Keys → Auth Keys` (solo tenía `Devices Core`). Corregido por el usuario en el panel de Tailscale.
  2. Mismo error tras el primer intento de arreglo — el usuario había marcado el scope pero no el selector de tags específico de `Auth Keys` (independiente del de `Devices Core`). Corregido.
  3. `tailscale: tailnet policy does not permit you to SSH to this node` — `tailscale up` ya funcionaba, pero la regla `ssh` de la ACL apuntaba a `tag:ingress`, que resultó ser el tag de los nodos internos de Tailscale Funnel, no del servidor `debian` (que no llevaba tag). Corregido creando `tag:prod-server` y asignándolo al servidor — ver grupo 2.3 y `design.md` Decisión 2.
  4. La sesión SSH ya se abría, pero `deploy-local.sh` no se pudo ejecutar como shell de login por falta del bit de ejecución — el commit original se hizo desde Windows y quedó `100644` en git; cada `git pull` en el servidor se lo quitaba. Corregido con un fix dedicado (PR #113, `git update-index --chmod=+x`) y aplicado además a mano en el servidor para desbloquear esta misma verificación.

  El quinto intento completó con éxito: `git pull` (already up to date) → `docker compose up -d --build` → recreación real de `docker-api-1` → verificación de salud en `200`. Log revisado confirmando que el host y las credenciales OAuth aparecen enmascarados (`***`), nunca en texto plano.
