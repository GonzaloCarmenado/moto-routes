# Plan de Implementación: Perfil de Usuario

## Decisiones de diseño resueltas en este plan

La spec deja explícitamente varias decisiones a criterio del plan-agent (ver "Notas de Implementación" de `perfil-usuario.md`). Se fijan aquí, todas dentro de los márgenes ya aprobados por la spec — ninguna añade AC nuevos:

1. **Cliente HTTP compartido en `src/shared/http/external-api.service.ts`**, genérico (no acoplado a vPIC en su interfaz pública, tal como pide la spec) — expone `fetchJson<T>(url, options?)` con timeout vía `AbortController` y un tipo de error `ExternalApiError` con `kind: 'network' | 'timeout' | 'invalid-json'`. Es la primera pieza de infraestructura reutilizable por integraciones externas futuras.
2. **Cliente vPIC en `src/profile/vpic.service.ts` (dominio `profile`, no `shared/`)**. Motivo: hoy solo `profile` lo consume — por la regla de `frontend-conventions.md` §4 ("shared solo con 2+ consumidores reales"), promoverlo a `shared/` sería prematuro. Si una feature futura necesitara otra API de vehículos, se revisaría entonces.
3. **CSP**: se añade `https://vpic.nhtsa.dot.gov` a `connect-src` en `tauri.conf.json`, host exacto (ADR-014). **No hace falta `@tauri-apps/plugin-http`**: el proyecto ya tiene precedente de que el `fetch()` nativo del WebView de Tauri 2 basta para una petición `connect-src` normal — `route-map.element.ts` ya pasa `https://tiles.openfreemap.org/styles/dark` directamente a MapLibre, que internamente usa `fetch()` nativo, sin ningún plugin Tauri, y funciona en Android real. Se recomienda registrar esto como **ADR-028** al implementar el Paso 6 (siguiente número disponible tras ADR-027).
4. **Control "Cambiar foto" del modal NO reutiliza la instancia del Web Component `<photo-capture>` tal cual.** Motivo: `app.element.ts` monta `cockpit-view`/`route-list`/`route-detail`/(ahora)`profile-view` como hermanos persistentes en el DOM, ocultos con `display:none` en vez de desmontados — si `profile-edit-dialog` insertara un `<photo-capture>` con su `data-cy="photo-add-button"` interno fijo, convivirían en el mismo documento con el `<photo-capture>` ya montado en cockpit/route-detail, rompiendo la unicidad de `data-cy` que exige AC-037 y arriesgando falsos positivos en Cypress (mismo tipo de riesgo ya documentado para `route-detail-title` en `cobertura-e2e`). En su lugar, `profile-edit-dialog` reutiliza únicamente las **funciones** de `photo-capture-adapter.service.ts` (`captureFromCamera`, `pickFromGallery`, `validatePhoto`) tras un botón y menú propios con `data-cy` únicos (`profile-btn-cambiar-foto`, `profile-menu-camara`, `profile-menu-galeria`) — duplicación deliberada y acotada del patrón de menú (mismo criterio ya aceptado en ADR-025 para el diálogo de guardado de ruta), no de la lógica de captura en sí (esa sigue centralizada en el adapter).
5. **La foto elegida en el modal NO se escribe a disco hasta pulsar "Guardar".** El archivo elegido se previsualiza con `URL.createObjectURL(file)` (síncrono, sin tocar el sistema de archivos) y solo se llama a `savePhotoFile()` (que si es Tauri copia a `appDataDir/photos/`) dentro del manejador de "Guardar". Es necesario para cumplir AC-011 (cancelar no persiste nada) sin dejar archivos huérfanos en disco — si se escribiera al elegir la foto y el usuario cancelase, el archivo quedaría guardado sin ninguna fila que lo referencie.
6. **`sanitizeRouteName` (100 caracteres, trim) se generaliza a `shared/utils/text.ts` → `sanitizeText(raw, maxLength)`.** El campo de nombre de perfil (AC-008) necesita exactamente la misma regla que el nombre de ruta (`mejoras-guardado-rutas.md` AC-009, ya citada como referencia directa por esta spec). Duplicar 2 líneas sería tolerable, pero al ser lógica *idéntica* entre dos dominios, la convención (`frontend-conventions.md` §7, "duplicar lógica entre dominios → extraer a shared") pide extraerla. `cockpit.transform.ts` mantiene `sanitizeRouteName` como wrapper fino sobre la nueva utilidad — sin cambio de comportamiento ni de tests existentes.
7. **Tipo/marca/modelo de vehículo se implementan como tres `<select>` nativos**, no como botones tipo toggle — es la lectura más literal de "select de marca"/"select de modelo" (AC-018/019/020) y del propio `data-cy` sugerido en la spec (`profile-select-*`, singular), y es el widget más simple y accesible para una lista dependiente de la API.
8. **`IProfileRepository` se crea e inyecta desde `app.element.ts`**, igual que `IRouteRepository` — no vía un `createProfileRepository()` en `shared/services/` (a diferencia de `createPhotoRepository()`, que sí vive ahí porque 3 dominios distintos lo necesitan). Solo `<profile-view>`, montado una vez en la raíz, necesita `IProfileRepository`.
9. **Promoción de `.stat-tile`/`.stat-grid`**: se extraen a `src/shared/styles/stat-tile.css` (CSS puro, sin Web Component nuevo — hoy son solo clases visuales, no un componente con lógica). `cockpit.element.css` y `profile.element.css` lo importan con `@import`, mismo patrón que ya usan con `tokens.css`. No se crea un `<stat-tile>` custom element — no lo pide la spec y sería sobreingeniería para algo que hoy es únicamente CSS.
10. **Gap real detectado — no resuelto por este plan, requiere decisión o refinamiento de la spec**: AC-019 pide que `GET /vehicles/GetModelsForMake/{make}?format=json` se use "filtrado por el tipo de vehículo elegido". Según la documentación pública de NHTSA vPIC, la respuesta de ese endpoint concreto **no incluye un campo de tipo de vehículo por modelo** (solo `Make_ID`, `Make_Name`, `Model_ID`, `Model_Name`) — el filtrado por tipo solo es real en el paso anterior (`GetMakesForVehicleType`, que ya limita las marcas al tipo elegido). El Paso 5 implementa un filtrado **defensivo y best-effort** (`filterModelsByVehicleType()`: filtra solo si la respuesta trae un campo de tipo; si no, no filtra nada) para no romper si la API cambiara, pero **hay que verificar el comportamiento real de la API contra un dispositivo/entorno con red durante el Paso 5** antes de dar AC-019 por cerrada tal cual está escrita. Si se confirma que no hay campo de tipo en la respuesta real, se recomienda reescribir AC-019 para reflejar que el filtrado ocurre únicamente al elegir la marca (paso previo), no como un segundo filtro sobre los modelos — **esto es responsabilidad de `spec-agent`, no de este plan**.
11. **Gap de nav-bar detectado, no un AC nuevo — infraestructura necesaria para cumplir AC-036 tal cual está escrita**: `nav-bar.element.ts` tiene hoy `nav-item--active` **hardcodeado únicamente en el botón "Grabar"** (`btn.className = 'nav-item nav-item--record nav-item--active'`), nunca se ha implementado un toggle dinámico real — "Rutas" nunca se marca activo al navegar a él, pese a que AC-036 de esta spec da por hecho que "ya lo reciben Grabar/Rutas al estar activos". Para que "Perfil" pueda marcarse activo correctamente (y los otros dos inactivos) hace falta implementar por primera vez el mecanismo genérico de vista activa en `nav-bar` (Paso 14) — como efecto colateral, esto dejará también "Rutas"/"Grabar" correctamente sincronizados por primera vez. No se trata de un comportamiento nuevo fuera de alcance: es lo mínimo necesario para que AC-036 sea cierto.

## Paso 4: Cliente HTTP compartido con timeout

- **Issue**: [#69](https://github.com/GonzaloCarmenado/moto-routes/issues/69)
- **Objetivo**: Base reutilizable para cualquier integración con API externa (esta y futuras), con timeout explícito y manejo diferenciado de error de red/timeout/respuesta no-JSON.
- **AC cubiertos**: AC-027.
- **Tests a escribir** (`external-api.service.spec.ts`, mockeando `global.fetch` con `vi.stubGlobal`):
  - Test: `fetchJson('https://example.com/x')` con `fetch` resuelto en éxito y `response.json()` resuelto devuelve el objeto parseado tal cual.
  - Test: `fetch` rechaza con un `TypeError` (fallo de red típico del navegador/WebView) → `fetchJson` rechaza con un `ExternalApiError` cuyo `kind` es `'network'` → Valida AC-027.
  - Test: `fetch` nunca resuelve dentro del `timeoutMs` configurado (usar `vi.useFakeTimers()` + una promesa que no resuelve) → `fetchJson` rechaza con `ExternalApiError` `kind: 'timeout'`, y el `AbortController` interno se aborta (verificar que la señal pasada a `fetch` se marca `aborted`) → Valida AC-027.
  - Test: `fetch` resuelve pero `response.json()` rechaza (cuerpo no-JSON, p. ej. una página de error HTML) → `fetchJson` rechaza con `ExternalApiError` `kind: 'invalid-json'` → Valida AC-027.
  - Test: `timeoutMs` por defecto es un valor razonable (p. ej. 8000) si no se especifica, y es configurable por llamada.
  - Test: al resolver o rechazar (en cualquiera de los casos), el `setTimeout` interno del timeout se limpia (`clearTimeout`) — regresión de fuga de temporizador, verificable con `vi.getTimerCount()`.
- **Archivos a crear/modificar**:
  - `CREAR src/shared/http/external-api.service.ts`: `export type ExternalApiErrorKind = 'network' | 'timeout' | 'invalid-json'`; `export class ExternalApiError extends Error { constructor(public readonly kind: ExternalApiErrorKind, message: string) { super(message); } }`; `export async function fetchJson<T>(url: string, options?: { timeoutMs?: number }): Promise<T>` — implementación con `AbortController`, `setTimeout(() => controller.abort(), timeoutMs ?? DEFAULT_TIMEOUT_MS)`, `try { const res = await fetch(url, { signal: controller.signal }); ... } catch (err) { if (controller.signal.aborted) throw new ExternalApiError('timeout', ...); throw new ExternalApiError('network', ...); } finally { clearTimeout(timer); }`, y un segundo `try/catch` alrededor de `res.json()` para el caso `'invalid-json'`.
  - `CREAR src/shared/http/external-api.service.spec.ts`: tests de arriba.
- **Notas**: Interfaz pública genérica — **no** debe mencionar vPIC ni vehículos en ningún nombre. `options` se deja abierto a crecer (p. ej. `headers` en el futuro) sin romper la firma actual. No usa ningún plugin de Tauri — `fetch()` nativo, disponible tanto en navegador como en el WebView de Tauri.
